- source_spec: `spec-4-xlsx-parquet-sources.md`
  summary: A raw `BYTE_ARRAY` Parquet column lands as the decoded string rather than as compact JSON, which is not what the Boundaries say.
  evidence: The spec groups "raw BYTE_ARRAY" with nested LIST/MAP/STRUCT under "text cells carrying compact JSON". Measured, hyparquet's default parsers decode an undeclared `BYTE_ARRAY` through `stringFromBytes`, so the value that reaches the adapter is already a `string` — JSON-wrapping it would produce `"Anna"` with quotes in the cell, which is worse for the user and worse for a later join. The column is still `text` and still carries the `parquet.unsupported_type` warning naming it, so nothing is silent; only the cell shape differs, and only for a type nothing declared anything about. Genuinely non-primitive values (a LIST, a MAP, a STRUCT, a JSON blob) do get compact JSON, as specified.
  status: **closed as decided, 2026-08-02 — the project owner confirmed the deviation: the behaviour stands and the Boundaries wording is what should move.** Quoting a decoded string back into the cell would be worse for the user and worse for a later join, so the code is right and the frozen line ("raw BYTE_ARRAY" grouped with nested types under compact JSON) is what was written without knowing hyparquet decodes first. Correct the Boundaries at the next renegotiation of this spec rather than opening one for a wording fix. Revisit only if a Parquet writer in the wild uses undeclared `BYTE_ARRAY` for non-text bytes, where the decode would be lossy; none seen so far.

- source_spec: `spec-3-typing-step-zero.md`
  summary: Detection blocks the main thread for 991 ms at the NFR-3 per-Source target of 100,000 rows by 20 columns, and again on every encoding or header-row re-read. It is linear in rows × columns, so a 200-column Source of that height costs about ten seconds.
  evidence: Reading every value is the frozen premise of the story (FR-9) and is not up for revision; the cost of doing so was. Two rounds of it are already paid — `score()` no longer allocates a row-index set per candidate, and a single pass now narrows the candidates to those a value could match, which took the NFR-3 shape from 1,499 ms to 991 ms and a 500,000-row integer column from 322 ms to 164 ms. The measured rate is about 2 million cells per second. What is left is real per-value work, and the routes out are all costly. **A worker is not one of them:** AD-15 forbids sending a dataset off-thread to compute on it, and R4 measured why — a structured clone of 100,000 rows blocks the sender for 109–132 ms and half a million for 511–627 ms, against 263–446 ms for the whole pipeline. That leaves making detection async so it can yield between columns, which turns `addSource` into an async command and touches the AD-10 command shape everywhere; or fusing the per-candidate walks into one pass over the values, which is maybe another third and makes `score` markedly harder to read. Both want a measurement harness in the repo rather than a script in a session, and neither belongs to a story about what a column is.
  status: **decided 2026-08-02 by the project owner — the harness first, the optimisation after.** Neither route is to be chosen by feel: async detection touches the AD-10 command shape everywhere, and fusing the candidate walks makes `score` markedly harder to read, so both are expensive enough to deserve a number rather than an intuition. The next step is a committed measurement harness that reproduces the 991 ms shape and the 200-column case; only then does the choice between async and fusion get made.

- source_spec: `spec-4-xlsx-parquet-sources.md`
  summary: Five Parquet and XLSX shapes were carried as untestable — INT96, a byte-array-backed DECIMAL, a repeated Parquet column name, a password-protected workbook, and a zero-sheet workbook — on the strength of a rule ("no binaries in git") that was never the project owner's.
  evidence: The rule was invented during story 4 and struck by the owner on 2026-08-02. The real blocker was always narrower and only ever about *generation at test time*: `hyparquet-writer` cannot write INT96 (`writePlain` throws), accepts only INT32/INT64 backing for DECIMAL, and resolves `columnData` against the schema by name so it cannot emit a duplicate; `write-excel-file` writes no encryption and always emits a `Sheet1`. None of that says the bytes cannot exist.
  status: closed 2026-08-02 — **all five produced, committed under `tests/fixtures/`, and wired into the adapter tests**, with `tests/fixtures/generate.mjs` + `generate.py` committed beside them so any of them can be remade and inspected. pyarrow 25.0.0 in a throwaway venv made the three Parquet files; LibreOffice via the UNO API made the protected workbook (its `--convert-to` filter options silently ignore a password — every documented spelling produced a plain `PK\x03\x04` zip, so UNO was the only route); `fflate`, reached through `read-excel-file`'s own dependency rather than added to `package.json`, made the zero-sheet workbook. **What the fixtures found:** the `risk:` note on the old entry was wrong about INT96 and byte-array DECIMAL and right to be suspicious in general. Both read correctly — hyparquet's parsers hand over a `Date` and a scaled number respectively, so the type map and the canonicalizer already held, and both columns sweep 100 % readable. The duplicate column name was a **live silent-corruption defect**: `rowgroup.js` resolves an array slot by `findIndex(c => c.pathInSchema[0] === name)`, so both `Betrag` columns carried the first one's values and a UTF8 column of `brutto`/`netto` displayed `1`/`2` under its own header, with no diagnostic. Fixed — a repeated name is now refused per column with `parquet.duplicate_column_name`, every other column in the file still read. Two follow-on entries remain open above: the zero-sheet branch (a `read-excel-file` bug, now named) and ZSTD/LZ4 fixtures.

- source_spec: `spec-4-xlsx-parquet-sources.md`
  summary: **`hyparquet` decompresses UNCOMPRESSED and SNAPPY only.** A Parquet written with GZIP, ZSTD, BROTLI or LZ4 — all of them ordinary defaults in the Spark, pandas and DuckDB ecosystems — could not be read at all.
  evidence: `datapage.js:129` throws `parquet unsupported compression codec: <codec>`. The reader read the codec off the metadata before touching a page and refused with `parquet.unsupported_codec`, so the card named the codec and said the file itself was in order — true, and still not the file read. The fix was `hyparquet-compressors`, a **runtime dependency beyond the two this spec's approval covered**, and therefore an explicit Ask First.
  status: closed 2026-08-02 — **put to the project owner and approved.** `hyparquet-compressors@1.1.1` (MIT, 161 KB unpacked, same author family as hyparquet) is a runtime dependency now, passed to `parquetRead` as `compressors`. It brings `fzstd` (pure JS) and `hysnappy` (WASM), and its snappy replaces hyparquet's pure-JS one. **No architecture decision forbids WASM**: the spine rejected `parquet-wasm` and DuckDB-WASM over multi-MB payloads *fetched at runtime*, and this is neither — the module is base64-inlined and instantiated with `atob` + `new WebAssembly.Module`, so the AD-18 gate holds, verified by building rather than assumed. The artefact went from 246,399 to 361,045 bytes. One hazard came with it and is pinned rather than noted: Chrome refuses a synchronous `new WebAssembly.Module` above **4,096 bytes** on the main thread and hysnappy's module is **3,458** — 638 bytes of margin. `scripts/assert-single-file.mjs` now finds the inlined module by its `AGFzbQ` base64 preamble and fails the build if it reaches the ceiling, and `tests/e2e/xlsx-parquet.spec.js` loads a snappy Parquet from the built `dist/index.html` in both engines and asserts the cells — a Vitest case would pass under Node whatever Chrome does, and so would the dev server. `parquet.unsupported_codec` stays, and is now the right answer for LZO instead of the wrong one for gzip.

- source_spec: `spec-3-typing-step-zero.md`
  summary: Step zero detects three types — `text`, `number`, `date` — and no text column can ever become a `datetime`, a time, a boolean, or a number carrying `%` or `€`. A timestamp column out of any ERP export is `text`, and so is every margin and every amount.
  evidence: Raised by the project owner on 2026-08-02 after using story 3. Measured against the built `detectColumn`, all of these return `text`: `2025-12-31T14:30:00`, `2025-12-31 14:30:00`, `31.12.2025 14:30`, `14:30`, `ja`/`nein`, `true`/`false`, `12,5 %`, `1.234,56 €`, `(1.234,56)`, `1.234,56-`, `31.12.25`. `text` is not a wrong answer that gets corrected — it is a column that can never be filtered with `>`, never summed, never grouped by month. `datetime` and `boolean` exist as words in AD-21 and in story 4's type map, but only a reader can produce them, so the same table is typed when it arrives as XLSX and untyped when it arrives as CSV. Separately, a digit string past `Number.MAX_SAFE_INTEGER` — a 19-digit order number — is reported as `number`, `settled`, 100 % readable, and loses its last digits when story 6 converts it; story 4 already names the same defect for Parquet INT64 (C-10), from the other side.
  status: closed 2026-08-02 — split three ways with the project owner and each part given a home. **Story 4** (spec amended, this session): the positive list of admissible `native:<type>`s, and the type catalogue in `core/types` that ends the four-way duplication of the type vocabulary — both because story 4 edits all four sites anyway. **New story 4a** (`stories.yaml`, this session): `datetime`, `time`, `boolean`, affixed numbers (percent and currency), accounting signs, the `MAX_SAFE_INTEGER` guard for the text path, and two-digit years — placed between 4 and 6 because story 4 lands the vocabulary it builds on and story 6 converts what it decides. **Ledger** (above): the space grouping separator, waiting on a real Source. **Cut, with reasons:** month names (the note in `typing.js` already says a story brings its own calendar evidence); exponential notation (a machine form, not something a person types into a report); ISO weeks, `2025-06` and quarters (period labels, not instants — they belong to whatever story first groups by period); `integer` as a type distinct from `number` (the precision guard removes the corruption, and a second numeric word buys nothing a user can see in the MVP).
  note: One claim made while triaging this was wrong and is recorded so it is not made again. Percent was argued to be ambiguous, on the reading that `12,5 %` might mean 12,5 or 0,125. It is not: `%` is a decisive marker competing with no second reading, exactly like a leading zero, and the number in front of it carries only the ordinary de/en ambiguity. What the argument actually described was a storage decision, and story 4a takes it — the stored number is 12,5, because that is what stands in the field.
