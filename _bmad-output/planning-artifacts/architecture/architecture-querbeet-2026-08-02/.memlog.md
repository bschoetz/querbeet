- (constraint) Stack is INHERITED from the PRD addendum, not decided here: Arquero 8.0.3, Vue 3.5.40, Vite + vite-plugin-singlefile, Vue Flow 1.48.2, ECharts 6.1.0 SVG-renderer-only, PapaParse 5.5.4, write-excel-file 4.1.1 / read-excel-file 9.3.5, jsonrepair 3.15.0, json-formatter-js 2.5.23, hyparquet-writer 0.16.3 + hyparquet 1.27.1, date-fns 4.4.0, Tailwind v4.3.3 without preflight, IndexedDB with no library. All versions verified against the registries during research runs R1-R9 on 2026-08-01, one day before this run. Do not re-decide; the spine records them as seed.
- (decision) Paradigm = hexagonal (ports and adapters) with a pipes-and-filters domain inside the core. Ben chose it over a layered Vue app and over pipes-and-filters as the whole paradigm. Two properties decided it: a Recipe enters through three doors (Editor, clipboard from a model, loaded file or Package) and FR-28 requires identical validation at each, which a single core guarantees structurally rather than by discipline; and every hard constraint of this product sits at an edge (opaque file:// origin, no network, single-file build, blob-URL classic workers), so a core that knows nothing about them is immune to them and testable outside a browser. Cost named and accepted: more indirection than a solo project strictly needs.
- (decision) Typing is applied as an implicit Step zero, not materialized at load. The registry holds raw parsed tables (strings); the Recipe's type record is applied by the engine as a cached Step like any other. Consequences Ben accepted: a Recipe re-run on fresh files reproduces typing exactly, swapping Recipes leaves the registry untouched, and FR-9's retained original is structural rather than a second in-memory copy.
- (decision) Per-Step cache is content-addressed: key = hash(canonical serialization of the step config + the keys of its inputs). Chosen over a per-Step revision counter and over a dirty flag. Nearly free because the Recipe format must define a canonical serialization anyway — the Editor spike measured a byte-identical 1,309 B round trip for a six-Step graph. Both FR-38 execution modes share this one cache, and undo/redo plus A/B comparison reuse entries for free.
- (decision) Two conventions set by the architect rather than elicited, both derived from settled requirements. Diagnostics have one shape across every Step and loader — {severity, code, message, stepId, rowCount?} — because FR-34 aggregates them into the run status and cannot if each site invents its own. IDs are short and human-readable (src:patch, s1, s2) rather than UUIDs, because FR-28 requires a language model to author them and the authorship spike measured that working.
- (constraint) Registry ownership conflict resolved by the architect: the addendum describes a shallowRef registry while the adopted rule forbids framework imports in the core. Resolution — the registry is a plain Map owned by the core, and the Vue layer wraps it in shallowRef for rendering. The measurement that mattered was 'no proxy over the data' (R2: 437-479 MB and 11-13x slower reads), which holds either way.
- (decision) Recipe format carries a version field and a mismatch is REFUSED naming both versions, rather than migrated. Consistent with the product's stance everywhere else — refuse rather than silently do the wrong thing. Consequence accepted: a Consumer holding an old Recipe needs a freshly exported one from the Author. Migration is named as the first post-MVP candidate. Follow-on the architect notes: the application must therefore display its own build version where a Consumer can read it back to the Author.
- (decision) State changes go through named commands — addStep, connect, reconfigure, deleteStep — and the UI never mutates the model directly. Chosen over direct mutation on a reactive store. What it buys structurally: the cycle guard runs at exactly one place, the Vue Flow projection has exactly one source of change, and undo/redo later is recording commands. Decisive evidence: the Editor spike measured that Vue Flow's mutation API contains no cycle detection at all, so the guard must sit in front of it — direct mutation would need that remembered at four separate sites.
- (decision) Testing = Vitest over the pure core plus Playwright over the built artifact opened from file://. This dimension was decided by no prior document. Vitest covers validator, graph guards, type and locale detection, Step functions and cache keys, with no browser. Playwright covers what only appears from file:// — blob-URL workers, IndexedDB, the shared storage bucket — and asserts the build emits exactly one file in dist/, which the addendum records as a silent failure mode with no build-time signal. The spikes already use Playwright, so the harness exists.
- (decision) Step boundaries carry a Table handle behind querbeet's own narrow Table interface, which Arquero implements; materialization to plain row arrays happens only at the real edges (preview, export, IndexedDB, worker transfer). SUPERSEDES the PRD addendum's reversibility seam, which states the boundary is plain arrays of objects. Replaceability is preserved but moves from the row shape into the interface: swapping the engine becomes one interface implementation instead of a per-operation change. Driver: at 30 Steps the per-boundary wrap/unwrap could dominate, and nobody measured it — R4 measured only the whole pipeline at 263-446 ms for 100k rows. Ben was told the number is missing and chose anyway. UPSTREAM ACTION OWED: addendum section 5 must be corrected or it silently contradicts the spine.
- (decision) Architect's own calls, each forced by an adopted rule or a measurement rather than elicited. Step functions stay synchronous while the SCHEDULER is chunked and async, because FR-38 needs progress and cancellation and R4 measured that cancellation has to run through the message queue (3.0/2 ms at ~5 ms chunks, progress ~2.6% overhead) since SharedArrayBuffer is hidden from file://. Workers exist only for the two exports and are owned inside the TableWriter adapter, so the core never knows a worker exists. The UI is a driving adapter: browser File objects never reach the core, which receives bytes and a name. LLM profile computation is core; the clipboard is a port. SessionStore keys carry a discriminator because R9 measured the file:// origin as one shared bucket across directories.
- (question) Deferred by absence of research, both named in PRD section 8: the view-document export adapter (FR-37) has no research at all since R8 is unrun, and the Package container (FR-24) is open past R9's IndexedDB gate. Both sit behind ports that the spine defines, so the gap is an unimplemented adapter rather than an undecided boundary.
- (decision) Unparsed values are boxed cells carrying the original text, and the TableEngine adapter is the single place that knows the box — comparison never matches one, aggregation skips and counts it, sorting groups them, export writes the original text. Ben chose it over a sidecar column (which leaks into every column enumeration: FR-13 union mapping, FR-16 selection, FR-21 contract, FR-26 profile, every export) and over a sparse overlay on the Table handle (which cannot survive a join, and UJ-1 has two joins before its filter, so the markers would be gone by the Result).
