- (decision) TWO USER ROLES emerged, not one: (a) recipe author = Ben, builds the pipeline; (b) recipe consumer = a business department that receives a recipe, drops it plus their own files into the tool and reads the result. Consumer never builds a pipeline and never sends Ben their data. This is the core value driver: 'Fachabteilungen helfen sich selbst und verschwenden meine Zeit nicht'
- (decision) Ben's competitive framing vs PowerQuery: (1) no special software needed — drag recipe + files in, result falls out; (2) likely faster than PowerQuery, which 'lahmt'; (3) adaptations can be discussed with an LLM instead of experimenting in PowerQuery by hand
- (decision) NEW CONCEPT — LLM probe queries: the LLM writes verification/exploration queries, the tool runs them locally against the real data and returns only the RESULT to the LLM. Data never leaves the system even while the LLM learns about it. This partially supersedes the earlier 'structure + opt-in sample values' decision
- (decision) NEW CONCEPT — column annotations: the user can describe what a column contains; those descriptions are fed to the LLM so it can reason about semantics (e.g. that 'Kst' and 'Kostenstelle' are the same thing)
- (decision) Ben softened on the LLM API binding: copy-paste interaction with a chat AI is explicitly 'charmant' to him and an API binding is 'nicht zwingend nötig'. Re-decide against the earlier 'standalone MVP feature with API' answer

- (decision) Ben named PDF as an export target and an interactive HTML export the recipient can filter further. idea.md section 1 lists PDF export as explicitly out of scope for MVP — contradiction to resolve
- (event) Vision elicitation round 1 complete
- (decision) LLM channel decided: copy-paste protocol is primary and always available (tool generates a prompt block, user pastes into any chat AI, pastes the answer back). An optional API key automates the same conversation. Tool stays fully functional and offline without a key. Supersedes the earlier 'API only' answer
- (decision) Recipe artifacts decided: TWO named artifacts. (1) Recipe = steps, settings, expected input files — data-free. (2) Package = recipe plus raw data, for handing a concrete run to someone else. Not one format with a checkbox
- (decision) MVP result exports decided: Excel/CSV/JSON, Parquet, and a static HTML/PDF view document. INTERACTIVE HTML (recipient can filter/sort in the exported file) is OUT of MVP — Ben dropped it as the most expensive item
- (decision) Parquet confirmed in MVP scope, which per R3 makes the Vite build step mandatory rather than optional (hyparquet-writer is ESM-only, no UMD)
- (decision) Named consumer persona: Christian, head of the consulting practice. Wants to measure consultant utilisation and profitability by relating HR data, project/lead data, time-booking data and billing data — four sources. Not a BI professional. Today: manual Excel, incomplete, shallow, probably gap- and error-ridden. He is the person a recipe is written for
- (decision) Consumer MUST be able to repair a recipe whose input files do not match (renamed columns from a different export setting). Repair is in scope — depth to be decided
- (decision) Ben's own patch-report outcome: a compliance status for the audit file, plus a list of people the CISO can chase about missing updates. The deliverable is a list plus a status, nothing exotic
- (decision) Non-users confirmed: live database/API connections, shared team tool with permissions/user management. NOT confirmed as a non-user: large data — Ben explicitly does not want a hard row cap built in, but expects to rarely exceed 100k rows. Design target stays ~100k; do not engineer an artificial block
- (decision) Repair depth decided: MVP ships ONE app with a full editor for everybody — no consumer mode, no permissions. But the pipeline is NOT the landing view: the editor is a distinct area the user deliberately enters, behind an acknowledgement that this is where things can break. A roles/rights/views model is explicitly post-MVP
- (decision) Recipe/data mismatch handling decided: PRE-FLIGHT CHECK. A recipe carries an expected contract (files, required columns, coarse types). Before the first step runs, the tool validates and shows a status per requirement — fits / missing / doubtful. Execution only starts after that
- (decision) EVIDENCE GAP, load-bearing: Ben does not know how Christian actually works today. Only that Christian is unhappy, lacks data, and does not know how to process what he has. UJ-2 (the Consumer journey) is therefore a HYPOTHESIS, explicitly tagged as such in the PRD, not a captured journey. The entire recipe-handoff value proposition rests on this one unvalidated user
- (decision) RISK named to Ben: 'ihm fehlen Daten' is a data-ACQUISITION problem; querbeet solves data-CONSOLIDATION. If Christian's main pain is acquisition, the tool only half hits him. Cheapest mitigation: a 20-minute conversation with Christian — 'show me the files you have and what you do with them today'. Becomes an open question with an owner
- (decision) [ASSUMPTION] Aggregate (group-by) added as a sixth Step kind, against idea.md and the README roadmap which both place it post-MVP. Rationale: Christian's job (utilisation and profitability) cannot be expressed without grouping, and Top-N tiles and key figures presuppose it. Flagged to Ben for contradiction
- (decision) Typing decided: detect with a German-aware parser, show the guess plus a hit rate per column, let the user correct — AND the Pipeline does not run until the user has actively confirmed the type mapping of each Source once. The confirmation is stored in the Recipe. Unparseable values are marked, never silently nulled
- (decision) Computed columns decided: click-together only, from a fixed operation list (add/subtract/multiply/divide two columns, concatenate with a separator, date difference in days, ratio of two columns). No expression language, no formula parser. Rationale carried: an LLM can emit the fixed form as JSON trivially and cannot invent syntax the parser does not know
- (decision) Persistence decided: BOTH Recipe and loaded Source data survive a reload (IndexedDB), plus a prominent and simple way to delete the stored data. Overrides idea.md open decision 4. Consequence: the tool now writes company data to the browser profile, so the delete affordance is a requirement, not a convenience
- (decision) Filtering: two distinct concepts confirmed. Pipeline Filter Step changes the Result and lives in the Recipe. View Filter on the table header is transient exploration and does NOT live in the Recipe — but a 'promote this view filter to a Pipeline Step' action bridges them
- (decision) Dashboard model confirmed: flat tile list in a fixed grid, order via up/down, three size steps, no drag positioning, no overlap. Tile kinds in MVP: table, Top-N/Bottom-N, bar, line, key figure. All configured through one small mask (group-by column, measure column, aggregation, row count). The Dashboard lives in the Recipe. Anything richer is post-MVP
- (decision) Own search over the FULL dataset confirmed as a product requirement — Ctrl+F cannot find virtualized rows and cannot be intercepted (R4). Without it a user searches for a name, does not find it, and concludes the data is wrong
- (decision) Landing view confirmed: loading a Recipe plus files lands on the Dashboard after the Pre-flight Check, with a VISIBLE status of whether loading ran cleanly. Starting empty lands directly in the Editor
- (decision) Dashboard is evidenced by UJ-1, not only by the unvalidated UJ-2: Ben wants a bar chart of patched vs unpatched devices and an OS version distribution across the device fleet for the patch report. Removes the concern that the Dashboard block served only a hypothetical user
