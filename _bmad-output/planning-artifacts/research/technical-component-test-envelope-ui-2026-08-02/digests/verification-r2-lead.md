# Digest — Round 2 lead verification (not firewalled; primary-source spot-check)

Two round-1 items were flagged as load-bearing and contested/unconfirmed. Per `references/verification.md` (`normal` validation — spot-check load-bearing claims at landing), the lead checked both directly against primary sources: Playwright's own release notes/npm registry (via `gh` CLI and `npm view`), and happy-dom's actual source code (via GitHub contents API). This is a primary-source fact-check, not requirements-setting, so running it without the research firewall is consistent with the method (the firewall protects against project context biasing *what's true*; a `gh api` fetch of a changelog is not exposed to that risk).

## Playwright Component Testing: resolving the "stable vs. experimental" tension

- `gh api repos/microsoft/playwright/releases/tags/v1.62.0` (fetched in full): confirms the new **"stories and galleries"** `fixtures.mount()` model shipped as a headline, non-experimental-labeled feature in 1.62.0 — matching this project's already-installed `@playwright/test` version.
- `npm view @playwright/experimental-ct-vue`: the OLD per-framework package is **still published** (1.62.1, "published 3 days ago" relative to access date), still maintained by Playwright/Microsoft's own team (maintainers list: `pavelfeldman`, `yurys`, `dgozman-ms`, `playwright-bot`), tracking each core release in lockstep (`@playwright/experimental-ct-core: 1.62.1` pinned exactly), depending on `@vitejs/plugin-vue: ^6.0.7` — the same major this project already has (6.0.8).
- `gh api repos/microsoft/playwright/contents/packages/playwright-ct-vue/README.md`: the package's own README still reads, verbatim: **"BEWARE This package is EXPERIMENTAL and does not respect semver."**
- `gh api repos/microsoft/playwright/releases/tags/v1.59.0`: Breaking Changes section confirms **"Removed `@playwright/experimental-ct-svelte` package"** — independently verifies currents.dev's claim directly from the primary source.
- `gh api repos/microsoft/playwright/issues/26778/comments`: one comment, from Playwright maintainer `aslushnikov`, dated 2023-08-29: *"There's no estimated date [for a non-experimental release] ... Playwright evolves according to user feedback with a monthly cadence."* This was true in 2023 for the old per-framework packages; it is superseded by the 1.62.0 changelog above for the *new* model, and does not itself constitute a "stable" claim for the new model beyond what the docs already state.

**Resolution: this was not actually a contradiction between two sources about the same thing** — round 1's two subagents (jsdom/happy-dom and Playwright-CT researchers) were each, in effect, describing a different one of two coexisting mechanisms. Today, for a new adopter on Playwright ≥1.62 (which this project already is): the **new, package-free `fixtures.mount()` model is the relevant candidate**, shipped as a real (non-experimental-labeled) feature of core `@playwright/test`, needing no additional dependency. The **old** `@playwright/experimental-ct-vue` package is a separate, parallel, genuinely still-experimental-by-its-own-admission mechanism that a new adopter has no reason to reach for. Both are real and both are currently published; they are not the same thing.

## happy-dom source-level fidelity (resolving round 1's "unconfirmed" gap)

Read directly from `capricorn86/happy-dom`, `packages/happy-dom/src/`:

- `resize-observer/ResizeObserver.ts`: `observe()`, `unobserve()`, `disconnect()` are each body-only `// TODO: Not implemented` — a pure stub, never fires a callback. **Confirms jsdom-equivalent failure for ResizeObserver.**
- `nodes/element/Element.ts`, `getBoundingClientRect()`: `return new DOMRect();` unconditionally — comment: `// TODO: Not full implementation`. **Confirms jsdom-equivalent failure — always a zero rect.**
- `nodes/element/Element.ts`, `scrollTop`/`scrollLeft`/`scrollHeight`/`scrollWidth`: plain getter/setter pairs backed by private fields (`PropertySymbol.scrollTop` etc.), default `0`, but **genuinely settable and readable** — not hardcoded, not stubbed. A test that does `el.scrollTop = 500` and reads it back gets 500. It is not *computed from real layout* (nothing recalculates it from actual rendered content height), but nothing in this project's row-window mechanism needs that: the component reads whatever `scrollTop` currently holds and does fixed-row-height division, entirely independent of whether that number came from a real scroll gesture or a test setting it directly.

## Decisive project-side finding (read from this project's own source, not the web)

`ui/RowWindow.vue`'s untested AD-24 paging branch (`v-if="view.pages > 1"`, the two buttons, their disabled states, the German labels) is driven entirely by `view.pages`, which `core/view/row-window.js`'s `buildWindow()` (line 206) sets from `pageCount(total)` (line 68) — a function of `table.rowCount` alone. `sliceRows()` (line 152) only ever reads the small window of column-cell indices actually rendered, regardless of the table's claimed `rowCount`. **A test can reach the paging UI with a fake `props.table` object carrying a large `rowCount` and a tiny/sparse `columns[].cells` array — no real half-gigabyte CSV fixture, no real scroll gesture, and (this is the point) no real `getBoundingClientRect`/`ResizeObserver`/computed-`scrollTop` needed at all.** The gap that motivated R10 is a plain props → template-output test, not a geometry test.

This reframes the decision-criterion in the R10 brief that says "a DOM emulator may not be able to assert what actually matters here" — that concern is real for *some* future `ui/` component (anything that measures real layout, e.g. anything mirroring the Editor canvas's per-node `ResizeObserver`), but it does not apply to the specific gap that opened this research.
