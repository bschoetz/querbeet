A component-test envelope for ui/

Decision: Should querbeet add a third test envelope for Vue components, and if so which one?

Executive summary

Verdict: add @vue/test-utils + happy-dom as a second Vitest project, scoped to ui/** only weighted score 84/100. Runner-up: Playwright Component Testing's new built-in model 82/100, near-tie — reach for it specifically when a future ui/ component needs real ResizeObserver/getBoundingClientRect behavior, since the project already carries @playwright/test ^1.62 and this costs zero new dependencies. Vitest Browser Mode scores third 72/100: real-browser fidelity, but a documented CI wall-clock regression and an extra helper dependency of unresolved provenance make it the more expensive of the two real-browser options for no fidelity gain over the runner-up.

The gap that opened this research does not need what the brief worried it might need. ui/RowWindow.vue's untested AD-24 paging branch depends only on core/view/row-window.js's buildWindow(), which derives .pages from table.rowCount alone — verified by reading the source directly. A fake props.table with a large rowCount and a tiny columns[].cells array reaches the branch; no real scroll gesture, no real layout, and no getBoundingClientRect/ResizeObserver at all. jsdom or happy-dom are sufficient for exactly the trigger case, which is why the geometry-fidelity criterion turns out not to decide this run.

What does decide it is cost against a five-year horizon. happy-dom needs no browser binary, starts near-instantly, and slots into the existing npm test (Vitest) runner as one more project. Both real-browser candidates run through a Vite dev server over HTTP, not the shipped file:// artefact (verified for all three), so none of the three candidates tests what AD-27's second envelope already owns — that job stays where it is.

One correction that changed the shape of this run: round 1 surfaced an apparent contradiction about whether Playwright Component Testing is "stable" or "still experimental." Verified directly against Playwright's own release notes and the @playwright/experimental-ct-vue npm package: both are true, about two different things. The old per-framework package is still published and its own README still says "EXPERIMENTAL, does not respect semver." A new, package-free fixtures.mount() model shipped in 1.62.0 — the version this project already runs — as a real feature the docs call "stable." A new adopter reaches for the new model.

Biggest caveat: happy-dom's own docs are silent on ResizeObserver/getBoundingClientRect/scrollTop fidelity. This research read happy-dom's TypeScript source directly: ResizeObserver and getBoundingClientRect are unimplemented stubs (same failure as jsdom), but scrollTop is a genuine settable/gettable property — the one this project's current need actually touches. The stub gap is real and will bite the day a ui/ component needs to assert ResizeObserver behavior — that day, reach for the runner-up.

Requirements frame

Sourced from the project itself — AD-27, AD-6, AD-24 (ARCHITECTURE-SPINE.md), ui/RowWindow.vue, core/view/row-window.js, and deferred-work.md — not from web research, per the select-shape method.

  • AD-27 («The browser matrix and the test envelope are rules, not preferences»): core/, ports/, adapters/ run under Vitest with environment: 'node'; the built artefact runs under Playwright from a real file:// URL. A third envelope must be scoped to ui/** only and must not leak a DOM into a core/** test.
  • AD-6 («Datasets never enter the graph model, and never enter reactive state»): tables live in a Map registry, held via shallowRef in ui/. Not directly at stake for a component-props test, but disqualifying if a candidate's mounting mechanism forced reactivity onto a table handed in as a prop.
  • AD-24 («The Result table is windowed, and the scroll extent is guarded»): fixed-height row windowing, ~50-row window, mandatory spacer clamp, pages past the clamp. The paging controls are the named gap in deferred-work.md: "The paging controls in ui/RowWindow.vue — the buttons, their German labels, their disabled states — are rendered by no test in any envelope; only the page math underneath them is covered."
  • Direct code read, this run: buildWindow(table, page, scrollTop) sets pages: pageCount(total), a pure function of the row count alone. sliceRows() only ever indexes the window actually shown. The gap is reachable with a fake table prop — a props-in/DOM-out test, not a geometry test.

Candidate screen

All four candidates clear the ui/**-only hard gate and can drive component props directly — differentiation happens entirely on the weighted criteria below.

  • @vue/test-utils + happy-dom, as a second Vitest projects entry scoped to ui/**.
  • Vitest Browser Mode (@vitest/browser + a provider), real Chromium/Firefox via the Vitest runner, plus the community helper vitest-browser-vue.
  • Playwright Component Testing, the model shipped inside core @playwright/test 1.62.0 (fixtures.mount(), "stories and galleries") — not the older, separately-versioned @playwright/experimental-ct-vue package.
  • No third envelope — push every interesting state into core/ as pure data, keep templates thin enough that e2e coverage suffices.

Ecosystem health mixed

@vue/test-utils is the Vue core team's own package [5], but its latest release, 2.4.11, is dated 2024-06-04 by GitHub's own releases page — against a conflicting snippet claiming "2 months ago" this run could not reconcile [5][6]. Vitest Browser Mode graduated to stable in Vitest 4.0 (2025-10-22) [10], but its Vue helper vitest-browser-vue has an unresolved organizational home [15]. Playwright CT's new model ships inside @playwright/test core — the package this project already pins for e2e — confirmed as a headline feature of 1.62.0, the version already installed [16][17].

Geometry fidelity verified from source

Read directly from happy-dom's TypeScript source: ResizeObserver.observe()/unobserve()/disconnect() are each a bare // TODO: Not implemented [8]; Element.getBoundingClientRect() unconditionally return new DOMRect() [9] — the same failure documented for jsdom via its own issues [1][2][3][4]. But happy-dom's scrollTop/scrollLeft/scrollHeight/scrollWidth are genuine settable/gettable properties, not stubs [9] — all this project's mechanism needs. Both real-browser candidates get real layout by construction [11][14][16].

Setup / dependency cost

happy-dom + @vue/test-utils is additive to the existing Vitest config [7]. Playwright CT's new model needs no new package at all. Vitest Browser Mode needs a provider package plus, for ergonomic Vue mounting, vitest-browser-vue — a second config surface, and Playwright's own browser binaries if that provider is chosen [11].

npm run verify wall-clock one data point

happy-dom needs no browser launch. Vitest Browser Mode has one concrete, dated data point against it: a GitHub issue reporting that adding 3 Browser Mode tests to a 507-test jsdom suite raised total CI wall-clock from 284.83s to 473.52s — a ~66% increase — closed by Vitest maintainers as "not planned" [12]. Single, CI-specific, not independently corroborated — but for a gate every developer runs before every commit, it outweighs Playwright CT's absence of any equivalent report, scored here on architectural reasoning about already-warm, already-parallel workers.

Prop-driven ergonomics

mount(Component, { props }) and render(Component, { props }) are direct, single-call mounting APIs. Playwright CT's fixtures.mount() requires authoring a "story" rather than calling mount with ad hoc props inline — real but modest extra ceremony.

No third envelope — evaluated, not dismissed

A live alternative, not a null option — it is what closed most of Story 2's gaps already, moving page-composition arithmetic into core/view/row-window.js so a deleted offset fails a Vitest test rather than passing silently. But the remaining gap is proof this discipline has a ceiling: v-if="view.pages > 1", a button's :disabled binding, and German label interpolation are Vue template execution that exists only inside the render function. Pushing them further into core/ would mean rebuilding Vue inside core/, in direct tension with AD-2. The discipline stays the right default for state derivation — it cannot, by itself, close a gap that is about what the template does with state it already has correctly.

Cost & lock-in

All three technology candidates are devDependencies only — none ships in the built single-file artefact. No licensing or hosting cost: @vue/test-utils (MIT), happy-dom (MIT), @playwright/test (Apache-2.0, already accepted for e2e) are all permissive with no runtime key. Migration-away cost is low for all three — each is exercised only inside test files behind a mount/render-shaped call.

Verdict

Pick: @vue/test-utils + happy-dom, as a second Vitest projects entry scoped to ui/**. It clears both hard gates, closes the concrete gap at the lowest cost on every axis this project already cares about, and its one real weakness — no ResizeObserver/getBoundingClientRect fidelity — does not touch the trigger case.

Named runner-up and the switch condition: Playwright Component Testing's built-in model out-scores the pick on ecosystem backing and matches it on fidelity, but loses on wall-clock risk and authoring ceremony. The day a ui/ component's untested branch depends on real ResizeObserver firing or a real computed getBoundingClientRect — the Editor canvas's per-node ResizeObserver mechanism (R4/D4) is the shape to watch — happy-dom's stub cannot assert it and Playwright CT can, at zero new dependency cost.

Strongest argument against the pick: happy-dom's own documentation never states what this research had to determine by reading source code — a project adopting it without that check could believe ResizeObserver/getBoundingClientRect work, and ship a component test that never actually failed under a broken resize handler.

Cheapest reversibility hedge: keep the DOM-emulator choice inside vitest.config.js's per-project environment field, never inside a component or test assertion — a later switch changes one line of config and adds files; it rewrites nothing already-passing.

Implementation note: carry one comment at the DOM-emulator boundary (mirroring vitest.config.js's existing AD-27 comment) stating plainly that ResizeObserver and getBoundingClientRect are not implemented under happy-dom.

Cross-dimension insights

  • The fidelity concern and the cost concern (Executive summary) only look opposed in the abstract. Checked against core/view/row-window.js's actual implementation rather than against the brief's worry in isolation, they turn out not to conflict for this gap — only for gaps this project hasn't hit yet.
  • The round-1 "stable vs. experimental" contradiction for Playwright CT was not actually a contradiction — two research assistants each accurately described one of two coexisting mechanisms. This is exactly what a landing-time verification pass against primary sources is for, rather than accepting or rejecting a whole candidate on a single blog's framing.
  • All three candidates share one structural property this project should lean on: none of them tests the shipped file:// artefact, and none needs to — that job is already Playwright's, from AD-27, and stays there. A third envelope's job is narrower (and cheaper) than the second envelope's.

Contrary evidence

The red-team pass was not run this cycle (red_team = off, validation = normal). The strongest counter-argument surfaced organically — happy-dom's undocumented stub behavior being invisible without reading source — is carried in the Verdict section above rather than duplicated here, since it came from this run's own verification step, not a dedicated skeptic pass.

Recommendations

  1. Add @vue/test-utils + happy-dom as a second Vitest projects entry, environment: 'happy-dom', scoped to ui/**. high on the mechanism [7]; medium on release cadence.
  2. Write RowWindow.vue's paging-branch test as a props-only test — a fake table object with a large rowCount, no real CSV fixture. high confidence.
  3. Document, at the DOM-emulator config boundary, that ResizeObserver and getBoundingClientRect are unimplemented stubs under happy-dom. high confidence.
  4. Do not adopt Vitest Browser Mode or Playwright CT now — hold Playwright CT as the named upgrade path for the first geometry-dependent component. medium confidence.

Open questions

  • Does @vue/test-utils 2.4.11's ~2-year release gap indicate dormancy, or a stable API needing no further releases? Route: npm view @vue/test-utils time --json against the live registry.
  • Real measured npm run verify wall-clock cost, in this project's own repo, for each candidate — settle with a local spike rather than more research.
  • Whether happy-dom's ResizeObserver/getBoundingClientRect stubs are being actively worked on — not distinguished from "permanently unimplemented" in this run.
