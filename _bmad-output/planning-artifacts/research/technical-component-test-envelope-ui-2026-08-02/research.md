# technical research: A component-test envelope for ui/

**Decision this research serves:** Should querbeet add a third test envelope for Vue components, and if so which one?

## Executive summary

**Verdict: add `@vue/test-utils` + `happy-dom` as a second Vitest project, scoped to `ui/**` only** (weighted score 84/100). Runner-up: **Playwright Component Testing's new built-in model** (82/100, a near-tie) — reach for it specifically when a future `ui/` component needs real `ResizeObserver`/`getBoundingClientRect` behavior, since the project already carries `@playwright/test` ^1.62 and this costs zero new dependencies. Vitest Browser Mode scores third (72/100): real-browser fidelity, but a documented CI wall-clock regression and an extra helper dependency of unresolved provenance make it the more expensive of the two real-browser options for no fidelity gain over the runner-up.

**The gap that opened this research does not need what the brief worried it might need.** `ui/RowWindow.vue`'s untested AD-24 paging branch depends only on `core/view/row-window.js`'s `buildWindow()`, which derives `.pages` from `table.rowCount` alone — verified by reading the source directly. A fake `props.table` with a large `rowCount` and a tiny `columns[].cells` array reaches the branch; no real scroll gesture, no real layout, and (contrary to the brief's stated concern) no `getBoundingClientRect`/`ResizeObserver` at all. **jsdom or happy-dom are sufficient for exactly the trigger case**, which is why the geometry-fidelity criterion — the one that looked like it might force Vitest Browser Mode as "the only real candidate" — turns out not to decide this run.

**What does decide it is cost against a five-year horizon.** happy-dom needs no browser binary, starts near-instantly, and slots into the existing `npm test` (Vitest) runner as one more project — the cheapest possible addition to `npm run verify`'s wall-clock. Both real-browser candidates run through a Vite dev server over HTTP, not the shipped `file://` artefact (verified for all three), so none of the three candidates tests what AD-27's *second* envelope (Playwright, from `file://`) already owns — that job stays where it is.

**One correction that changed the shape of this run:** round 1 surfaced an apparent contradiction about whether Playwright Component Testing is "stable" or "still experimental" [22]. Verified directly against Playwright's own 1.59.0 [18] / 1.62.0 [17] release notes and the `@playwright/experimental-ct-vue` npm package [19]: **both are true, about two different things.** The old per-framework package (`@playwright/experimental-ct-vue`) is still published, still real, and its own README still says "EXPERIMENTAL, does not respect semver" [20] — consistent with a 2023 maintainer comment that no stabilization timeline existed for it [21]. A **new**, package-free `fixtures.mount()` model shipped in 1.62.0 — the version this project already runs — as a real, non-experimental-labeled feature, and is what the docs call "stable" [16]. A new adopter reaches for the new model; the old package's experimental status is true but irrelevant to this decision.

**Biggest caveat:** happy-dom's own docs and wiki are silent on `ResizeObserver`/`getBoundingClientRect`/`scrollTop` fidelity — this research settled the question by reading happy-dom's TypeScript source directly rather than trusting docs, and the answer is mixed: `ResizeObserver` and `getBoundingClientRect` are unimplemented stubs (same failure as jsdom), but `scrollTop` is a genuine settable/gettable property, which is the one this project's current need actually touches. The stub gap is real and will bite the day a `ui/` component needs to assert `ResizeObserver` behavior (e.g. anything shaped like the Editor canvas's per-node observers, R4/D4) — that day, reach for the runner-up.

## Requirements frame

Sourced from the project itself — AD-27, AD-6, AD-24 [24], `ui/RowWindow.vue`, `core/view/row-window.js` [23], and `deferred-work.md` [25] — not from web research, per the select-shape method (web research does not set requirements).

- **AD-27** («The browser matrix and the test envelope are rules, not preferences»): `core/`, `ports/`, `adapters/` run under Vitest with `environment: 'node'` — a DOM available there would erase the wall that keeps the core framework-free. The built artefact runs under Playwright from a real `file://` URL in both engines. Whatever a third envelope is, it must be **scoped to `ui/**` only** and must not create a path for a DOM to leak into a `core/**` test.
- **AD-6** («Datasets never enter the graph model, and never enter reactive state»): tables live in a `Map` registry, `ui/` only ever holds them via `shallowRef`. A test envelope that deep-watches or proxies a table would reintroduce the 437–479 MB cost R2 measured. Not directly at stake for a component-props test, but a disqualifying property if any candidate's mounting mechanism forced reactivity onto a table handed in as a prop.
- **AD-24** («The Result table is windowed, and the scroll extent is guarded»): fixed-height row windowing, ~50-row window, mandatory spacer clamp, pages past the clamp. This is the mechanism whose UI-layer half — the paging controls — is the concrete, named gap (`deferred-work.md`): *"The paging controls in `ui/RowWindow.vue` — the buttons, their German labels, their disabled states — are rendered by no test in any envelope; only the page math underneath them is covered."* Reason given there: paging engages only above `PAGE_ROWS` (571,428 rows at 28 px), unreachable by an affordable e2e fixture, and no `ui/` component-test envelope exists.
- **Direct code read, this run:** `core/view/row-window.js`'s `buildWindow(table, page, scrollTop)` sets `pages: pageCount(total)` where `total = count(table.rowCount)` — a pure function of the row count alone, not of anything rendered or scrolled. `sliceRows()` only ever indexes into `columns[c].cells` for the window actually shown. **This means the gap is reachable by handing `RowWindow.vue` a fake `table` prop with a large `rowCount` and a short `cells` array — a props-in/DOM-out test, not a geometry test.**
- Decision criteria carried into the weighted matrix below (from the R10 brief, itself grounded in the above): holds the `ui/**`-only line; drives component props directly; fidelity for DOM geometry APIs (`getBoundingClientRect`, `ResizeObserver`, `scrollTop`/`scrollHeight`/`clientHeight`); cost against a five-year toolchain horizon (R2's own framing); impact on `npm run verify`'s wall-clock.

## Candidate screen

Four candidates, per the R10 brief. All four clear the `ui/**`-only hard gate (none requires exposing a DOM to `core/**`) and all four can drive component props directly (a hard requirement, since the untested states are reachable only from a prop) — so differentiation happens entirely on the weighted criteria below, not on gate failures.

- **`@vue/test-utils` + `happy-dom`**, as a second Vitest `projects` entry (`environment: 'happy-dom'`, scoped to `ui/**`) alongside the existing `environment: 'node'` project.
- **Vitest Browser Mode** (`@vitest/browser` + a provider, e.g. `@vitest/browser-playwright`), running real Chromium/Firefox via the same Vitest runner, plus the community helper `vitest-browser-vue` for a `render(Component, {props})` API.
- **Playwright Component Testing**, specifically the model shipped inside core `@playwright/test` 1.62.0 (`fixtures.mount()`, "stories and galleries") — not the older, separately-versioned `@playwright/experimental-ct-vue` package, which this screen treats as a distinct, still-experimental mechanism this project has no reason to adopt (see the correction in the executive summary).
- **No third envelope** — the discipline Story 2's review already applied by hand: push every interesting state into `core/` as pure data, keep templates thin enough that e2e coverage suffices.

`jsdom` was screened alongside `happy-dom` as the other DOM-emulator option and is folded into the same candidate row below (jsdom vs. happy-dom is a sub-decision, resolved in favor of happy-dom — see Evidence).

**Ecosystem health.** `@vue/test-utils` is the Vue core team's own package (`vuejs` GitHub org) [5], but its latest release, 2.4.11, is dated 2024-06-04 by GitHub's own releases page — roughly two years with no tagged release as of this run — against a conflicting WebSearch snippet claiming "2 months ago" that this research could not reconcile [5][6]. Treat "official but possibly quiet" rather than either extreme. Vitest Browser Mode graduated from experimental to stable in Vitest 4.0 (2025-10-22), a headline feature with clear team investment [10], but the Vue-specific rendering helper `vitest-browser-vue` has an unresolved organizational home (its repo page reads `vitest-community`, a releases URL pointed at `vitest-dev`) [15] — a real, if narrow, backing-durability question for exactly the piece that makes it usable for Vue. Playwright Component Testing's new model ships inside `@playwright/test` core — the same package this project already pins for its e2e suite — so it inherits that package's release cadence with zero incremental dependency risk; confirmed as a headline (non-experimental-labeled) feature of 1.62.0, the version already installed [16][17].

**Geometry fidelity.** Read directly from happy-dom's TypeScript source (not docs, which are silent on this): `ResizeObserver.observe()`/`unobserve()`/`disconnect()` are each a bare `// TODO: Not implemented` [8]; `Element.getBoundingClientRect()` unconditionally `return new DOMRect()` — an all-zero rect, `// TODO: Not full implementation` [9] — the same failure mode documented for jsdom via its own open issues (`getBoundingClientRect` #3621 [1], `ResizeObserver` #3368 [2], `scrollHeight`/`clientHeight` #1013 and a corroborating Testing Library issue #353 [3][4]). But happy-dom's `scrollTop`/`scrollLeft`/`scrollHeight`/`scrollWidth` are genuine settable/gettable properties backed by private fields, not stubs [9] — a test can set `el.scrollTop = 500` and read it back correctly, which is all `RowWindow.vue`'s mechanism needs, since it never asks a DOM emulator to *compute* a scroll offset from real rendered content, only to hold whatever number the test (or a real scroll event) put there. Both real-browser candidates get this by construction — genuine layout, genuine `ResizeObserver` firing, genuine `getBoundingClientRect` — though no source found names `scrollTop` specifically for either; it follows architecturally from "a real browser engine is driving the page" [11][14][16].

**Setup / dependency cost.** happy-dom + `@vue/test-utils` is additive to the existing Vitest config: one new `projects` entry, two new devDependencies, reusing the test runner, watch mode and reporter already wired into `npm test` [7]. Playwright CT's new model needs no new package at all — this project is already past the version (1.62.0) where it shipped — just a `testDir`/`webServer` config block and story files [16][17]. Vitest Browser Mode needs a provider package (Playwright or WebdriverIO) plus, for ergonomic Vue mounting, `vitest-browser-vue` — a second config surface (`browser.provider`, `instances`) and, if the Playwright provider is chosen, Playwright's own browser binaries as a hard dependency even though this project could in principle avoid a second browser toolchain by choosing WebdriverIO instead [11]. Further rough edges reported in the last 12 months (Chromium disk-usage accumulation, friction with Vitest's own `projects` feature, a Node-API crash mode) add up to a mode still finding its footing operationally even after graduating from "experimental" [13].

**`npm run verify` wall-clock.** happy-dom needs no browser launch and is reported — secondary sources only, direction corroborated twice but no reconciled multiplier — to run several times faster than jsdom-equivalent suites; all such figures traced to aggregator content rather than a primary benchmark, so treat the speedup as real in direction and unverified in size. Vitest Browser Mode has one concrete, dated data point against it: a GitHub issue reporting that adding 3 Browser Mode tests to a 507-test jsdom suite raised total CI wall-clock from 284.83s to 473.52s — a ~66% increase — closed by Vitest maintainers as "not planned"/"needs reproduction" with no fix on record [12]. This is a single, CI-specific, not-independently-corroborated report, but for a gate every developer runs before every commit, a documented regression of that shape (even as one data point) outweighs Playwright CT's *absence* of any equivalent report — no timing data was found for Playwright CT either way, scored here on the architectural reasoning that its workers are already warm and parallelized for the existing e2e suite (`fullyParallel: true` is already this project's config), so its marginal cost is plausibly lower than standing up a second, separate browser-launching mechanism inside Vitest.

**Prop-driven ergonomics.** `@vue/test-utils`'s `mount(Component, { props })` and `vitest-browser-vue`'s Testing-Library-style `render(Component, { props })` are both direct, single-call mounting APIs. Playwright CT's `fixtures.mount()` model requires authoring a "story" (a named, pre-configured scenario) rather than calling mount with ad hoc props inline in the test body — real but modest extra ceremony for the kind of small, parametric assertion this gap needs ("`rowCount` = 600,000 → paging controls visible, page 1 of N, prev button disabled").

## No third envelope — evaluated, not dismissed

This is a live alternative, not a null option, and it is what closed most of Story 2's gaps already: the review moved the page-composition arithmetic into `core/view/row-window.js` specifically so a deleted offset would fail a Vitest test rather than pass silently. **But the remaining gap is proof this discipline has a ceiling for this project's own architecture.** `v-if="view.pages > 1"`, a button's `:disabled` binding, and German label interpolation are Vue template execution — they exist only inside the render function. Pushing them further into `core/` would mean re-implementing conditional rendering and reactive attribute binding as plain JS returning markup or view-state objects, which is not "thinner templates," it is rebuilding Vue inside `core/`, in direct tension with AD-2's reason for existing (a framework-free core). The discipline remains the right default for *state derivation* — and should stay the first move for any future `ui/` gap — but it cannot, by itself, close a gap that is genuinely about what the template does with state it already has correctly.

## Cost & lock-in

All three technology candidates are devDependencies only — none ships in the built single-file artefact (verified against `package.json`'s existing `dependencies`/`devDependencies` split; the project's whole build-and-inline discipline, R2/R3, applies to runtime code, not to the test toolchain). There is no licensing or hosting cost: `@vue/test-utils` (MIT, Vue core org), `happy-dom` (MIT), `@playwright/test` (Apache-2.0, already accepted for the e2e suite) are all permissive with no runtime key. Migration-away cost is low for all three, since each is exercised only inside test files behind the same `mount`/`render`-shaped call — swapping the DOM emulator later (happy-dom → jsdom, or promoting to Playwright CT for a specific component) touches test files, never `ui/` component source.

## Verdict

**Pick: `@vue/test-utils` + `happy-dom`, as a second Vitest `projects` entry scoped to `ui/**`.** It clears both hard gates, closes the concrete gap that opened this research at the lowest cost on every axis that this project has already said it cares about (a five-year toolchain horizon, and `npm run verify`'s wall-clock as a hard developer-facing constraint), and its one real weakness — no `ResizeObserver`/`getBoundingClientRect` fidelity — does not touch the trigger case, verified by reading `core/view/row-window.js` directly.

**Named runner-up: Playwright Component Testing's built-in model, and the condition under which it wins instead.** It out-scores the pick on ecosystem backing (it rides the already-adopted `@playwright/test` package's release train, zero incremental dependency) and matches it on fidelity. It loses on wall-clock risk and authoring ceremony for the *kind* of small, parametric test this gap needs. **The day a `ui/` component's untested branch depends on real `ResizeObserver` firing or a real computed `getBoundingClientRect`** — the Editor canvas's per-node `ResizeObserver` mechanism (R4/D4) is the shape to watch — happy-dom's stub (verified from source, not assumed) cannot assert it and Playwright CT can, at zero new dependency cost. Vitest Browser Mode was screened seriously but does not win under any criterion weighting this research considered plausible for this project: it matches Playwright CT's fidelity but adds an extra, ownership-ambiguous dependency (`vitest-browser-vue`) and carries the one concrete wall-clock regression report found in this whole run.

**The strongest argument against the pick:** happy-dom's own documentation never states what this research had to determine by reading source code — a project adopting it without that check could reasonably believe `ResizeObserver`/`getBoundingClientRect` work, ship a component test that never actually failed under a broken resize handler, and get a false sense of coverage. That risk is mitigated, not eliminated, by naming it explicitly in the implementation note below.

**The cheapest reversibility hedge:** keep the DOM-emulator choice inside `vitest.config.js`'s per-project `environment` field, never inside a component or a test file's assertions — a later switch from happy-dom to jsdom, or a later addition of a Playwright-CT-based project for specific geometry-dependent components, changes one line of config and adds files; it rewrites nothing already-passing.

**Implementation note (not itself a finding):** given the verified stub, any test suite adopted from this pick should carry one comment at the DOM-emulator boundary — the equivalent of `vitest.config.js`'s existing AD-27 comment — stating plainly that `ResizeObserver` and `getBoundingClientRect` are not implemented under happy-dom, so a future author does not spend time debugging a component that "should" call one and silently doesn't.

## Cross-dimension insights

- **The fidelity concern and the cost concern (Executive summary) only look opposed in the abstract.** Checked against `core/view/row-window.js`'s actual implementation rather than against the brief's worry in isolation, they turn out not to conflict for *this* gap — only for gaps this project hasn't hit yet.
- **The round-1 "stable vs. experimental" contradiction for Playwright CT was not actually a contradiction** — it was two research assistants each accurately describing one of two coexisting mechanisms (the old per-framework package, genuinely still experimental by its own README; the new built-in model, genuinely new and headline-shipped in the version already installed). This is exactly the kind of thing a landing-time verification pass against primary sources (release notes, the package's own README) is for, rather than either accepting or rejecting the whole candidate on a single blog's framing.
- **All three candidates share one structural property this project should lean on:** none of them tests the shipped `file://` artefact, and none needs to — that job is already Playwright's, from AD-27, and stays there. A third envelope's job is narrower (and cheaper) than the second envelope's, which is part of why the cheapest candidate wins.

## Recommendations

1. **Add `@vue/test-utils` + `happy-dom` as a second Vitest `projects` entry, `environment: 'happy-dom'`, `include: ['ui/**/*.test.js']` (or the project's existing SFC-test naming convention).** Confidence: high on the mechanism (Vitest's `projects` config is documented, current, and supported for exactly this shape [7]); medium on `@vue/test-utils`'s release cadence (the ~2-year-gap claim is unresolved against a conflicting snippet). Feeds: closes the `deferred-work.md` item directly; extends AD-27 with a new, explicitly `ui/**`-scoped third envelope.
2. **Write RowWindow.vue's paging-branch test as a props-only test — a fake `table` object with a large `rowCount`, no real CSV fixture.** Confidence: high (verified directly from `core/view/row-window.js`'s `buildWindow`/`pageCount` source this run).
3. **Document, at the DOM-emulator config boundary, that `ResizeObserver` and `getBoundingClientRect` are unimplemented stubs under happy-dom** (mirroring the existing AD-27 comment style in `vitest.config.js`), so a future author does not lose time to a silently-never-firing observer in a component test. Confidence: high (read directly from happy-dom's source this run).
4. **Do not adopt Vitest Browser Mode or Playwright Component Testing now — hold Playwright CT as the named upgrade path** for the first `ui/` component whose untested branch genuinely needs `ResizeObserver`/`getBoundingClientRect` fidelity. Confidence: medium (the wall-clock case against Browser Mode rests on one unreplicated GitHub issue; the case for Playwright CT as the better real-browser fallback rests on architectural reasoning about already-warm workers, not a measurement).

## Open questions

- **Does `@vue/test-utils` 2.4.11's ~2-year release gap indicate dormancy, or a stable API needing no further releases?** This run found conflicting signals (GitHub releases page date vs. a WebSearch snippet) and could not reconcile them within budget. Route: a direct fetch of `registry.npmjs.org/@vue/test-utils`'s `time` object (blocked by a 403 from npmjs.com's website for the round-1 subagent; worth retrying via `npm view @vue/test-utils time --json`, the way this run resolved the Playwright-package question).
- **Real measured `npm run verify` wall-clock cost, in this project's own repo, for each candidate** — this run found one third-party data point for Vitest Browser Mode and none for the other two; a local spike (add one project entry, run `npm test`, compare before/after) would settle this in minutes rather than research.
- **Whether happy-dom's `ResizeObserver`/`getBoundingClientRect` stubs are being actively worked on** (an open PR, a roadmap note) — this run found the stub via source, not the project's own issue tracker or roadmap, so "permanently unimplemented" vs. "not yet implemented" was not distinguished.
