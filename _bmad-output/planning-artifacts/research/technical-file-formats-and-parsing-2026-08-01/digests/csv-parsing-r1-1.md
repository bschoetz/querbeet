### Q2 — Delimiter auto-detection

7. Documented behaviour: leaving `delimiter` blank "auto-detect[s] from a list of most common delimiters, or any values passed in through `delimitersToGuess`"; the default candidate set is **`[',', '\t', '|', ';', Papa.RECORD_SEP, Papa.UNIT_SEP]`** — semicolon **is** in the default set, in fourth position. `{claim: delimitersToGuess default list and auto-detect wording, source: https://www.papaparse.com/docs, publisher: Papa Parse (official docs), pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

8. Source-level algorithm: `guessDelimiter` parses a **preview of 10 rows** per candidate, computes `delta` (sum of absolute differences in field counts between consecutive rows) and `avgFieldCount`, **requires `avgFieldCount > 1.99`**, prefers the lowest delta and breaks ties by highest avgFieldCount; `Papa.DefaultDelimiter = ','` is the fallback. `{claim: guessDelimiter uses preview:10, delta/avgFieldCount scoring, avgFieldCount>1.99 threshold, DefaultDelimiter ',', source: https://raw.githubusercontent.com/mholt/PapaParse/master/papaparse.js, publisher: PapaParse repo (primary source), pub_date: master @ 2026-07-03, accessed: 2026-08-01, confidence: high, class: pattern}`

9. **Failure mode implied by the `avgFieldCount > 1.99` gate** (derived from the retrieved source, not from a bug report): a two-column semicolon file gives avgFieldCount = 2.0 and passes only just; a **single-column** file, or a file whose first 10 rows are a preamble/title block with no delimiter at all, fails the gate for every candidate and silently falls back to comma. Likewise, because only the first 10 rows are sampled, a **preamble before the header row** is exactly the input the sampler sees. `{claim: derived from the guessDelimiter code above, source: same, publisher: PapaParse repo, pub_date: 2026-07-03, accessed: 2026-08-01, confidence: medium, class: pattern}`

10. Delimiter guessing is **actively being changed right now**: commit `apoorva-01, 2026-07-03, "fix guess delimiter by row consistency before field count (#1128)"` landed on master **after** 5.5.4 shipped (2026-06-19), so the released version does **not** contain it. `{claim: commit date/message vs release date, source: https://api.github.com/repos/mholt/PapaParse/commits?per_page=50 + releases.atom, publisher: GitHub API, pub_date: 2026-07-03, accessed: 2026-08-01, confidence: high, class: ecosystem}`

### Q3 — Header handling

11. PapaParse **does not detect which row is the header**; `header: true` only means "the first row of parsed data will be interpreted as field names". `{claim: header option wording, source: https://www.papaparse.com/docs, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

12. Confirmed as an acknowledged absence, not an oversight in my reading: issue **#1121 "[Feature] Add automatic header detection", opened 2026-05-10, still open**. `{claim: open feature request for automatic header detection, source: https://github.com/mholt/PapaParse/issues?q=is%3Aissue+is%3Aopen+sort%3Aupdated-desc, publisher: GitHub, pub_date: 2026-05-10, accessed: 2026-08-01, confidence: high, class: ecosystem}`

13. Two **documented** workarounds for junk/title rows before the real header: `skipFirstNLines` ("To skip first N number of lines when converting a CSV file to JSON") and `beforeFirstChunk` ("A function to execute before parsing the first chunk … it may return a modified chunk to parse. This is useful for stripping header lines (as long as the header fits in a single chunk)"). Both require **you** to know how many rows to skip — neither infers it. `{claim: verbatim docs for skipFirstNLines and beforeFirstChunk, source: https://www.papaparse.com/docs#config-details, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

14. Note the ordering hazard: `skipFirstNLines` removes lines *before* parsing, but delimiter guessing samples the first 10 rows of what it is given — so skipping the preamble is also the fix for finding 9's delimiter failure. (Derived from findings 8/9/13; not separately evidenced.)

### Q4 — Type inference danger (load-bearing)

15. `dynamicTyping` is documented only as "If true, numeric and boolean data will be converted to their type instead of remaining strings", with the sole caveat that "Numerical values greater than `2^53` or less than `-2^53` will not be converted to numbers to preserve precision." **No locale awareness is documented.** `{claim: verbatim dynamicTyping docs, source: https://www.papaparse.com/docs, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

16. The actual conversion test in source is the regex **`var FLOAT = /^\s*-?(\d+\.?|\.\d+|\d+\.\d+)([eE][-+]?\d+)?\s*$/;`** with `MAX_FLOAT = Math.pow(2, 53)`; `parseDynamic` converts `'true'/'TRUE'` → true, `'false'/'FALSE'` → false, FLOAT matches → `parseFloat`, ISO_DATE matches → `Date`, empty string → `null`. `{claim: verbatim FLOAT/ISO_DATE/MAX_FLOAT and parseDynamic behaviour, source: https://raw.githubusercontent.com/mholt/PapaParse/master/papaparse.js, publisher: PapaParse repo (primary source), pub_date: master @ 2026-07-03, accessed: 2026-08-01, confidence: high, class: pattern}`

17. **Consequences for German-formatted numbers, read directly off that regex** (derivation, flagged as such): `"1.234"` matches the `\d+\.\d+` branch → `parseFloat("1.234")` → the number **1.234**, i.e. a German thousands separator is silently reinterpreted as a decimal point and the value is wrong by 1000×, with no error raised. `"1.234,56"` does **not** match (the comma fails the anchored regex) → it is left as the **string** `"1.234,56"`, not NaN. `"1.234.567"` also fails to match → string. So the corruption is **not uniform**: within one column, four-digit values silently become wrong numbers while values with a decimal comma stay strings, producing a mixed-type column. `{claim: derived from the retrieved FLOAT regex and parseDynamic logic, source: https://raw.githubusercontent.com/mholt/PapaParse/master/papaparse.js, publisher: PapaParse repo, pub_date: 2026-07-03, accessed: 2026-08-01, confidence: medium (derivation from primary source, not an executed test), class: pattern}`

18. Same regex means `"0123"` matches `\d+\.?` → `parseFloat` → **123**, dropping leading zeros (relevant for German cost centres, account and customer numbers). Derived, same source and confidence as 17.

19. This is a **known and explicitly deferred** limitation, not an unnoticed bug: issue **#143 "Numeric value with comma (European-formatted numbers)"**, labelled `deferred` / `suggestion`, **closed 2014-12-28** with no locale support added — and the 2026 source above confirms it still has none. `{claim: issue #143 title, labels deferred/suggestion, closed 2014-12-28, source: https://github.com/mholt/PapaParse/issues?q=is%3Aissue+dynamicTyping+number+locale+decimal, publisher: GitHub, pub_date: 2014-12-28, accessed: 2026-08-01, confidence: high, class: ecosystem}` — **age flag: this issue is 11.5 years old**, cited only as evidence that the request was made and declined; the current-version evidence is finding 16.

20. Practical implication: `dynamicTyping` must be **off** (or per-column, which the docs say "accepts objects or functions for column-specific control") for German business exports, with numeric conversion done by your own de-DE parser. `{claim: dynamicTyping accepts per-column object/function, source: https://www.papaparse.com/docs, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

### Q5 — Scale and streaming

21. Streaming is documented via `step` (per row) and `chunk` ("after every _chunk_ of the file is loaded and parsed"), both receiving a parser handle supporting `parser.abort()` and — **only outside workers** — `parser.pause()` / `parser.resume()`. The docs state large files require streaming "to avoid crashing the browser". `{claim: verbatim step/chunk/pause/resume and large-file caveat, source: https://www.papaparse.com/docs, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

22. `worker: true` is documented as "Using a worker will keep your page reactive, but may be slightly slower" — i.e. the maintainers themselves position workers as a **responsiveness** feature with a throughput cost, not a speed feature. `{claim: verbatim worker docs, source: https://www.papaparse.com/docs, publisher: Papa Parse official docs, pub_date: n/a, accessed: 2026-08-01, confidence: high, class: pattern}`

23. The only **measured** throughput numbers I retrieved: on a 17 MB / **100K row** / 12-column customer dataset, PapaParse reached **1.13M rows/s (186 MiB/s)** parsing to string arrays and **454K rows/s (75 MiB/s)** with type conversion; on quote-heavy `uszips.csv` (6 MB, 34K rows) it reached **176K rows/s (31.4 MiB/s)**. Test conditions: **Ryzen 7 ThinkPad, Linux 6.14.7, NodeJS v24.1.0** — **Node, not a browser, and no worker**. Extrapolated naively, 100k rows ≈ 0.09 s untyped / 0.22 s typed, i.e. the target scale is not near any limit. `{claim: uDSV benchmark table numbers and environment, source: https://github.com/leeoniya/uDSV, publisher: leeoniya (uDSV author), pub_date: not stated (latest npm publish 2025-07-06), accessed: 2026-08-01, confidence: medium (author of the winning library ran it; Node not browser), class: performance}`

24. Second, weaker performance source: LeanyLabs' JS CSV parser benchmark ranks **PapaParse fastest** of the parsers it tested for both non-quoted and quoted input across files from 1 MB (10 cols × 10k rows) to 140 MB (100 cols × 100k rows), noting it "even outpaced String.split" and slowed ~2× on quoted input. **No publication date, no hardware, no Node version, and numeric results only in charts** — this fails the source-quality bar for a number a decision rests on. `{claim: PapaParse ranked fastest, methodology as described, source: https://leanylabs.com/blog/js-csv-parsers-benchmarks/, publisher: LeanyLabs, pub_date: not stated, accessed: 2026-08-01, confidence: low, class: performance}`

32. Head-to-head numbers, same run as finding 23 (17 MB, 100K rows, 12 cols, Node v24.1.0): strings — csv-simple-parser 2.21M rows/s, uDSV 2M, **PapaParse 1.13M**, d3-dsv 939K; typed — uDSV 967K, csv42 712K, **PapaParse 454K**; quote-heavy 6 MB/34K rows — uDSV 537K vs **PapaParse 176K**. So PapaParse is ~2× slower than the current speed leaders and degrades ~3× on quote-heavy input. `{source: https://github.com/leeoniya/uDSV, publisher: leeoniya (author of the winning library — advocacy risk), pub_date: not stated, accessed: 2026-08-01, confidence: medium, class: performance}`

33. **Read for this decision:** at 100k rows the absolute times implied by 32 are all well under one second in Node, so the ~2× speed gap is not decision-relevant; what *is* decision-relevant is maintenance and API surface. PapaParse has a 2026 release, MIT, worker + chunk streaming, `skipFirstNLines`/`beforeFirstChunk` for preambles, and semicolon in its default guess set; d3-dsv has been unpublished for 5 years and does no delimiter detection or streaming; uDSV and web-csv-toolbox are pre-1.0 with 8-13 month release gaps; csv42's licence is unstated in its manifest. (Synthesis of findings 6, 7, 13, 21-22, 29-32.)

## Leads worth chasing

- **Commit #1128 "fix guess delimiter by row consistency before field count"** (2026-07-03) is on master but unreleased. Worth reading the issue/PR: it implies the *released* 5.5.4 guesser mis-ranks candidates in exactly the "which of two plausible delimiters wins" case that semicolon-vs-comma German files present.
- **Issue #1132** (streaming defects, 2026-07-27) claims **chunk-boundary UTF-8 corruption** — if real, that hits umlauts specifically and only in streaming/chunk mode. I read only the title; the thread body should be read before committing to `chunk`/`step` for large files.
- **`csv-simple-parser`** surfaced as the fastest parser in uDSV's own benchmark and was not on the brief's alternatives list — unknown licence, size, maintenance.
- The `encoding` option is documented as passing through to the **FileReader API**, which means German exports in **Windows-1252 / ISO-8859-1** (very common for German ERP/DATEV output) depend on FileReader's encoding label support rather than on PapaParse. Encoding detection is not PapaParse's job and is an open sub-question for D1.
- Nobody in the retrieved material has published **browser-side** (as opposed to Node) parse timings or **memory** figures. That is an open measurement gap that a 30-minute local harness would close better than more searching.

## Contradictions

- **PapaParse's speed rank.** LeanyLabs ranks PapaParse **fastest of all tested parsers**; uDSV's benchmark places it **mid-pack, ~2× behind uDSV and csv-simple-parser**. These are reconcilable rather than contradictory: LeanyLabs' candidate set predates uDSV and csv-simple-parser entirely, and it publishes no date, no hardware and no numbers. **uDSV's is the stronger source** on methodology transparency (named dataset, row/column counts, hardware, Node version, throughput in both rows/s and MiB/s) despite the obvious advocacy risk of being run by the winner's author; LeanyLabs is undated with results only in charts. Neither is a browser measurement, so neither should carry a browser-scale recommendation alone.
- **PapaParse's latest version.** The rendered GitHub releases HTML page returned "5.4.0, Mar 2" as latest with year-less dates; the releases **atom feed** and the **npm registry** both return **5.5.4 / 2026-06-19**. The atom+npm pair wins on agreement and on being machine-readable; the HTML page reading was a scraping artefact (year-less relative dates, partial pagination). Flagging it because the same trap will catch anyone re-checking this.
