## Findings

### Q1 — What current Excel writes

1. Microsoft's own file-format documentation (applies-to: Excel for Microsoft 365, Excel 2024, 2021, 2019, 2016) describes "CSV (comma delimited)" only as "Saves a workbook as a comma-delimited text file for use on another Windows operating system" and **says nothing at all about character encoding or byte order marks** for any CSV variant. `{claim: Microsoft's canonical file-format page documents CSV/CSV(Macintosh)/CSV(MS-DOS) by target OS and never states a code page or BOM, source: https://support.microsoft.com/en-us/office/file-formats-that-are-supported-in-excel-0943ff2c-6014-4e8d-aaea-b83d51d46247, publisher: Microsoft, pub_date: undated (applies-to Excel 2024/M365), accessed: 2026-08-01, confidence: high, class: spec}`
2. The differentiation of "CSV (comma delimited)" / "CSV (Macintosh)" / "CSV (MS-DOS)" **by target operating system** is itself the strongest primary-source hint that the plain variant writes the Windows ANSI code page (1252 in German locales) and the MS-DOS variant the OEM code page — but Microsoft never says so, so this is inference, not documentation. `{claim: Microsoft distinguishes three non-UTF-8 CSV variants purely by target OS, implying OS-default code pages, source: same as (1), publisher: Microsoft, accessed: 2026-08-01, confidence: medium, class: spec}`
3. Secondary but consistent accounts state plainly that "CSV (comma delimited)" produces ANSI code page 1252 in Western/German locales, and that reading such a file as UTF-8 turns `ä ö ü` into mojibake (`Ã¤`). This is folklore-grade in isolation but matches (2). `{claim: Excel's plain CSV export produces Windows-1252/ANSI in Western locales, source: search-snippet layer incl. https://neatcsv.com/blog/csv-encoding-explained and https://learn.microsoft.com/en-us/answers/questions/5081567/, publisher: mixed/Microsoft Q&A, pub_date: 2026 and undated, accessed: 2026-08-01, confidence: medium, class: pattern}`
4. Multiple independent secondary accounts agree that Excel's "CSV UTF-8 (comma delimited)" export **does** write the UTF-8 BOM `EF BB BF`, and that Excel-for-macOS cannot reliably read UTF-8 CSV without it — i.e. the BOM is deliberate, not accidental. `{claim: Excel's "CSV UTF-8" option writes a leading EF BB BF BOM, source: https://www.johndcook.com/blog/2019/09/07/excel-r-bom/ + https://www.oliverjobson.co.uk/marketing/excel-macos-utf8-csv-bom-fix/, publisher: John D. Cook / Oliver Jobson, pub_date: 2019-09-07 / undated, accessed: 2026-08-01, confidence: medium-high (two independent publishers, one with hex evidence; 2019 source is 7 years old), class: pattern}`
5. Microsoft Q&A threads from users show the "CSV UTF-8" path is still not clean in practice (e.g. "Office 365/Excel generates incorrect CSV UTF-8 format files", "Mac Excel: CSV UTF-8 trying to save as UTF-16 Unicode Text") — a signal that a browser tool must not assume "UTF-8 label ⇒ UTF-8 bytes". `{claim: current Microsoft Q&A threads report Excel's CSV UTF-8 export misbehaving incl. writing UTF-16 on macOS, source: https://learn.microsoft.com/en-us/answers/questions/4912580/ and https://learn.microsoft.com/en-us/answers/questions/5004751/, publisher: Microsoft Q&A (user-generated), accessed: 2026-08-01, confidence: low-medium, class: failure}`

### Q2 — BOM detection

6. The Encoding Standard defines a normative **BOM sniff** algorithm over exactly three marks: `EF BB BF` (UTF-8), `FE FF` (UTF-16BE), `FF FE` (UTF-16LE); no other BOMs exist in the standard's model. `{claim: the spec's BOM sniff recognises exactly UTF-8, UTF-16BE and UTF-16LE marks, source: https://encoding.spec.whatwg.org/, publisher: WHATWG, pub_date: Living Standard last updated 2026-05-21, accessed: 2026-08-01, confidence: high, class: spec}`
7. The spec's decode algorithm gives the BOM **priority over any declared label**, with the stated rationale that "a byte order mark has priority over a label as it has been found to be more accurate in deployed content" — i.e. the standard itself endorses BOM sniffing as the most reliable available signal. `{claim: WHATWG decode gives BOM priority over label, on empirical grounds, source: https://encoding.spec.whatwg.org/, publisher: WHATWG, pub_date: 2026-05-21, accessed: 2026-08-01, confidence: high, class: spec}`
8. No source retrieved gives a measured **fraction** of real-world CSV files carrying a BOM. Unquantified.

### Q3 — The built-in browser route (strongest findings of this round)

9. `windows-1252` is a required encoding in the Encoding Standard, and the spec closes the set: **"User agents must not support any other encodings or labels."** So `new TextDecoder('windows-1252')` is guaranteed in every conforming browser — no library needed to *decode*. `{claim: windows-1252 is a mandatory, closed-set encoding for conforming user agents, source: https://encoding.spec.whatwg.org/, publisher: WHATWG, pub_date: 2026-05-21, accessed: 2026-08-01, confidence: high, class: spec}`
10. **Decisive for this decision:** `iso-8859-1`, `latin1`, `l1`, `cp819`, `csisolatin1`, `us-ascii` and `ascii` are all *labels for windows-1252* in the standard — there is no separate ISO-8859-1 decoder in a browser. The full label list is: `ansi_x3.4-1968, ascii, cp1252, cp819, csisolatin1, ibm819, iso-8859-1, iso-ir-100, iso8859-1, iso88591, iso_8859-1, iso_8859-1:1987, l1, latin1, us-ascii, windows-1252, x-cp1252`. `{claim: iso-8859-1/latin1/us-ascii are labels that map to the windows-1252 decoder, source: https://encoding.spec.whatwg.org/, publisher: WHATWG, pub_date: 2026-05-21, accessed: 2026-08-01, confidence: high, class: spec}`
11. Consequence of (10): the "Windows-1252 vs ISO-8859-1" discrimination problem **does not exist in the browser** — both labels select one decoder, so any detector effort spent separating them is wasted. `{claim: the 1252-vs-8859-1 distinction is unreachable and irrelevant via TextDecoder, source: derived from (10), confidence: high, class: spec}`
12. `TextEncoder` is UTF-8-only by spec: "A TextEncoder object offers no label argument as it only supports UTF-8." Encoding *to* windows-1252 in the browser therefore requires a library; decoding *from* it does not. `{claim: TextEncoder cannot encode to non-UTF-8, source: https://encoding.spec.whatwg.org/, publisher: WHATWG, pub_date: 2026-05-21, accessed: 2026-08-01, confidence: high, class: spec}`
13. `TextDecoder`'s `fatal: true` option is specified/documented to throw `TypeError` on malformed input (default `false` substitutes U+FFFD), which is the mechanism behind the "try strict UTF-8, catch, fall back to windows-1252" pattern; the pattern is widely described but I did not retrieve a first-party MDN/spec passage explicitly *recommending* it as a detection technique. `{claim: fatal:true throws TypeError on invalid sequences, enabling a strict-UTF-8 validity test, source: https://developer.mozilla.org/en-US/docs/Web/API/TextDecoder/TextDecoder (via search snippet, page not fetched), publisher: MDN, accessed: 2026-08-01, confidence: medium, class: spec}`

### Q5 — Accuracy reality

23. The chardet lineage has a long-standing, maintainer-visible failure on exactly the discrimination in question: Python-chardet issue #84 "ISO-8859-1 being detected as Windows-1252" and issue #185 "1 sentence utf-8 detected as Windows-1252". The second is the dangerous direction — valid UTF-8 misclassified as a single-byte encoding on short input. `{claim: chardet demonstrably misdetects short UTF-8 as Windows-1252 and confuses ISO-8859-1 with Windows-1252, source: https://github.com/chardet/chardet/issues/185 and https://github.com/chardet/chardet/issues/84, publisher: chardet issue tracker, accessed: 2026-08-01, confidence: medium (issues surfaced via search, not fetched), class: failure}`
24. The failure is structural, not a bug: ISO-8859-1 and Windows-1252 differ only in the 32 code points 0x80–0x9F, so statistical separation is near-impossible on text that never uses that range — which German business data typically does not (ä ö ü ß are all ≥ 0xC4; only `€` at 0x80 lives in the divergent range). `{claim: the two encodings differ only in 0x80–0x9F, source: search-snippet layer over encoding-comparison pages + WHATWG label mapping in (10), accessed: 2026-08-01, confidence: medium-high, class: spec}`
25. **No measured accuracy percentage for any of these libraries on short Western-European text was found.** Every retrieved statement is qualitative ("heuristics, not always accurate"; "don't blindly trust automatic detection"). Treat any accuracy claim in a recommendation as unevidenced.
26. Counterweight that makes heuristics largely unnecessary here: UTF-8 is self-validating — multi-byte sequences have a rigid structure, so arbitrary Windows-1252 German text (e.g. `ä` = 0xE4 followed by an ASCII letter) is overwhelmingly *invalid* UTF-8, which is what makes the `fatal: true` probe work. I retrieved no source quantifying the false-accept rate, so the magnitude is asserted-not-measured. `{claim: strict UTF-8 validation is the discriminating signal, confidence: medium, class: pattern — mechanism follows from the spec's UTF-8 decoder, false-accept rate unmeasured}`

## Leads worth chasing

- **jschardet 4.0.0-rc.1 landed 2026-07-27** — five days before this run. Worth checking what the major version changes (ESM? browser build? licence?) before writing jschardet off.
- The WHATWG label collapse (finding 10) reframes the whole dimension: in-browser there is no ISO-8859-1, so the only real question is "UTF-8 or not", which is a *validation* question, not a *classification* question. Round 2 should test whether the `fatal:true` probe alone suffices.
- Excel-for-macOS reportedly writing UTF-16 under a "CSV UTF-8" label — if real, the UTF-16LE/BE BOM branch is not optional.
- `€` at 0x80 is the one German-business character that sits in the exact byte range where Windows-1252 and ISO-8859-1 diverge; it is also the character most likely to appear in accounting exports. Worth an explicit test case.
- Papa Parse's own encoding handling was never examined; it is the most likely incumbent in a browser CSV tool.

## Contradictions

- **Microsoft's silence vs. universal community claim (Q1).** Microsoft's own documentation states no code page for plain CSV; a large secondary consensus says Windows-1252/ANSI. The secondary side is stronger here on weight of consistent independent testimony plus the structural evidence of Microsoft shipping three OS-targeted CSV variants — but the claim remains *undocumented by the vendor*, which is itself a finding: do not build a design that depends on Microsoft having promised anything.
- **"Detectors work" vs "detectors fail on this exact pair."** npm download volume (31.6M/wk for chardet) implies the ecosystem trusts these libraries; the chardet issue tracker shows the specific discrimination failing. The issue tracker wins — download counts measure convenience, not correctness, and the failures are on precisely the short-Western-European-text case in scope.
