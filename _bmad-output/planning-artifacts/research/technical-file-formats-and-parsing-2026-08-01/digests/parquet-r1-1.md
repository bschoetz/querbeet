# Digest: D5 Parquet in the browser — round 1

## Gate verdict

**Yes — browser-side Parquet export is viable, and it is not close.** `hyparquet-writer` 0.16.3 (published 2026-07-31, MIT) is pure JavaScript with exactly one dependency (`hyparquet`, same authors), and bundles to **57,703 bytes minified / 17,239 bytes gzipped** as a self-contained IIFE that can be pasted inline into a single HTML file — measured by me from the published npm artefact, not claimed. Snappy compression is built in (pure JS, no extra dependency); GZIP works by passing `fflate`'s `gzipSync` (+3,569 bytes gzipped). I wrote 100,000 rows × 5 columns from the published package and the resulting files were read correctly by **pyarrow 25.0.0, DuckDB 1.5.5 and Polars 1.43.2** — SNAPPY, UNCOMPRESSED and GZIP variants, with types, timestamps and nulls preserved. Write time was 159–351 ms for 100k rows (Node 24 on this machine; browser not directly measured — flagged). `parquet-wasm` is the thing the gate would have killed: its WebAssembly payload is **6,494,208 bytes raw / 1,813,165 bytes gzipped**, rising to **8,658,944 bytes of base64 (2,680,916 gzipped)** if inlined into the HTML — an order of magnitude worse than the JS route for the same job. DuckDB-WASM (36–41 MB `.wasm`) is out by two orders of magnitude. Parquet stays in scope; the recommendation is hyparquet-writer with SNAPPY as default and UNCOMPRESSED as fallback.

## Findings

### Q1 — hyparquet and hyparquet-writer

1. `hyparquet-writer` latest is 0.16.3, published 2026-07-31T22:36:22Z, licence MIT, single runtime dependency `hyparquet@1.27.1` (exact pin), 208,921 bytes unpacked over 76 files. {registry.npmjs.org/hyparquet-writer, npm registry, 2026-07-31, accessed 2026-08-01, confidence: high, class: version}
2. `hyparquet` latest is 1.27.1, published 2026-07-30T18:12:28Z, licence MIT, **zero dependencies**, 262,727 bytes unpacked. {registry.npmjs.org/hyparquet, npm registry, 2026-07-30, accessed 2026-08-01, confidence: high, class: version}
3. MIT licence is corroborated independently by the GitHub repository metadata (`spdx_id: MIT`) for both `hyparam/hyparquet` and `hyparam/hyparquet-writer`, and a LICENSE file ships in both npm tarballs. {api.github.com/repos/hyparam/hyparquet-writer, GitHub, accessed 2026-08-01, confidence: high, class: licence}
4. Maintenance is sustained, not a snapshot: hyparquet has **133 published versions since 2024-01-04**, with releases in every recent month (1.25.7 2026-05-09, 1.26.0 2026-05-23, 1.26.1 2026-06-19, 1.26.2 2026-07-01, 1.27.0/1.27.1 2026-07-30); the writer has **53 versions since 2025-03-26**, including 0.15.7 2026-06-19, 0.16.0/0.16.1 2026-06-20, 0.16.2/0.16.3 2026-07-31. {registry.npmjs.org time field, npm registry, accessed 2026-08-01, confidence: high, class: ecosystem}
5. Repositories are active and unarchived: `hyparam/hyparquet` last push 2026-07-30, 842 stars, 31 open issues; `hyparam/hyparquet-writer` last push 2026-07-31, 59 stars, 6 open issues. {api.github.com/repos/hyparam/*, GitHub, accessed 2026-08-01, confidence: high, class: ecosystem}
6. **No UMD/IIFE build is published** — both packages ship ESM source only (`main: src/index.js`, `exports` map, no `unpkg`/`jsdelivr`/`browser` field, no `dist/`), so a plain `<script>` tag will not work without either `<script type="module">` + CDN imports or a one-time bundle step. {data.jsdelivr.com/v1/packages/npm/hyparquet-writer@0.16.3 file listing (25 `src/*.js` files, no dist), jsDelivr, accessed 2026-08-01, confidence: high, class: version}
7. That bundle step is trivial and the result is small: `esbuild --bundle --minify --format=iife` over the published packages gives **writer-only 57,703 B min / 17,239 B gzip**, reader-only 58,921 / 18,426, and reader+writer together **111,525 / 33,439**. {measured locally from npm artefacts hyparquet-writer@0.16.3 + hyparquet@1.27.1 with esbuild, own measurement, 2026-08-01, confidence: high, class: performance}
8. The writer really writes Parquet — `parquetWrite`, `parquetWriteBuffer`, `parquetWriteRows`, `ParquetWriter` streaming class, plus schema inference; the repo carries 35 test files including `write.roundtrip`, `write.struct`, `write.variant`, `write.pageindex`, `write.statistics`, `write.bloom`. {api.github.com/repos/hyparam/hyparquet-writer/contents/test, GitHub, accessed 2026-08-01, confidence: high, class: pattern}
9. Codecs: **SNAPPY is the default and is implemented in-package** (`src/snappy.js`, 6,107 B, included in the 17 KB gzip figure); `UNCOMPRESSED` is available via `codec: 'UNCOMPRESSED'`; every other codec must be supplied by the caller as a **synchronous** function in the `compressors` map (`compressors[codec]?.(pageBytes) ?? pageBytes`). {hyparquet-writer@0.16.3 `src/parquet-writer.js`, `src/datapage.js`, `src/write.js`, published source, accessed 2026-08-01, confidence: high, class: pattern}
10. GZIP output works today with `fflate`'s `gzipSync` — I wrote a `codec: 'GZIP'` file this way and pyarrow reports `compression = GZIP`; the extra payload is **7,035 B min / 3,569 B gzipped** for a gzipSync-only bundle. {own measurement with fflate 0.8.3 + hyparquet-writer 0.16.3, 2026-08-01, confidence: high, class: performance}
11. Because compressors must be synchronous, the browser-native `CompressionStream('gzip')` (async) cannot be dropped in directly — a sync JS gzip such as fflate is required. {inferred from published source signature `compressors[codec]?.(bytes)` returning bytes, hyparquet-writer@0.16.3, accessed 2026-08-01, confidence: medium, class: pattern}
12. ZSTD **write** has no evidenced pure-JS path: the companion `hyparquet-compressors` (1.1.1, last published 2025-03-20 — 16 months old, flagged) depends on `fzstd` and `hysnappy` and is documented as a *read*-side package; Apache's own status page lists ZSTD for hyparquet as read-only. {registry.npmjs.org/hyparquet-compressors + parquet.apache.org implementation status, npm/Apache, 2025-03-20 / page modified 2026-07-07, accessed 2026-08-01, confidence: medium, class: pattern}
13. The optional `hysnappy` WASM Snappy compressor (1.1.1, 2026-02-22, MIT, 19,075 B unpacked) exists for higher throughput but is **not needed** — the pure-JS snappy is bundled by default. {registry.npmjs.org/hysnappy + hyparquet-writer README, npm/GitHub, 2026-02-22, accessed 2026-08-01, confidence: high, class: version}

### Q2 — parquet-wasm

14. `parquet-wasm` latest is 0.7.2, published 2026-06-29T15:40:47Z, licence `MIT OR Apache-2.0`, 19,954,845 bytes unpacked across three build variants. {registry.npmjs.org/parquet-wasm, npm registry, 2026-06-29, accessed 2026-08-01, confidence: high, class: version}
15. **The load-bearing number: the WebAssembly payload is 6,494,208 bytes raw (esm variant) and 1,813,165 bytes at gzip -9**; jsDelivr serves it at 1,808,240 bytes over the wire. Plus 100,770 B / 17,480 B gzip of JS glue. {jsDelivr file listing + direct download and local gzip of cdn.jsdelivr.net/npm/parquet-wasm@0.7.2/esm/parquet_wasm_bg.wasm, jsDelivr/own measurement, accessed 2026-08-01, confidence: high, class: performance}
16. Inlining it into one HTML file costs **8,658,944 bytes of base64 text (2,680,916 bytes gzipped)** — technically possible because the ESM build exposes `initSync(ArrayBuffer)` alongside the async `wasmInit()`, but a ~8.7 MB HTML file. {own base64+gzip measurement of the published .wasm; init API per parquet-wasm README, own measurement/GitHub, accessed 2026-08-01, confidence: high, class: performance}
17. Without `initSync`, the default path **fetches `parquet_wasm_bg.wasm` from the module's location at runtime**, which breaks a single-file build outright. {README, github.com/kylebarron/parquet-wasm, accessed 2026-08-01, confidence: high, class: pattern}
18. The README's own size claims are "1.2 MB brotli" for the full build and "456 KB brotli" for a minimal read-only build — the small figure requires compiling with `wasm-pack --no-default-features --features reader`, i.e. a Rust toolchain, and it excludes writing and compression, so it is not a CDN-loadable option. {README, github.com/kylebarron/parquet-wasm, accessed 2026-08-01, confidence: medium, class: performance}
19. parquet-wasm is maintained (repo pushed 2026-07-27, 658 stars, 42 open issues, Apache-2.0/MIT dual) and supports ZSTD, Snappy, Gzip, Brotli and LZ4_RAW on write — it is a good library that simply cannot meet the single-file constraint. {api.github.com/repos/kylebarron/parquet-wasm + README, GitHub, accessed 2026-08-01, confidence: high, class: ecosystem}

### Q4 — correctness and interoperability

25. **Files written by hyparquet-writer 0.16.3 open cleanly in all three reference tools.** 100,000 rows × 5 columns (INT32, DOUBLE, STRING, TIMESTAMP, BOOLEAN with 33,334 nulls): pyarrow 25.0.0 read the SNAPPY file with the exact schema `id: int32, value: double, name: string, ts: timestamp[ms, tz=UTC], flag: bool` and null count 33,334; DuckDB 1.5.5 aggregated it correctly (`count=100000, min(id)=0, max(id)=99999, count(flag)=66666`); Polars 1.43.2 read shape (100000, 5) with matching dtypes. {own round-trip test against published npm artefacts, 2026-08-01, confidence: high, class: failure→passed}
26. The same holds for the UNCOMPRESSED and GZIP variants — pyarrow, DuckDB and Polars all read both; pyarrow confirms the recorded codec as `GZIP` for the fflate-compressed file. {own measurement, 2026-08-01, confidence: high, class: pattern}
27. hyparquet round-trips its own output: `parquetReadObjects` returned 100,000 rows with values and nulls intact, and `created_by` is stamped `hyparquet`. {own measurement, 2026-08-01, confidence: high, class: pattern}
28. Third-party conformance signal: **the Apache Parquet project's own implementation-status page lists hyparquet** as a JavaScript implementation with per-feature support (all physical types except INT96/FLBA write, PLAIN/RLE/RLE_DICTIONARY/delta encodings, SNAPPY, bloom filters, page indices, geospatial); page last modified 2026-07-07. {parquet.apache.org/docs/file-format/implementationstatus/, Apache Parquet, 2026-07-07, accessed 2026-08-01, confidence: high, class: pattern}
29. hyparquet's own test corpus contains 209 files including recognisable Apache `parquet-testing` fixtures (`byte_stream_split.zstd.parquet`, `datapage_v2.snappy.parquet`, `concatenated_gzip_members.parquet`, `bloom_filter.parquet`) with expected-value JSON alongside each — i.e. it is tested against the ecosystem's reference corpus, not only against itself. {api.github.com/repos/hyparam/hyparquet/contents/test/files, GitHub, accessed 2026-08-01, confidence: high, class: pattern}
30. No issue reports of unreadable hyparquet-writer output surfaced; the repo has only 6 open issues total. This is absence of evidence rather than evidence of absence — I did not read the issue tracker item by item. {api.github.com/repos/hyparam/hyparquet-writer, GitHub, accessed 2026-08-01, confidence: low, class: failure}

### Q5 — scale

31. **100,000 rows × 5 columns, SNAPPY: 258 ms, output 2,321,579 bytes, heap delta 54.4 MB.** UNCOMPRESSED: 159 ms, 3,600,536 bytes. GZIP via fflate (3 columns): 351 ms, 1,180,560 bytes. Read-back with hyparquet: 115 ms. {own measurement, Node.js on Linux x86-64, hyparquet-writer@0.16.3, 2026-08-01, confidence: high, class: performance}
32. **These are Node numbers, not browser numbers** — same V8 engine and same pure-JS code path with no Node built-ins in the browser export path, so browser timings should be the same order, but I found **no third-party measurement of hyparquet-writer in a real browser at 100k rows** and did not run one myself. Flagged as the main unverified item. {own measurement + absence of retrieved browser benchmarks, 2026-08-01, confidence: medium, class: performance}
33. `parquetWriteBuffer` is **synchronous**, so a ~0.3 s write blocks the main thread and freezes the tab for that long; the package also exports a streaming `ParquetWriter` and `parquetWriteRows`, and being dependency-free JS it can be moved into a Web Worker. {hyparquet-writer@0.16.3 `src/index.js` exports + own timing, published source/own measurement, accessed 2026-08-01, confidence: high, class: pattern}

### Q6 — the honest alternative (footnote)

34. Not needed — the gate passes. If a zero-dependency fallback is ever wanted, UNCOMPRESSED Parquet from the same library needs no compressor at all, and CSV remains the trivial floor. Hyperparam's own stated motivation for building the writer was exactly this use case: "Before Hyparquet-Writer the only way to write parquet files from the browser was huge wasm bundles (duckdb, datafusion)… export those results in-browser as a Parquet file… avoiding expensive CSV conversions". {hyperparam.app/about/opensource via web search result text, Hyperparam (vendor — advocacy register, discount accordingly), accessed 2026-08-01, confidence: low, class: ecosystem}

## Leads worth chasing

- Run the 100k-row write in an actual Firefox 145 / Chrome 143 tab and time it; also test in a Web Worker with a transferable ArrayBuffer, since the API is synchronous.
- Check `hyparquet-writer`'s bus factor (contributor count, whether one person publishes every release) — the Hyperparam org is small and the writer has only 59 stars.
- `hyparquet-compressors` has not been published since 2025-03-20; if ZSTD or Brotli output is ever wanted, verify whether a *sync* JS compressor exists at all (fzstd is decompression-only as far as its name and role in the read path suggest).
- The writer pins `hyparquet@1.27.1` exactly; confirm that pinning does not cause duplicate copies if the app also depends on hyparquet directly (bundle measured at 33,439 B gzip for both, so dedup appeared to work with esbuild).
- Timestamps came back as `timestamp[ms, tz=UTC]` in pyarrow but `datetime[ms]` (naive) in Polars — worth checking whether the writer emits `isAdjustedToUTC` and whether that matters for the target users.

## Contradictions

- hyparquet's README claims it "supports all parquet types, encodings, and compression codecs", but its own compression table two sections later marks GZip, LZO and Brotli as ❌ without the separate `hyparquet-compressors` package. Trust the table.
- Apache's implementation-status page says hyparquet lacks BYTE_STREAM_SPLIT, yet hyparquet-writer ships `src/splitstream.js` and a `write.splitstream.test.js`. Likely the page describes the reader only, or predates the writer's feature; unresolved.
- parquet-wasm's README quotes 1.2 MB brotli for the full build while the published `.wasm` is 6.49 MB raw / 1.81 MB gzip. Brotli beats gzip, so these are compatible; the README number is best-case transfer, not the artefact size, and it says nothing about the inlining cost.
