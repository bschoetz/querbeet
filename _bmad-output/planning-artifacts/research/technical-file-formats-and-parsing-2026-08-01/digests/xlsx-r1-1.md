# Digest: D3 XLSX read/write — round 1

Budget note: 16 tool calls / ~9 sources spent. Primary sources dominate (SheetJS docs site, SheetJS Gitea API, npm registry API, GitHub API, SheetJS CDN artefacts fetched and measured directly). Two search-engine summaries were used only for leads and for two claims explicitly marked low/medium confidence.

## Findings

### Q1 — SheetJS distribution and licence

1. The current SheetJS Community Edition version is **0.20.3**, and the docs state plainly that release scripts live at `https://cdn.sheetjs.com/` and that "a number of services host older versions … due to syncing issues, they are generally out of date. The SheetJS CDN is the authoritative source". `{claim, https://docs.sheetjs.com/docs/getting-started/installation/standalone, SheetJS (vendor docs), pub_date: undated page, accessed 2026-08-01, confidence: high, class: version}`
2. The `xlsx` package on the public npm registry is **stale at 0.18.5, published 2022-03-24** — the registry `dist-tags.latest` is 0.18.5 and no 0.19.x/0.20.x version exists there; registry metadata was last modified 2026-07-17 (metadata only, no new version). `{claim, https://registry.npmjs.org/xlsx, npm registry API (primary), accessed 2026-08-01, confidence: high, class: version}`
3. Independent corroboration of the npm/CDN split: SheetJS's own issue tracker carries a bug titled "No matching version found for xlsx@0.20.3 in npm registry" (issue #3183) and users report installing via `npm i --save https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`; a third party republishes CE to npm as `@saadeh/xlsx`. `{claim, https://git.sheetjs.com/sheetjs/sheetjs/issues/3183 and https://www.npmjs.com/package/@saadeh/xlsx, SheetJS issue tracker + npm, accessed 2026-08-01 via search result listing, confidence: medium (titles/URLs seen, pages not opened), class: ecosystem}`
4. So the break happened **between 0.18.5 (2022-03-24) and 0.19.0** — i.e. registry publishing stopped in 2022; every release since is CDN-only. `{claim, derived from https://registry.npmjs.org/xlsx version timeline + https://docs.sheetjs.com/docs/getting-started/installation/standalone, confidence: high, class: version}`
5. **Licence is Apache-2.0** — declared in the npm package metadata and unchanged in the shipped build header (`xlsx.js (C) 2013-present SheetJS`). Apache-2.0 permits unrestricted commercial use; attribution/NOTICE obligations apply when redistributing. `{claim, https://registry.npmjs.org/xlsx (license field) + https://cdn.sheetjs.com/xlsx-0.20.3/package/dist/xlsx.full.min.js (header, fetched directly), confidence: high, class: licence}`
6. **CE releases have stalled: the newest tag `v0.20.3` is dated 2024-07-18**, i.e. just over two years old as of today. Preceding cadence: 0.20.0 (2023-11), 0.20.1 (2023-12-05), 0.20.2 (2024-04-04), 0.20.3 (2024-07-18). `{claim, https://git.sheetjs.com/api/v1/repos/sheetjs/sheetjs/tags, SheetJS Gitea API (primary), accessed 2026-08-01, confidence: high, class: version}`
7. **But the source tree is not dead** — commits continue into 2026: latest master commits 2026-02-09 (`sheet_to_html sanitize links option`, fixes #3345), 2026-01-31, 2025-12-12, 2025-12-03, 2025-12-01, 2025-08-27/26, 2025-04-30, mostly authored by "SheetJS" with occasional outside contributors. Repo not archived; 214 open issues, 15 open PRs; repo metadata updated 2026-02-09. `{claim, https://git.sheetjs.com/api/v1/repos/sheetjs/sheetjs/commits and /repos/sheetjs/sheetjs, SheetJS Gitea API (primary), accessed 2026-08-01, confidence: high, class: ecosystem}`
8. Net reading of 6+7: **CE is maintained-but-unreleased** — fixes land in master, no tagged/CDN release in ~24 months. Anyone pinning the CDN script gets 2024 code.

### Q2 — CE versus Pro boundary

9. The vendor's own Pro page places **all styling behind Pro Basic**: "Cell, column, table and worksheet-level styling", "Text styling and Rich text support", "Styled HTML table ingress and egress", "Data Validations and Conditional Formatting", "International locale support". Further paid builds: Pro Image, Pro Chart, Pro Edit (in-place editing of an existing file with fidelity). `{claim, https://sheetjs.com/pro, SheetJS (vendor), accessed 2026-08-01 (fetched directly), confidence: high, class: licence}`
10. **Performance is also partly a paid add-on**: the Pro page lists under "Additional Components" — "NodeJS and browser performance enhancements", alongside PivotTable generation and password/encryption support. `{claim, https://sheetjs.com/pro, SheetJS (vendor), accessed 2026-08-01, confidence: high, class: licence}`
11. No pricing is published — the page says "Inquire at [email protected]" / "Schedule a Short Conversation". Pro cost is therefore **unknown and quote-based**. `{claim, https://sheetjs.com/pro, accessed 2026-08-01, confidence: high, class: licence}`
12. **Number formats ARE in CE**, and this is the decisive nuance for the German-Excel requirement: the CE data model documents the cell `z` property as "number format string associated with the cell", with a worked example `{t:"n", v:3.5, z:"$0.00", w:"$3.50"}`, and the CE docs carry a whole "Number Formats" feature page. The `s` property ("the style/theme of the cell") is the one CE does not author. `{claim, https://docs.sheetjs.com/docs/csf/cell, SheetJS CE docs (primary), accessed 2026-08-01, confidence: high, class: pattern}`
13. **Column widths are CE**: the CE docs sidebar carries a "Column Properties" feature page under Spreadsheet Features (alongside Row Properties, Merged Cells, Hyperlinks, Comments, Defined Names, Sheet Visibility, VBA). `{claim, https://docs.sheetjs.com/docs/csf/cell (navigation of CE docs), SheetJS CE docs, accessed 2026-08-01, confidence: medium (page listed in CE docs nav; page itself not opened), class: pattern}`
14. So the CE/Pro line for a plain tabular exporter is: **numbers, dates, number formats, column widths, merges, comments, hyperlinks = CE; bold headers, fills, borders, fonts, freeze-pane styling, conditional formatting = Pro.** Header bolding is "not in CE" at all — not merely awkward. `{synthesis of 9, 12, 13, confidence: medium-high}`
15. No read-side capability limit was found in CE — the standalone `xlsx.full.min.js` "includes support for reading and writing many spreadsheet formats"; the only documented reduction is in the opt-in `xlsx.mini.min.js` slim build, which drops CSV/SYLK encodings ("directly affecting users outside of the United States"), XLSB/XLS/Lotus/SpreadsheetML/Numbers, and stream utilities. `{claim, https://docs.sheetjs.com/docs/getting-started/installation/standalone, SheetJS CE docs, accessed 2026-08-01, confidence: high, class: pattern}` — note the mini build is explicitly wrong for a German user.

### Q3 — SheetJS at scale, and size

16. **Measured bundle size (my own measurement, fetched from the vendor CDN today): `xlsx.full.min.js` 0.20.3 = 951,904 bytes raw, 334,805 bytes gzip (gzip -6). `xlsx.mini.min.js` = 279,523 bytes raw, 86,340 bytes gzip.** `{claim, https://cdn.sheetjs.com/xlsx-0.20.3/package/dist/xlsx.full.min.js and .../xlsx.mini.min.js, SheetJS CDN (primary artefact), measured 2026-08-01, confidence: high, class: performance}` — ~930 KB inlined into a single HTML file, ~335 KB over the wire compressed. Much of the bulk is codepage tables (the build starts with `cptable` CP437 data), which is exactly what the mini build drops and exactly what a German user needs.
17. SheetJS's own docs page "Large Datasets" (`/docs/demos/bigdata/stream/`) documents that API functions read entire files into memory, that browsers enforce tight memory limits, that **Web Workers are strongly encouraged** for large files in the browser, and that "dense mode" worksheets (arrays of arrays) exist as a workaround for Chrome performance regressions. `{claim, https://docs.sheetjs.com/docs/demos/bigdata/stream/, SheetJS CE docs, accessed 2026-08-01 via search-result summary, confidence: medium (page not opened directly), class: performance}`
18. A long-lived SheetJS issue #798 records `XLSX.write` producing "JavaScript heap out of memory" on large JSON input, and issue #61 "Support large excel files" and #1113 "Memory leak issue" exist on the tracker. `{claim, https://github.com/SheetJS/sheetjs/issues/798, https://git.sheetjs.com/sheetjs/sheetjs/issues/61, .../issues/1113, SheetJS issue trackers, accessed 2026-08-01 via search-result listing, confidence: medium (titles seen, threads not read; ages and fix status unverified), class: failure}`
19. A secondary comparison claims SheetJS uses ~6x more memory than ExcelJS on a 100,000-row / 10-column / 8 MB XLSX, and that writing 100k records in one file can exceed 90 seconds. **I did not reach a primary benchmark for either number and I do not rest anything on them.** `{claim, https://www.pkgpulse.com/guides/sheetjs-vs-exceljs-vs-node-xlsx-excel-files-node-2026 (aggregator guide), accessed 2026-08-01 via search summary, confidence: low, class: performance}`
20. **No credible, reproducible, browser-side measurement for ~100k rows was found in round 1.** This is the single biggest evidence gap.

### Q5 — "Opens cleanly in Excel" pitfalls

27. **The 1900 leap-year bug is documented and handled by SheetJS as a first-class concern**, not an accident: Excel's default epoch is "January 0 1900" (value 0 = 1899-12-31 00:00) because Lotus 1-2-3 wrongly treated 1900 as a leap year, and the 1904 system exists to skip the bad date; the workbook's epoch is exposed as `wb.Workbook.WBProps.date1904`. XLSX/XLSM/XLSB all support both 1900 and 1904. `{claim, https://docs.sheetjs.com/docs/csf/features/dates, SheetJS CE docs (primary), accessed 2026-08-01, confidence: high, class: pattern}`
28. **The epoch is timezone-relative** — "The epoch is based on the system timezone" — which is the documented mechanism behind off-by-one-day date bugs when a JS `Date` round-trips through a spreadsheet serial. `{claim, https://docs.sheetjs.com/docs/csf/features/dates, SheetJS CE docs, accessed 2026-08-01, confidence: high, class: pattern}`
29. `cellDates: true` is the documented parse option that makes SheetJS produce JS `Date` objects rather than raw serial numbers on read. `{claim, https://docs.sheetjs.com/docs/csf/features/dates, SheetJS CE docs, accessed 2026-08-01, confidence: high, class: pattern}`
30. **Number-stored-as-text is explicitly addressed by SheetJS on write**: the cell-type docs state that where a value could be interpreted as "number stored as text", "generated Excel files automatically suppress that class of error, but other formats may elicit errors". Combined with finding 12, the correct discipline is to emit `t:"n"` with a `z` number format for numerics and `t:"s"` only for genuine text (which is also the leading-zeros fix — leading zeros survive only as text cells or via a `00000`-style format). `{claim, https://docs.sheetjs.com/docs/csf/cell, SheetJS CE docs, accessed 2026-08-01, confidence: high, class: pattern}`
31. **Umlauts are a non-issue in XLSX and a real issue in CSV.** XLSX is a zipped XML container that is UTF-8 throughout, so umlauts are structural, not locale-dependent; the mini build is the only SheetJS variant that drops "CSV and SYLK encodings (directly affecting users outside of the United States)" — the vendor flags the non-US risk on the *CSV* path specifically. `{claim, https://docs.sheetjs.com/docs/getting-started/installation/standalone, SheetJS CE docs, accessed 2026-08-01, confidence: medium (UTF-8-ness of OOXML is background knowledge, not retrieved this round), class: pattern}`
32. **Decimal comma for a German user is a display/locale property, not a stored-value property** — the value stays `3.5` and the number format decides rendering; Excel renders per the user's Windows regional settings. SheetJS lists "International locale support" as a **Pro** feature, and sells "SSF Pro: Format numbers and dates in different locales" as a standalone component — meaning CE writes format *codes*, and locale-aware formatting tooling is paid. `{claim, https://sheetjs.com/pro, SheetJS (vendor), accessed 2026-08-01, confidence: medium, class: licence}`
33. **No issue-tracker evidence about Excel "protected view" or repair prompts on JS-generated xlsx was retrieved this round.** Not found ≠ does not exist. `{class: pattern, confidence: n/a}`

### Q6 — the CSV escape hatch

34. Excel on Windows defaults to the system locale encoding (e.g. Windows-1252) **unless it finds a UTF-8 BOM** (`EF BB BF`), which is why the BOM is the standard fix for umlauts; the BOM is a widely used convention (Python's `utf-8-sig` exists for exactly this). `{claim, https://www.convertmystuff.com/resources/developer-tools/csv-encoding-and-excel/ and https://www.ablebits.com/office-addins-blog/convert-excel-csv/, secondary blogs, accessed 2026-08-01 via search summary, confidence: low-medium (no primary/Microsoft source read), class: pattern}`
35. **The BOM fixes encoding but NOT the delimiter** — German/European Excel expects a **semicolon** because the comma is the decimal separator; a comma-delimited CSV opened by double-click in German Excel lands everything in column A. A Microsoft Q&A thread also exists titled "Excel is not considering csv UTF-8-BOM file as UTF-8", i.e. BOM handling is not universally reliable. `{claim, https://learn.microsoft.com/en-us/answers/questions/1642023/excel-is-not-considering-csv-utf-8-bom-file-as-utf and https://www.mrexcel.com/board/threads/...1136683/, Microsoft Q&A + MrExcel forum, accessed 2026-08-01 via search listing, confidence: low (threads not opened), class: failure}`
36. Practical consequence for the fallback: a German-safe CSV needs **UTF-8 + BOM + semicolon delimiter + comma decimal separator**, i.e. three locale decisions that XLSX makes for you. This is why CSV is a fallback, not the recommendation. `{synthesis of 34, 35, confidence: medium}`

## Leads worth chasing

- **The write/read split pair (`write-excel-file` + `read-excel-file`) is the strongest maintenance signal in the field** — both released within the last 8 weeks, one within the last 4 days, both MIT, same author (`catamphetamine`, GitLab-hosted). Round 2 must establish: browser bundle size, CDN/UMD availability for single-file inlining, whether styles and number formats are supported on write, and 100k-row behaviour. If it clears those, it is the runner-up — and it wins outright if MIT-with-styles matters more than format breadth.
- **SheetJS "maintained but unreleased"** is the crux of the decision. Chase: has the vendor said anything about the release gap? Is there a 0.20.4/0.21 in a branch? Does the tarball at `cdn.sheetjs.com/xlsx-latest/` differ from 0.20.3?
- **`@office-kit/xlsx`** describes itself as openpyxl-inspired and pure-MIT with no Pro tier — if real and browser-capable it directly targets the SheetJS styling paywall. Pre-1.0 in July 2026 makes it a risk, not a pick.
- **Dense mode** (`dense: true`, arrays-of-arrays worksheets) is the named SheetJS lever for 100k rows and Chrome regressions. Worth a targeted round-2 look at the CE docs page.
- The mini build's exclusion note ("CSV and SYLK encodings — directly affecting users outside of the United States") is a **trap for anyone size-optimising the single-file bundle for a German user.** Flag it hard.
- SheetJS Pro sells "browser performance enhancements" as an add-on — evidence that CE browser performance at scale is a known weak point the vendor monetises.

## Contradictions

- **ExcelJS "maintainers explicitly call it inactive" (search summary) vs the repository.** The repository shows no archive flag, no deprecation on npm, and a `4.4.1-prerelease.0` published 2024-12-20 — someone touched it after the last commit I can see on master. The *hard* evidence (no stable release in 33 months, no default-branch commit in 31 months, 798 open issues) supports "dormant" without needing the maintainer-statement claim, which I could not verify. I report dormancy on repository metrics and do **not** assert a maintainer declaration.
- **"ExcelJS is Node.js-only" (search summary) vs ExcelJS's own marketing site (exceljs.org) which says "Node.js & Browser".** Unresolved; neither page was read directly. Given ExcelJS is dormant either way, this contradiction does not change the ranking, but it must be settled before ExcelJS is named runner-up.
- **SheetJS "abandoned" framing (implied by the npm staleness) vs the commit log.** The commit log wins: work continued through 2026-02. The correct characterisation is a *release* gap, not abandonment.

## Looked for and could not find

- **Any primary, reproducible browser benchmark for ~100k rows** — read or write, time or memory, with hardware and browser stated. Only an aggregator's unsourced "6x memory" and "90 seconds" figures, which I refuse to rest a recommendation on.
- **SheetJS Pro pricing.** Not published anywhere; quote-only. Cost of escaping the styles paywall is therefore unknowable without contacting the vendor.
- **Confirmation of the CE column-width feature page contents** (seen in the docs nav, page not opened).
- **Any issue-tracker evidence on Excel "protected view" / "we found a problem with some content" repair prompts** for JS-generated xlsx.
- **Browser-build details for every non-SheetJS candidate**: bundle size, gzip size, UMD/IIFE availability, CDN presence, whether a Node polyfill (Buffer/stream) is required. This is the entire round-2 workload.
- **German-locale-specific evidence** — no German-language issue thread or Microsoft doc on decimal-comma or umlaut handling was retrieved; the CSV/BOM findings rest on generic English-language blog sources and are correspondingly weak.
- **Whether SheetJS `xlsx.full.min.js` at 952 KB actually inlines cleanly into a single HTML file** (escaping of `</script>` sequences inside the codepage tables) — untested.
