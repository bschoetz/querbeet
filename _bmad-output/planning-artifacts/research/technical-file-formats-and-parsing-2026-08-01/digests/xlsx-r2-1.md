# Digest: D3 XLSX — round 2

Accessed date for everything below: 2026-08-01.

## Findings

### Q1 — Browser viability and size of the live alternatives

1. **`write-excel-file` ships a real UMD browser bundle that needs no bundler and no Node polyfills.** `https://cdn.jsdelivr.net/npm/write-excel-file@4.1.1/bundle/write-excel-file.min.js` starts with a standard UMD prelude and exposes the global `writeXlsxFile`: `!function(e,r){"object"==typeof exports&&…:(e=…globalThis…).writeXlsxFile=r()}`. A grep of the downloaded file finds `require(` 0 times and `process.` 0 times (`Buffer` appears 4 times, in guard positions only — I did not decompile each occurrence). {source: https://cdn.jsdelivr.net/npm/write-excel-file@4.1.1/bundle/write-excel-file.min.js, publisher: jsDelivr serving npm `write-excel-file` (catamphetamine), pub_date: 2026-06-08 (version publish time from npm registry), accessed: 2026-08-01, confidence: high, class: primary artefact}
2. **Its own README documents exactly this usage.** The `## CDN` section shows `<script src="https://unpkg.com/write-excel-file@1.x/bundle/write-excel-file.min.js"></script>` followed by `writeXlsxFile(data, { fileName: 'file.xlsx' })`. Note the example still pins `@1.x` — stale in the docs, but the 4.1.1 bundle path is identical and exists. {source: https://cdn.jsdelivr.net/npm/write-excel-file@4.1.1/README.md, publisher: catamphetamine, pub_date: 2026-06-08, accessed: 2026-08-01, confidence: high, class: primary doc}
3. **`read-excel-file` likewise ships a UMD bundle exposing global `readXlsxFile`**, same prelude shape, `require(` 0 hits, `process.` 0 hits. Its README `## CDN` section shows `<script src="https://unpkg.com/read-excel-file@9.x/bundle/read-excel-file.min.js"></script>` with a file-input example. {sources: https://cdn.jsdelivr.net/npm/read-excel-file@9.3.5/bundle/read-excel-file.min.js and https://cdn.jsdelivr.net/npm/read-excel-file@9.3.5/README.md, publisher: catamphetamine, pub_date: 2026-07-28, accessed: 2026-08-01, confidence: high, class: primary artefact + primary doc}
4. **Caveat on `read-excel-file` 9.x in a single HTML file: the `browser` entry now spawns a Web Worker internally.** README: "`read-excel-file` already uses Web Workers internally when reading `.xlsx` file contents… for those who still prefer to manually run `read-excel-file` in their own Web Worker, there's `read-excel-file/web-worker` import path which is same as `read-excel-file/browser` except that it doesn't spawn any Web Workers." Worker spawning normally needs a separate script URL or a blob worker; the dependency list includes `worker-f`, which suggests inline/blob workers, but I did not verify that the UMD bundle works from a `file://` single HTML page. This is the one open browser-viability risk for this candidate. {source: https://cdn.jsdelivr.net/npm/read-excel-file@9.3.5/README.md, publisher: catamphetamine, pub_date: 2026-07-28, accessed: 2026-08-01, confidence: medium, class: primary doc}
5. **Both packages are MIT and dependency-light.** npm registry: `write-excel-file@4.1.1`, licence MIT, one dependency (`fflate ^0.8.2`), repo `gitlab.com/catamphetamine/write-excel-file`. `read-excel-file@9.3.5`, licence MIT, deps `saxen`, `fflate`, `worker-f`, `unzipper-esm`, repo `gitlab.com/catamphetamine/read-excel-file`. {source: https://registry.npmjs.org/write-excel-file and https://registry.npmjs.org/read-excel-file, publisher: npm registry, pub_date: 2026-06-08 / 2026-07-28, accessed: 2026-08-01, confidence: high, class: primary metadata}
6. **`@office-kit/xlsx` and `xlsx-kit` ship no UMD/IIFE build at all — ESM-only, multi-chunk, no root entry point.** Both packages' `exports` maps contain only subpath entries (`./io`, `./styles`, `./workbook`, `./node`, …) and no `"."` entry; there is no `main`, no `browser`, no `unpkg`/`jsdelivr` field. jsDelivr's auto-bundler confirms this: `https://cdn.jsdelivr.net/npm/@office-kit/xlsx@0.9.0/+esm` returns the 33-byte body `Couldn't find the requested file.` The dist is ~dozens of hash-named `.mjs` chunks with relative imports, so using it in one HTML file would require running a bundler yourself. {sources: https://registry.npmjs.org/@office-kit/xlsx, https://data.jsdelivr.com/v1/packages/npm/@office-kit/xlsx@0.9.0?structure=flat, https://cdn.jsdelivr.net/npm/@office-kit/xlsx@0.9.0/+esm, publisher: npm registry + jsDelivr, pub_date: 2026-07-12, accessed: 2026-08-01, confidence: high, class: primary metadata + primary artefact}
7. **`@office-kit/xlsx` declares a Node 22+ runtime floor for parts of its API.** Its README: "**Node 22+ required**: relies on built-in `Web Streams`, `Blob`, and `fetch`. Node 18 / 20 (EOL) are not supported." and, under limitations, "**Browser stress-test history is shorter** than ExcelJS's. If you ship to millions of browser users today, run your own benchmark first." The same README explicitly routes browser readers elsewhere: "**Read simple xlsx in the browser** → `read-excel-file` is excellent." That is the vendor conceding the browser case. {source: https://cdn.jsdelivr.net/npm/@office-kit/xlsx@0.9.0/README.md, publisher: office-kit, pub_date: 2026-07-12, accessed: 2026-08-01, confidence: high, class: primary doc}

### Q2 — What `write-excel-file` can actually do on write

8. **Number formats: yes, per cell and per column, as raw Excel format codes.** README `### Format` section and examples: `{ value: 1234.56, format: '[$$-409]#,##0.00' }`, `{ value: 120000, type: Number, format: '#,##0.00' }`. {source: https://cdn.jsdelivr.net/npm/write-excel-file@4.1.1/README.md, publisher: catamphetamine, pub_date: 2026-06-08, accessed: 2026-08-01, confidence: high, class: primary doc}
9. **Dates as real Excel dates: yes, and a format is mandatory.** "All `Date` cells are required to specify a `format`, unless a default `dateFormat` option has been specified." Cell shape `{ value: new Date(), type: Date, format: 'mm/dd/yyyy' }`. {same source, confidence: high, class: primary doc}
10. **Cell styling: yes — this is the gap SheetJS CE leaves open and `write-excel-file` closes.** Documented cell options include `fontWeight: 'bold'`, `backgroundColor: '#aabbcc'`, `borderColor` plus `leftBorderColor`/`rightBorderColor`/`topBorderColor`/`bottomBorderColor`, `align` (`left`/`center`/`right`), `alignVertical` (`top`/`center`/`bottom`), `wrap: boolean`, and `columnSpan` for merged cells. {same source, confidence: high, class: primary doc}
11. **Column widths: yes, in characters** — `const columns = [ …, { width: 20 } ]` passed as `writeExcelFile(sheetData, { columns })`; README notes widths are "in 'characters' rather than in 'pixels'". Behaviour change in v4: "Previously, it used to apply the default `width: 14` to `type: Date` columns. It no longer does that" and "Previously, it used to apply bold font to the header row by default. It no longer does that." So headers must be styled explicitly now. {same source, confidence: high, class: primary doc}
12. **Multiple sheets: yes**, `## Multiple Sheets` section; v4 changed the call shape to an array of per-sheet objects `{ data, sheet: 'Sheet1', columns }`. {same source, confidence: high, class: primary doc}
13. **Bonus: conditional formatting is supported, free.** `conditionalFormatting` option takes rules of `{ cellRange: {from:{row,column}, to:{row,column}}, condition: {operator, value}, style: {backgroundColor} }`. This is a paid-Pro feature on the SheetJS side per round 1. {same source, confidence: high, class: primary doc}
14. **`read-excel-file` reads arbitrary sheets with no schema.** README: "The result is an array of rows. Each row is an array of values — `string`, `number`, `boolean` or `Date`." The schema is optional and additive — "It also supports parsing spreadsheet rows into JSON objects using a schema" — and in v9 schema parsing is a separate step (`parseData(await readSheet(...), schema)`). The v9 default export "returns all available sheets — an array of objects: `[{ sheet: 'Sheet 1', data: [[…]] }, …]`", replacing the old `getSheets: true` parameter, so sheet discovery is schema-free too. {source: https://cdn.jsdelivr.net/npm/read-excel-file@9.3.5/README.md, publisher: catamphetamine, pub_date: 2026-07-28, accessed: 2026-08-01, confidence: high, class: primary doc}
15. **`read-excel-file` publishes its own read benchmark** ("sample `.xlsx` files of different size"): 1 MB → 0.1 s browser / 0.1 s Node; 10 MB → 0.5 s / 0.6 s; 50 MB → 2.6 s / 3.0 s. Conditions (machine, browser version, row counts) are not stated, and it is vendor self-measurement — treat as an order-of-magnitude signal only. Architecture note from the same section: unzip via fflate (async in browser for files > 512 KB), then a synchronous SAX XML parse. {same source, confidence: medium, class: vendor self-benchmark}

### Q5 — SheetJS at scale, and the practical levers

25. **What `dense: true` actually changes.** "When the option `dense: true` is passed, parsers will generate a 'dense-mode' worksheet where cells are stored in an array of arrays. `sheet['!data'][R][C]` returns the cell object at row R and column C… When processing small worksheets in older environments, sparse worksheets are more efficient than dense worksheets. In newer browsers, when dealing with very large worksheets, **dense sheets use less memory and tend to be more efficient**." Dense worksheets "were overhauled in version 0.19.0". `read`, `readFile` and `aoa_to_sheet` accept the option; `write`/`writeFile`/`sheet_to_json` auto-detect. Rationale given: "designed to work around Google Chrome performance regressions" — V8 made the address-keyed-object layout slow, arrays-of-arrays fast; the sparse default is kept only for backwards compatibility. {sources: https://docs.sheetjs.com/docs/csf/sheet and https://docs.sheetjs.com/docs/demos/bigdata/stream, publisher: SheetJS, pub_date: stream page updated 2026-03-23, accessed: 2026-08-01, confidence: high, class: primary doc}
26. **The vendor's stated position on large data is a memory warning, not a row number.** "For maximal compatibility, SheetJS API functions read entire files into memory and write files in memory. Browsers and other JS engines enforce tight memory limits. The library offers alternate strategies to optimize for memory usage." The Big Data index lists exactly two levers: "Large Datasets — Dense Mode + Incremental CSV / HTML / JSON / XLML Export" and "Web Workers — Run large data flows without freezing the browser". {sources: https://docs.sheetjs.com/docs/demos/bigdata/ and https://docs.sheetjs.com/docs/demos/bigdata/stream, publisher: SheetJS, accessed: 2026-08-01, confidence: high, class: primary doc}
27. **Decision-relevant: SheetJS's streaming *write* path does not emit xlsx.** The streaming writers are `XLSX.stream.to_csv` / `to_html` / `to_json` (+ XLML per the index page) — there is no streaming xlsx writer. Writing 100k rows to `.xlsx` therefore always means building the whole workbook and the whole output file in memory. The browser section of the same page states plainly: "NodeJS streaming APIs are not available in the browser." {source: https://docs.sheetjs.com/docs/demos/bigdata/stream, publisher: SheetJS, pub_date: last updated 2026-03-23, accessed: 2026-08-01, confidence: high, class: primary doc}
28. **The vendor's browser worker recipe is concrete and copyable**: a blob worker that `importScripts("https://cdn.sheetjs.com/xlsx-0.20.3/package/dist/xlsx.full.min.js")`, reads with `new FileReaderSync().readAsArrayBuffer(e.data.file)`, parses with `XLSX.read(ab, {dense: true})`, and posts the result back. Note this pulls the script from the CDN inside the worker — for a truly offline single HTML file the worker body would have to inline the library instead. {source: https://docs.sheetjs.com/docs/demos/bigdata/worker, publisher: SheetJS, accessed: 2026-08-01, confidence: high, class: primary doc}
29. **No measured SheetJS browser number for ~100k rows was found.** The Big Data pages give recipes and a row-counter UI but no timing table; the bigdata index page's own footer says "Last updated on Apr 12, 2024". I found no credible third-party measured figure within budget. State this as a gap, not as a favourable result. {sources: https://docs.sheetjs.com/docs/demos/bigdata/, https://docs.sheetjs.com/docs/demos/bigdata/stream, publisher: SheetJS, accessed: 2026-08-01, confidence: high, class: primary doc (negative result)}

## Leads worth chasing

- Verify the `read-excel-file` 9.x UMD bundle actually works from a `file://` single HTML page — the internal Web Worker (`worker-f` dependency) is the specific thing that could break there. If it does break, `read-excel-file@8.x` or the `web-worker` export may be the fallback; check whether the UMD bundle exposes that variant.
- `write-excel-file`'s German-Excel behaviour is untested here: whether format codes like `#,##0.00` and `mm/dd/yyyy` are locale-translated by Excel on open (they normally are, since format codes are stored locale-neutral) and whether it writes shared strings as UTF-8 with BOM-free XML. Worth a one-file empirical test rather than more searching.
- SheetJS issues #992 (sheet-name-length repair prompt) and #2425 sit behind the Gitea login; the GitHub mirror `github.com/SheetJS/sheetjs/issues/992` may be readable via the GitHub API as #1537 and #1652 were.
- `write-excel-file`'s "Features" extension mechanism (hook into `xl/styles.xml`, `xl/worksheets/sheet{id}.xml` generation) is an escape hatch if something needed is missing — relevant if e.g. autofilter or freeze panes turn out to be unsupported.
- Neither `write-excel-file` nor `read-excel-file` publishes a write-side benchmark. A 100k-row write timing is unmeasured for the leading candidate.

## Contradictions

- **Round 1 framing vs. reality for `@office-kit/xlsx` / `xlsx-kit`.** Round 1 listed them as two separate new MIT packages. They are one codebase renamed (finding 18). Any tally that counts them as two independent live alternatives overstates the field.
- **Round 1's "master commits continue into February 2026" vs. today.** True, but February 2026 is the newest commit, i.e. ~6 months of silence (finding 22). The correct present-tense reading is "no tagged release in 2 years and no commit in 6 months, while docs were still edited in March 2026" — weaker than "actively developed but unreleased".
- **Gzip figure for `xlsx.full.min.js`:** 334,035 (this round, `gzip -9`) vs 334,805 (round 1). Same raw byte count, so the same artefact; the difference is compression settings. Use ~334 KB and do not treat either figure as exact.
- **`write-excel-file` README's CDN example pins `@1.x`** while the current version is 4.1.1 with a documented breaking-change list — a doc-freshness wart in an otherwise current package. The `bundle/` path itself is present and correct at 4.1.1 (verified by download).
