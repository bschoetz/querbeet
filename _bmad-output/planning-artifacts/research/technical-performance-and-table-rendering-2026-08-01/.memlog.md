- (claim) ref=[31] status=verified class=performance pub=2026-08 — One 100,000 x 20 source costs 80.2 MB of Chromium heap as an Arquero table (802 B/row) vs 102.8 MB as plain frozen row objects (1,078 B/row). The column store is ~22% cheaper; the saving is per-row object overhead.
- (claim) ref=[31] status=verified class=performance pub=2026-08 — aq.from() on top of an existing row array adds only 8.0 MB, because column arrays hold shared references to the same string values. Holding both source array and table costs 110.8 MB per source vs 80.2 MB for the table alone. Rule: drop the parsed row array after aq.from().
- (claim) ref=[31] status=verified class=performance pub=2026-08 — Memory scales exactly linearly across simultaneous sources: 80.2 MB each, reaching 552.6 MB cumulative Chromium heap at 5 x 100k x 20. This is ~2.4x R1's Node-based estimate of ~235 MB for five sources. Plan the budget from 550 MB.
- (claim) ref=[27] status=verified class=architecture pub=2025-05 — Arquero derived tables share the parent's column arrays by default (create() falls back to this._data). Confirmed empirically by object identity in a running browser [31]: select, filter, orderby and derive all SHARE the same backing array; slice, join and concat COPY. Heap deltas corroborate: filter 0.0 MB, select 0.0, orderby 0.1, derive 0.4, join 11.1, concat 16.0.
- (claim) ref=[31] status=verified class=performance pub=2026-08 — reify() is the memory release lever and it works: a source table of 80.2 MB filtered to 1,000 rows, reified, then with parent and view dropped, retains only 0.7 MB. Without reify() the small view pins the entire 80.2 MB parent.
- (claim) ref=[27] status=verified class=architecture pub=2025-05 — Two undocumented behaviours visible only in the 8.0.3 source: slice() materializes (calls reify(indices)) rather than being a view; and derive() allocates an array sized to totalRows(), not to the surviving row count. Measured [31]: deriving on a table filtered 100k->1k costs 0.4 MB naive vs 0.1 MB if reified first (4x less memory, 2.4 ms more time).
- (claim) ref=[31] status=verified class=performance pub=2026-08 — Reading the D1 render window out of an Arquero table is free: objects({limit:50}) costs 0.3 ms (Chromium) / 1 ms (Firefox), independent of offset in the table, 0 MB heap. Combined with D1's 4-5 ms window swap the complete preview path is ~5 ms.
- (claim) ref=[31] status=verified class=performance pub=2026-08 — Firefox is 1.5-2x slower than Chromium across Arquero work and 8x slower on full row materialization: objects() over 100k rows costs 12.5 ms in Chromium vs 97 ms in Firefox. Budget every whole-table materialization path (export, clipboard, JSON) against Firefox. Feeds D3.

- (decision) D2 verdict: Arquero fits with room to spare. Three architecture rules, all measured: (1) drop the parsed row array after aq.from(); (2) reify() after a selective filter and release the parent, or a 1k-row view pins 80 MB; (3) read the render window with objects({limit,offset}), never by iterating. Memory budget: plan from 550 MB at five simultaneous 100k sources, not R1's 235 MB. Arquero pipeline costs 263-446 ms vs R1's 10.5 ms plain JS — decision holds, price now known.

- (claim) ref=[32] status=verified class=performance pub=2026-08 — Fan-out in an Arquero DAG is free: 1/3/10 pure-view consumers of one 100k x 20 source cost 0.05 / 0.05 / 0.13 MB in total, and the per-consumer figure FALLS as consumer count rises. A derived column costs a flat 0.40 MB per consumer at 100k rows (0.43 / 1.20 / 3.95 MB for 1/3/10), so a 30-Step graph deriving one column per Step costs ~12 MB.
- (claim) ref=[32] status=verified class=performance pub=2026-08 — The join is the entire price of a graph: a diamond's two branches held unjoined cost 0.79 MB, recombining them with join_left (50,000 rows out) costs 10.81 MB — 10.0 MB for the rejoin. Branching is free, combining is not.
- (claim) ref=[32] status=verified class=performance pub=2026-08 — Retention in a DAG is clean and there is no leak: four Steps over a shared 80 MB source cost 0.82 MB total; dropping one leaf reclaims only its own derive array (0.42 MB) and nothing of the shared parent; dropping the whole graph returns exactly to baseline (0.00 MB).
- (claim) ref=[32] status=overturned class=performance pub=2026-08 — OVERTURNS a D2 recommendation. D2 stated 'reify() after a selective filter and release the parent' unconditionally. Measured in the graph case where the parent stays alive (the Editor can re-run from any Step): view-only 0.01 MB vs reified 0.11 MB, i.e. reifying COSTS 0.10 MB and saves nothing. It saves ~69 MB only when the parent can genuinely be released (69.65 -> 0.70 MB). Corrected rule: reify only when the parent is going away.
- (claim) ref=[32] status=verified class=failure-mode pub=2026-08 — NEW TRAP qualifying an R1 recommendation. R1's null-key sentinel substitution is safe only against a UNIQUE lookup. When both join inputs carry nulls — which a DAG makes easy, since two branches of one source inherit its nulls — every sentinel row matches every sentinel row and the output tracks the sentinel PAIR count almost exactly: 7k/14k/28k source rows produce 170,000 / 673,000 / 2,687,670 join rows against 167,000 / 667,000 / 2,668,000 sentinel pairs. Quadratic in the null count, invisible on a sample. At 100k source rows the pairs come to ~34 million and it crashed the tab. Reproduced independently in Node before acceptance. Route out: exclude sentinel rows and re-attach, or give each side a distinct sentinel, or refuse the join; and warn in the Join Step UI when both inputs carry nulls in the key column.
- (claim) ref=[32] status=verified class=performance pub=2026-08 — The realistic rescoped target measured end to end: five 100k sources unioned, sentinel-substituted, left-joined against a 5k unique-key lookup, filtered and derived (250,000 rows out) costs 447.07 MB retained (358.43 MB sources + 88.64 MB graph) and runs in 699.9 ms in Chromium.
