# Digest — D2 / Arquero internals, memory model, materialization — round 1, assistant 1

Brief: Arquero's data representation; which verbs share parent columns vs materialize;
what getting data back out costs; reported memory problems at scale; current version facts.
Budget: 5 sources, 12 tool calls. Returned 2026-08-01. Evidence is largely read from the
8.0.3 source, which is the strongest available basis and also means most quantitative
figures are derived from allocation sites rather than measured.

### Findings

1. **An Arquero table is a column store over a frozen plain object; each column is whatever array-like was handed in, accessed through `.at(row)`.** `Table`'s constructor is `const data = Object.freeze({ ...columns }); this._names = Object.freeze(names); this._data = data;` — one entry per column name, every read via `column.at(row)`, so a column may be a plain `Array`, a typed array, or a Flechette/Arrow vector interchangeably. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/table/Table.js, uwdata/arquero 8.0.3 via jsDelivr, 2025-05-29, accessed 2026-08-01, high, architecture}`
2. **`aq.from(arrayOfObjects)` converts — it allocates one fresh plain `Array(len)` per column and copies each field across; it does not retain the source array.** `columns-from.js`'s `fromArray` does `const add = name => columns[name] = Array(len)` then `cols[i][idx] = row[names[i]]`. Consequence: the table costs N x C new array slots holding the *same* value references (strings/objects shared, numbers copied); the original row-object array is a separate, independently retained allocation. Holding both ~ 2x the pointer/slot overhead, not 2x the string payload. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/table/columns-from.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
3. **Derived tables share the parent's column arrays by default: `create()` falls back to `this._data`.** `create({data, names, filter, groups, order})` calls `new this.constructor(data || this._data, ...)` — omit `data` and the child points at the identical column objects. This is the mechanism behind every view-style verb. `{same source, high, architecture}`
4. **`filter` is a bitset view: it allocates a `BitSet(totalRows)` and nothing else.** `_filter` builds `new BitSet(n)` where `n = table.totalRows()`, sets a bit per passing row, returns `table.create({ filter })`. `BitSet` is `new Uint32Array(Math.ceil(size / 32))` — at 100,000 rows that is 12,500 bytes per filter step (derived from source, not measured). The bitset is sized to the *backing* row count, not the surviving count, so chained filters each pay full price. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/filter.js + src/table/BitSet.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
5. **`orderby` stores only a comparator; the sort index is materialized lazily and then cached forever.** `_orderby` is `table.create({ order: comparator })`. `indices()` builds `new Uint32Array(n)` (400 KB at 100k rows), sorts it, memoizes it as `this._index`. Same lazy-cache pattern for `_partitions` and the row-object builder `_builder`. A table that has been printed, iterated or scanned in order retains a 400 KB index for its lifetime. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/orderby.js + src/table/Table.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
6. **`derive` shares all existing columns and allocates one new full-backing-length array per new expression — sized to `totalRows()`, not to the filtered row count.** `_derive` does `const cols = columnSet(options.drop ? null : table)` (copying existing column *references*) and then `names.map(name => cols.add(name, Array(total)))` with `const total = table.totalRows()`. Deriving on a table filtered from 100k down to 1k still allocates a 100k-slot array with 1k slots written. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/derive.js + src/table/ColumnSet.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
7. **`join` fully materializes: every output column is a new `[]` grown by `push`, plus two `Int32Array` hit-vectors, both input index vectors, and a hash lookup map.** `_join` builds `columns[i] = cols.add(names[i], [])`, calls `tableL.indices(false)` / `tableR.indices(false)`, `new Int32Array(nL)` and `new Int32Array(nR)`, and `indexLookup(...)`; the result is created via `cols.new(tableL)` which passes `filter: null, order: null`. Output is a genuinely independent copy. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/join.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
8. **`concat` (and therefore `union`) materializes every column, with a free early-out.** It allocates `const arr = Array(nrows)` per column and copies through `col.at(trow)`; but `if (trows === nrows) return table` — concatenating only empty tables returns the original by reference. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/concat.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
9. **`groupby` is a view plus a `Uint32Array(totalRows)` key vector (400 KB at 100k rows), and can be free when grouping a single Arrow dictionary column.** `_groupby` returns `table.create({ groups: createGroups(...) })`; `createGroups` allocates `const keys = new Uint32Array(nrows)`, plus a JS object index and a `rows` array of one representative row per group. Short-circuit: `if (n === 1 && !table.isFiltered() && exprs[0].field)` and the column exposes `col.groups(names)`, the column's own dictionary grouping is reused with no new allocation. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/groupby.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
10. **`slice` is the surprise materializer.** Non-grouped: it pushes row ids into a plain JS array and calls `table.reify(indices)`, which copies real data into new arrays. Grouped: `filter(table, _slice(start, end)).reify()`. Either path produces fresh columns of the slice's length — cheap for a small window, but it is a copy, not a view. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/verbs/slice.js, 2025-05-29, accessed 2026-08-01, high, architecture}`
11. **`reify()` is the explicit compaction primitive, and it has two no-copy fast paths.** `if (!indices && !this.isOrdered())`: unfiltered -> `return this` (no allocation at all); filtered but all rows pass -> `data = this.data()` (reuse). Otherwise it allocates `new (arrayType(prev))(nrows)` per column — preserving typed-array types — and rebuilds group keys via `reindex`. This is the documented lever for dropping a large parent's backing arrays after a selective filter. `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/table/Table.js, 2025-05-29, accessed 2026-08-01, high, capability}`
12. **Column sharing is confirmed by the official docs as intentional design, not an implementation accident.** The API reference states "A column instance may be used across multiple tables and so does not track a table's filter or orderby criteria," and `table.data()` "returns the same structure used by the Table (not a copy)." `{https://idl.uw.edu/arquero/api/table.html, UW Interactive Data Lab, undated, accessed 2026-08-01, high, architecture}`
13. **`objects()` supports true windowed extraction — `{limit, offset, columns, grouped}` — and the offset is honoured inside `scan`, never by building the full array first.** `objects` calls `this.scan(fn, true, limit, offset)`; `scan` computes `const n = Math.min(nrows, i + limit)` and, on a filtered table with no cached index, seeks with `filter.nth(i)` then walks `filter.next(...)`. So a 50-row page over a 100k-row filtered table touches ~50 rows. Docs corroborate: "A new set of objects will be created, copying the backing table data." `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/table/Table.js + https://idl.uw.edu/arquero/api/table.html, 2025-05-29, accessed 2026-08-01, high, capability}`
14. **There is no row-object reuse or proxy mode on `Table.objects()` / iteration — every row is a freshly allocated object.** `objects` does `obj.push(createRow(row, data))` per row; `[Symbol.iterator]` yields `createRow(i)` per row. The builder function is memoized (`table._builder`), but the objects it produces are not pooled. Two allocation-free read paths exist instead: `*values(name)` (a generator yielding raw values via `getter(name)`, zero objects) and `array(name, constructor)` (extracts one column into a new plain or typed array). `{https://cdn.jsdelivr.net/npm/arquero@8.0.3/src/table/Table.js, 2025-05-29, accessed 2026-08-01, high, capability}`
15. **`[Symbol.iterator]` has no limit/offset and forces `indices()` on any filtered or ordered table.** `objectBuilder(table)` calls `table.indices()` when `isOrdered() || isFiltered()`, materializing and caching the 400 KB `Uint32Array`. Iterating for a preview is therefore more expensive than `objects({limit, offset})` on a filtered table. `{same source, high, capability}`
16. **Latest release is `arquero` 8.0.3, published 2025-05-29T22:24:12Z; sole `latest` dist-tag.** Preceding: 8.0.2 (2025-05-15), 8.0.1 (2025-02-17), 8.0.0 (2025-02-05). No 8.1 or 9.x exists as of access date. `{https://registry.npmjs.org/arquero, npm registry, 2025-05-29, accessed 2026-08-01, high, version}`
17. **Arrow support is bundled, not an optional peer: the only runtime dependencies are `acorn ^8.14.1` and `@uwdata/flechette ^2.0.0`, with no `peerDependencies`, `peerDependenciesMeta` or `optionalDependencies`.** `apache-arrow` is no longer a dependency of any kind. Every consumer pays the Flechette bundle cost — relevant to a single-file build. `{https://registry.npmjs.org/arquero/latest, npm registry, 2025-05-29, accessed 2026-08-01, high, version}`
18. **The last two releases contain no memory or performance work; the performance change is in 8.0.0.** 8.0.3 fixed CSV quote handling; 8.0.2 fixed cross-chunk quoted spans and "aggregate row count over filtered and ordered tables". 8.0.0 replaced `apache-arrow` with `@uwdata/flechette` "for improved performance and flexibility" and added full streaming readers (`fromCSVStream`, `fromArrowStream`, `fromJSONStream`, `fromFixedStream`) plus gzip/deflate — streaming ingestion being the one memory-relevant capability added. Caution: the release page rendered these dates a year early (2024); the npm registry timestamps in finding 16 are authoritative and were used. `{https://github.com/uwdata/arquero/releases, accessed 2026-08-01, medium, version}`

### Verb table: view or copy?

| Verb | Verdict | Evidence |
|---|---|---|
| `filter` | **Shares parent columns.** Adds `BitSet(totalRows)` = `Uint32Array(ceil(n/32))`, ~12.5 KB @ 100k. | `_filter` -> `new BitSet(n)` -> `table.create({ filter })`; `create` falls back to `this._data`. |
| `select` | **Shares parent columns.** Allocates only a new names array and a new `{name -> column}` object holding the *same* column references; filter and order carry over. | `_select` -> `cols.add(next, table.column(curr))` -> `cols.derive(table)` -> `proto.create(this)`. |
| `slice` | **Materializes new arrays** of the slice length. | `table.reify(indices)` (non-grouped) / `filter(...).reify()` (grouped). |
| `orderby` | **Shares parent columns.** Stores a comparator; a `Uint32Array(numRows)` sort index (~400 KB @ 100k) is built on first ordered access and cached on `_index` permanently. | `_orderby` -> `table.create({ order })`; `indices()` memoizes. |
| `derive` | **Shares existing columns; allocates one new `Array(totalRows)` per new column** — sized to the backing row count even on a filtered table. | `columnSet(table)` spreads `table.data()`; `names.map(name => cols.add(name, Array(total)))`, `total = table.totalRows()`. |
| `join` | **Materializes everything.** New `[]` per output column, plus `Uint32Array` indices for both inputs, two `Int32Array` hit vectors, and a hash lookup map. | `_join`: `cols.add(names[i], [])`, `indices(false)`, `new Int32Array(nL/nR)`, `indexLookup(...)`, `cols.new(tableL)`. |
| `concat` / `union` | **Materializes** `Array(nrows)` per column. Early-out returns the parent unchanged when row count is unaffected. | `concat.js`: `const arr = Array(nrows)`; `if (trows === nrows) return table`. |
| `groupby` | **Shares parent columns.** Adds `Uint32Array(totalRows)` group keys (~400 KB @ 100k) + a key index object + a `rows` array. Free path when grouping one unfiltered dictionary-backed column. | `_groupby` -> `table.create({ groups })`; `createGroups`: `new Uint32Array(nrows)`; `if (col.groups) return col.groups(names)`. |
| `rollup` | **Materializes, but only at group cardinality** — new columns of length `groups.size` (or 1). Does not copy row-level data. | `_rollup` -> `cols.add(names[i], Array(size))` -> `cols.new(table)`. |

### Leads worth chasing

- **`reify()` is the memory-release lever, and it is cheap to reason about.** After a selective filter, `reify()` on the survivor lets the 100k-row backing arrays be garbage-collected once no other descendant references them — while an unfiltered `reify()` costs literally nothing (`return this`). A pipeline that reifies after the first big filter converts a 1x-shared-plus-bitsets chain into a small independent table. The measurement track should test `filter -> reify -> drop source` vs `filter -> drop source`.
- **The retention trap to measure:** because `create()` shares `_data`, dropping the source table frees nothing while any derived table lives. Every `derive` in a chain also pins a `totalRows`-length array. A 6-step pipeline is roughly *1x base data + one full-length array per derived column + one bitset per filter + up to one 400 KB index per ordered/iterated table* — not 6x, but not free either.
- **Verify `derive`-on-filtered-table waste empirically** (finding 6). If a UI derives columns after filtering 100k -> 1k, each derived column still costs 100k slots. Reifying before deriving should collapse that; the single highest-leverage ordering rule the measurement track can validate.
- **`values(name)` and `array(name, TypedArray)`** are the zero-object read paths — likely the right primitives for rendering and for handing data to a chart library, rather than `objects()`.
- **`useProxy` on Arrow ingestion** appeared in search summaries as a zero-copy row/struct extraction option that reduces memory. No primary source reached for Arquero 8's Flechette-based `fromArrow`; unverified — check `src/format/from-arrow.js`.
- **`toJSON()`** — `src/format/to-json.js` was not read; its allocation profile is unestablished.
- **Bundle-size angle for the single-file build:** Flechette is a hard dependency (finding 17), so Arrow machinery ships whether or not the app reads Arrow. Worth checking whether tree-shaking removes it when only `aq.from` is used.

### What I looked for and could not find

- **No evidence retrieved either way on reported out-of-memory problems at scale.** One issue-tracker search returned mostly unrelated repositories; the only Arquero-repo hit was issue #89 ("Table view() with sortable columns and lazy browsing"), not opened. **Zero** verified data points on OOM reports, memory growth over long pipelines, or maintainer advice on releasing intermediates — and specifically no basis to say such reports are absent. Largest gap in the brief; a follow-up should query the issue tracker directly rather than via general web search.
- **`toJSON()` allocation behaviour is unestablished.**
- **No published benchmark or profile of Arquero memory at 100k x 20.** Every quantitative figure above (12.5 KB bitset, 400 KB index, 400 KB group keys) is **arithmetic derived from allocation sites in the source**, not a measured or second-sourced number. Under the two-source rule these are single-source, source-code-derived claims and should be treated as lower bounds on structural overhead, ignoring JS engine per-object and per-array-slot overhead.
- **No documentation of the `derive`-allocates-`totalRows` behaviour.** Visible only in the source; the API docs do not mention it. Similarly, `slice`'s materialization is not flagged in the docs read.
- **No release note in 8.x addresses memory directly** — the absence is itself finding (18); the only memory-adjacent 8.0.0 change is streaming ingestion.
