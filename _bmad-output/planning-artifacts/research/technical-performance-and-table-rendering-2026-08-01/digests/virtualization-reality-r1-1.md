# Digest — D1 / virtualization reality at scale — round 1, assistant 1

Brief: what breaks when virtualized tables run at 100k rows x 20-50 columns; horizontal
virtualization, variable row height, scroll-range limits, the hand-roll cost list,
engine differences. Budget: 4 sources, 10 tool calls. Returned 2026-08-01.

### Findings

1. **Firefox's maximum element/scroll dimension is 17,187,496 px** (width, height, scrollWidth, scrollHeight), caused by overflow of the internal fixed-point `nscoord` representation of a CSS pixel; the bug is still **NEW/unresolved, P5**, filed ~2019, last touched ~1 year ago. `{https://bugzilla.mozilla.org/show_bug.cgi?id=1527883, Mozilla Bugzilla, filed 2019 (status NEW, last update ~2025), accessed 2026-08-01, high, scale-limit}`
2. **A second, higher figure circulates for the CSS-height ceiling — Firefox 33,554,400 px and Chrome 33,554,428 px** — reported by a TanStack Virtual user who hit it rendering 1,677,723 items x 20 px. The two sources disagree on Firefox's number (17.1M vs 33.5M), which likely reflects *layout height* vs *scrollable extent* being different limits; treat 17.1M as the conservative planning figure. `{https://github.com/TanStack/virtual/issues/616, GitHub / TanStack, issue open, accessed 2026-08-01, medium, scale-limit}`
3. **At 100k rows this limit is not a live risk.** 100,000 x 32 px ~ 3.2M px, an order of magnitude below even the conservative 17.1M ceiling; the limit only bites above roughly 500k-1M rows (or ~170k rows at 100 px each against the Firefox figure). Derived arithmetic from findings 1-2, not from a source that states it for 100k specifically. `{derived from the two sources above, accessed 2026-08-01, high, scale-limit}`
4. **TanStack Virtual's max-height issue #616 is open with no shipped workaround**; a related PR (#1172) exists but the thread documents no scaling/compression of scroll space. So if you ever *do* exceed the ceiling, the library will not save you. `{https://github.com/TanStack/virtual/issues/616, GitHub, open, accessed 2026-08-01, high, capability}`
5. **Two-axis virtualization (rows AND columns) is where TanStack Virtual visibly degrades**: a reproducible report against Virtual 3.1.1 + Table 8.12.0 shows a **blank page during combined horizontal+vertical scroll**, with repeated browser console warnings that the scroll handler took too long. Issue is **open**, no maintainer diagnosis, no workaround in-thread. `{https://github.com/TanStack/virtual/issues/685, GitHub, open, accessed 2026-08-01, high, failure-mode}`
6. **Sticky/frozen columns fight column virtualization.** Making a column sticky via `rangeExtractor` causes columns to stop rendering once virtualization engages; the practitioner-recommended path is to render sticky header/column layers *outside* the virtualized grid using plain CSS `position: sticky` rather than relying on the virtualizer. Sticky headers/footers can also be scrolled past because of the total-size spacer container. `{https://github.com/TanStack/virtual/discussions/917 and .../discussions/872, GitHub discussions, accessed 2026-08-01, medium, failure-mode}`
7. **Dynamic row height's core failure is scroll-offset drift and jumping**, because correct offsets require every row above the viewport to have been measured — infeasible during fast drag-scrolling of a long list. Reported repeatedly: list "jumps around when scrolling stops" when heights are recomputed mid-scroll (react-virtualized #424), and `scrollToRow` lands in the wrong place with `CellMeasurer` when jumping from a larger to a smaller index (#995). These are older libraries; the *mechanism* is generic, the specific bugs are not current-version claims. `{https://github.com/bvaughn/react-virtualized/issues/424, https://github.com/bvaughn/react-virtualized/issues/995, GitHub, 2016-2018 era, accessed 2026-08-01, medium, failure-mode}`
8. **Scrolling upward into unmeasured rows is a distinct, separately-reported failure** from scrolling downward — estimated heights above the viewport get corrected on measurement, shifting content under the user. `{https://github.com/bvaughn/react-virtualized/issues/610, GitHub, accessed 2026-08-01, low (single thread, old), failure-mode}`
9. **Find-in-page is unfixable from userland — confirmed by a maintainer-team issue that has been open since Feb 2018 and never resolved.** Angular's own components repo states plainly "we can't detect native browser ctrl+f"; the issue is filed as a *design* task to help developers build their own Ctrl+F replacement, i.e. the framework's answer is "you write your own search UI." `{https://github.com/angular/components/issues/10127, GitHub / Angular, opened 2018-02-23, still open, accessed 2026-08-01, high, platform-behaviour}`
10. **The platform has no hook for this by design**: landmark navigation, find-in-page, and intra-page anchor navigation are driven solely by DOM structure, and virtualized content is by definition not in the DOM — this is the stated motivation of the WICG virtual-scroller explainer. `{https://wicg.github.io/virtual-scroller/, WICG, accessed 2026-08-01, high, platform-behaviour}`
11. **`content-visibility: auto` is not a drop-in alternative: its documented failure mode is scrollbar instability.** An element under size containment with no specified height computes to 0 height, so the scrollbar length shifts as content enters/leaves the viewport. One practitioner measured a **60% rendering improvement in Chrome** and still removed the property because the scrollbar flicker was unacceptable. `{https://adithya.dev/content-visibility-and-the-scrollbar-problem/, personal blog, 2021-03-12, accessed 2026-08-01, medium (single author, 5 years old), failure-mode}`
12. **`contain-intrinsic-size` is the prescribed fix but only trades the failure for an estimation problem** — values that don't closely match eventual rendered height still produce "dancing scrollbars," and you frequently cannot know the height in advance. `{https://blog.logrocket.com/using-css-content-visibility-boost-rendering-performance/ and https://www.bram.us/2020/12/21/content-visiblity-vs-jumpy-scrollbars-a-solution/, accessed 2026-08-01, medium, capability}`
13. **`content-visibility` and scroll-anchoring interact badly enough to be an active CSSWG spec issue** — "[css-contain][css-scroll-anchoring] Scroll into view adjustments for content-visibility: auto" (#9833), with list traffic through at least Feb 2025, meaning the platform-native path still has unsettled scroll-position semantics. `{https://lists.w3.org/Archives/Public/public-css-archive/2024Nov/1036.html, W3C public-css-archive, 2024-11 / 2025-02, accessed 2026-08-01, medium, platform-behaviour}`
14. **Crucially for a 100k x 50 grid, `content-visibility` does not reduce DOM node count** — it skips *rendering* of off-screen subtrees, not their creation. 100k rows x 20-50 columns is 2M-5M cell elements that must still be parsed, constructed, and held in memory. No source I found tested `content-visibility` at that node count; the property's own documentation frames it as a rendering-work optimization, not a DOM-size one. `{https://css-tricks.com/almanac/properties/c/content-visibility/ and https://www.debugbear.com/blog/content-visibility-api, accessed 2026-08-01, medium, capability}`

### The hand-roll cost list

Ordered by reported surprise, worst first.

| Concern | Verdict | Evidence |
|---|---|---|
| **Ctrl+F / find-in-page** | **Genuinely hard — actually impossible** | Not solvable in userland at any budget; you must ship your own find UI. Angular has had this open and unsolved since 2018 (#10127); WICG names it as a motivating platform gap. This is the single item most likely to be discovered *after* launch. |
| **Two-axis (row + column) virtualization** | **Genuinely hard** | Even the leading library visibly breaks here — blank frames, long scroll handlers (TanStack #685, open). Hand-rolling means solving what the library has not. |
| **Sticky / frozen first columns under column virtualization** | **Genuinely hard** | Sticky columns stop rendering when virtualization engages (#917); the working pattern is to lift sticky layers *out* of the virtualizer entirely (#872), i.e. two parallel rendering paths kept in sync. |
| **Variable / dynamic row height** | **Genuinely hard** | Correct offsets require measuring every row above the viewport; you get jumping on measure (#424), wrong `scrollToRow` targets (#995), and upward-scroll drift (#610). Fixed row height is the escape hatch — and I'd treat it as the default recommendation, not a compromise. |
| **Screen-reader semantics for absent rows** | **Real work** | Rows not in the DOM are not in the accessibility tree; content that scrolls out may not be rendered to AT, and Ctrl+End misbehaves. Requires manual `aria-rowcount`/`aria-rowindex` bookkeeping. Evidence is secondary-source (a11y write-ups), not a primary post-mortem — medium confidence. |
| **Scrollbar length stability** | **Real work** | Direct consequence of unmeasured content; the same defect that makes `content-visibility: auto` unusable for one practitioner despite a 60% render win. Solved cleanly *only* by fixed row heights. |
| **Scroll-position restore, deep-link to row** | **Real work** | Implied by the same measurement problem (`scrollToRow` inaccuracy, #995) plus the WICG note that fragment navigation doesn't work on virtualized content. |
| **Very large scroll range / spacer div** | **Cheap at your scale** | 100k x 32 px ~ 3.2M px vs a 17.1M px conservative ceiling. Only becomes real above ~500k rows or with very tall rows. Do not architect around it. |
| **Vertical windowing itself (fixed height)** | **Cheap** | Uncontested across every source; index math on a known row height is a small amount of code. |

Text selection across the window boundary, printing, and cell-range copy-paste: could not evidence this run — see below.

### Leads worth chasing

- **The two element-height limits contradict each other.** Bugzilla 1527883 says Firefox tops out at 17,187,496 px; the TanStack thread says 33,554,400 px. Both are plausibly true of *different* quantities (layout box height vs scroll extent, or pre/post-fix behaviour). Neither was verified against Firefox 153. If any decision depends on exceeding ~10M px, measure it directly in the target browsers rather than trusting either number.
- **`content-visibility` advocacy vs. practitioner retreat.** LogRocket/DebugBear-class posts present it as a near-free win; the one practitioner account with a measurement (60% faster) removed it anyway. The advocacy posts benchmark long article pages, not 5M-cell grids — the populations are not comparable, and nobody has published the grid case.
- **TanStack #685 has no maintainer diagnosis.** Worth checking whether it reproduces on the current Virtual/Table versions before treating "the library handles columns" as true; the report is against 3.1.1/8.12.0, which is old.
- **CSSWG #9833** is the thing to watch if betting on the platform rather than a library — the scroll-anchoring interaction is still being specified.

### What I looked for and could not find

- **Any current-version (2025-2026) benchmark of a virtualized table at 100k rows x 20-50 columns.** Every scale number retrieved concerns 1D lists or synthetic 1000x1000 grids. The specific shape in this decision is unbenchmarked in public.
- **Chromium vs Firefox behavioural differences in virtualized scrolling**, beyond the raw element-height ceilings. No source reported jank, anchoring, or `ResizeObserver` behaviour differing between engines; the one practitioner who tested cross-browser explicitly ruled browser out as a factor. Absence of reported divergence is weak evidence of parity, not proof.
- **A confirmed `ResizeObserver` loop-limit-exceeded report tied to a table virtualizer.** The mechanism is widely assumed; no primary thread demonstrating it was found. Do not repeat this as fact.
- **Post-mortems at the 6-12-month horizon.** Issue trackers and one blog retreat, but no "we hand-rolled windowing and here is what it cost us a year later" write-up. The hand-roll cost list above is assembled from library issues, which is a weaker basis than a genuine retrospective would be.
- **Text selection across the window boundary, printing a virtualized table, and cell-range copy/paste.** Zero sources retrieved.
- **Vue-specific evidence.** Everything retrieved is React/Angular. No Vue 3 virtualizer was covered by any source read — a notable gap given the stack.
- **Whether `contain-intrinsic-size: auto` resolves the scrollbar problem on current Chromium.** The sources predate it or don't test it; a cheap, checkable follow-up.
