- (claim) ref=[M-1] status=verified class=memory pub=2026-08-01 — MEASURED: deep reactive() over 100k rows x 20 cols inside a render effect adds 436.8 MB (@vue/reactivity 3.1.1) to 478.5 MB (3.5.40) on top of 159.7 MB of data — 3-4x the data itself — and slows a full read from ~105 ms to 1193-1411 ms (11-13x). - (claim) ref=[M-2] status=verified class=memory pub=2026-08-01 — MEASURED: Object.freeze() on the row objects is a complete escape hatch — 0 MB added, no proxy created for array or rows (array_is_proxy=false, row_is_proxy=false), traversal back to plain-object speed (90-116 ms), identically on @vue/reactivity 3.1.1 AND 3.5.40. - (claim) ref=[R2-1b] status=verified class=api pub=unknown — Alpine.data() supplies data only, never markup, and Alpine has no <component :is> equivalent: heterogeneous step editors must dispatch through x-if chains inside x-for, or x-html (docs: trusted content only). - (claim) ref=[R2-1d] status=verified class=pattern pub=2020-06-12 — Alpine discussion #570 is v2-era and its core claim ('re-renders the entire component on any data change') is superseded by Alpine 3's per-effect reactivity; last comment 2024-02-16 covers only x-listbox/x-combobox. Keying: :key is opt-in, and on re-render Alpine reuses keyed nodes and refreshes their scope in place, so wholesale array replacement preserves DOM and input focus when keys match.
- (claim) ref=[R2-2a] status=verified class=api pub=unknown — Vue's global build: no SFC, Composition API requires setup(), but template: strings and <script type=text/x-template> are exempt from the in-DOM template caveats (kebab-case, no self-closing tags). <component :is> accepts a component object directly, so a {kind -> component} dispatch map needs no global registration.
