# D3 — Ergonomics and implementation reality for a three-pane, heterogeneous-step-list UI (round 1, pass 1)

Scope reminder: single HTML file, opened locally (likely `file://`), no server, no build step, one developer.
Budget note: 9 tool calls spent, 4 sources read in full (Alpine discussion #749, vuejs.org Quick Start, petite-vue README, MDN `Element.moveBefore()`), plus 4 web searches whose result snippets are cited separately and at lower confidence because the underlying page was NOT opened this run.

## Claims

- [D3-1] class=api confidence=high — Vue used from a CDN cannot use Single-File Component syntax; the official Quick Start states verbatim "When using Vue from a CDN, there is no 'build step' involved. This makes the setup a lot simpler, and is suitable for enhancing static HTML or integrating with a backend framework. However, you won't be able to use the Single-File Component (SFC) syntax."
  source: https://vuejs.org/guide/quick-start | publisher: Vue.js official docs (vuejs.org) | published: unknown (page undated; documents Vue 3, current line) | accessed: 2026-08-01

- [D3-2] class=tooling confidence=high — Vue's ES-module CDN build is unusable for a file that is double-clicked from disk: the Quick Start states "Due to security reasons, ES modules can only work over the `http://` protocol" and cannot work over `file://`. Therefore a local-only single-file app must use the *global* build (`vue.global.js`, exposing APIs on `window.Vue`) inlined into the HTML, not `vue.esm-browser.js` + import maps. This is a hard constraint on the "one HTML file, opened locally" premise and it silently rules out the modern, most-documented Vue-without-build recipe.
  source: https://vuejs.org/guide/quick-start | publisher: Vue.js official docs | published: unknown | accessed: 2026-08-01

- [D3-3] class=tooling confidence=medium — The same page notes import maps are "only supported in Safari 16.4+", another reason the import-map recipe adds surface for no gain here. (Freshness caveat: this compatibility note is old relative to the ≤1-month bar; Safari 16.4 shipped years ago so the constraint is effectively moot today, but it shows the docs' CDN section is not actively refreshed.)
  source: https://vuejs.org/guide/quick-start | publisher: Vue.js official docs | published: unknown | accessed: 2026-08-01

- [D3-4] class=api confidence=medium — Vue's in-browser template compilation (in-DOM templates or JS template strings) is done at runtime and the docs advise it "is usually fast enough but is best avoided if your application is performance-sensitive". For a three-pane app with a preview table this is likely irrelevant (compilation happens once per component definition, not per row), but it is the documented cost of the no-build path.
  source: https://vuejs.org/guide/quick-start | publisher: Vue.js official docs, surfaced via search snippet — snippet-level only, the exact sentence was not located on the page I opened | published: unknown | accessed: 2026-08-01

- [D3-5] class=retrospective confidence=medium — Alpine's own repository hosts an explicitly-solicited "Pitfalls, honest draw backs of alpine.js" discussion in which the strongest scoping statements are: "If you're trying to build an SPA, Alpine is definitely not the right answer" and "complex tasks on that side of things are better suited to Vue, React, Svelte, etc." (ryangjchandler, 2020-09-04). Appropriate use cases given: server-rendered content, class toggling, replacing jQuery patterns. NOTE: this is a contributor/community statement in the Alpine repo, not a verbatim line from Caleb Porzio nor from alpinejs.dev docs; I did not verify ryangjchandler's formal role this run.
  source: https://github.com/alpinejs/alpine/discussions/749 | publisher: alpinejs/alpine GitHub Discussions | published: 2020-09-04 | accessed: 2026-08-01

- [D3-6] class=retrospective confidence=medium — Concrete Alpine failure mode reported in the same thread: heavy `x-html` use (translations) caused visible blinking because "every unrelated change triggers an update on all of the x-html"; the maintainer response was that Alpine "would need to implement dependency tracking or diff the DOM" to fix it (rhengles, 2020-09-05; filed as alpine issue #286). This is the architectural point that matters for a live preview table: Alpine re-evaluates expressions broadly rather than diffing, so a big re-rendered pane is a known weak spot. FRESHNESS FLAG: these posts are Alpine v2-era (2020), far outside the ≤2-year pattern bar; the thread does not confirm whether Alpine v3's reactivity engine fixed it. Treat as a hypothesis to re-verify against current Alpine, not as a current fact.
  source: https://github.com/alpinejs/alpine/discussions/749 | publisher: alpinejs/alpine GitHub Discussions | published: 2020-09-05 | accessed: 2026-08-01

- [D3-7] class=pattern confidence=medium — Also from that thread: Alpine performance degrades when state is held "over a massive DOM tree"; the recommended discipline is many small `x-data` scopes and never `x-data` on `<body>`/`<html>`. That discipline is in direct tension with this app's shape, where one pipeline-config object must be shared by the middle pane (step forms) and the right pane (preview) — i.e. the natural design is exactly one large root scope. Alpine's answer to that is `Alpine.store()`/`$store` (not evidenced this run — see gaps).
  source: https://github.com/alpinejs/alpine/discussions/749 | publisher: alpinejs/alpine GitHub Discussions | published: 2020-09-04 | accessed: 2026-08-01

- [D3-8] class=api confidence=high — petite-vue is DISQUALIFIED for this UI on its own README: it explicitly does not support "`v-is` or dynamic component binding", and also lacks `ref()`, `computed()`, render functions, and a virtual DOM. The five-heterogeneous-step-kinds requirement is precisely the dynamic-component case, so the wildcard that looks closest to "Vue without a build step" cannot express the core pattern.
  source: https://github.com/vuejs/petite-vue | publisher: vuejs/petite-vue (official Vue org) README | published: unknown (README undated) | accessed: 2026-08-01

- [D3-9] class=tooling confidence=high — petite-vue's own README says "This is pretty new. There are probably bugs and there might still be API changes, so use at your own risk", states the issue tracker is intentionally disabled, and that feature requests are unlikely to be accepted. For a solo maintainer betting on multi-year maintenance, that is a self-declared no-support posture from the vendor.
  source: https://github.com/vuejs/petite-vue | publisher: vuejs/petite-vue README | published: unknown | accessed: 2026-08-01

- [D3-10] class=api confidence=high — `Element.moveBefore(movedNode, referenceNode)` moves a node within the same parent while PRESERVING state that `insertBefore()` destroys: animation/transition state, `<iframe>` load state, `:focus`/`:active`, popover open state, `<dialog>` modal state, and media play state. This is the platform-native answer to "reorder a list of step cards without blowing away the form field the user was typing in".
  source: https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore | publisher: MDN | published: unknown (living doc) | accessed: 2026-08-01

- [D3-11] class=api confidence=high — BUT as of today MDN marks `moveBefore()` "Limited availability — Not Baseline", with the note "This feature is not Baseline because it does not work in some of the most widely-used browsers." Constraints: same-document only; cannot move a disconnected node into a connected parent; throws `HierarchyRequestError` otherwise. Verdict for this decision: usable as a progressive enhancement behind a `if ('moveBefore' in Element.prototype)` guard, NOT as the reordering strategy. Since the app is opened locally by a known user, browser support may be a settled question — worth pinning the actual per-browser table, which I did not retrieve.
  source: https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore | publisher: MDN | published: unknown (living doc, compat data updated continuously) | accessed: 2026-08-01

- [D3-12] class=pattern confidence=medium — The known drag-reorder-vs-framework-diffing conflict is real and documented in the Vue/SortableJS ecosystem: the failure is "two sources of truth" — the framework wants to own DOM order from the data array, SortableJS mutates DOM order directly on drop — producing "unpredictable behaviour" / "rearranged order not sticking after drop". Documented mitigations: put a stable content-derived `key` on children (array index as key "won't work"), key the parent on item count to force a clean re-init on add/remove, or use a wrapper (`vue-draggable`/`vuedraggable`, `sortablejs-vue3`, VueUse `useSortable`) that writes the drop back into the array and lets the framework re-render. There is an open VueUse issue titled "useSortable clashes with Vue reactivity" (#3727), i.e. the wrappers do not fully close the gap.
  source: https://github.com/eliottvincent/vue3-sortablejs + https://github.com/vueuse/vueuse/issues/3727 + https://github.com/SortableJS/Vue.Draggable/issues/56 | publisher: SortableJS / VueUse GitHub | published: unknown (issue #3727 date not retrieved) | accessed: 2026-08-01 | EVIDENCE GRADE: search-snippet only, pages not opened this run

- [D3-13] class=pattern confidence=low — Implication of D3-12 for the build: the lowest-risk reordering design for a five-kind step list under ANY of the candidates is to avoid library-driven DOM mutation entirely — either (a) up/down buttons plus keyboard shortcuts mutating the array (zero dependency, zero conflict, fully accessible, and the German UI can label them "Nach oben"/"Nach unten"), or (b) native HTML5 `dragstart`/`dragover`/`drop` handlers that only compute a target index and then splice the array, never touching the DOM. Both keep exactly one source of truth. This is my inference from D3-10/11/12, not a retrieved recommendation — verify against a current tutorial before treating as a finding.
  source: (inference from the above) | publisher: — | published: — | accessed: 2026-08-01

- [D3-14] class=retrospective confidence=low — I found no prominent, detailed account of someone building a nontrivial app in Alpine and later regretting it. The nearest real-world migration story runs the OTHER way: Fyle reports replacing Vue 2 with Alpine.js on a large static (Jekyll) site, calling it "one of our best decisions yet" with ~20% JS bundle reduction. That is a content-site/progressive-enhancement case, NOT a three-pane stateful editor, so it does not transfer to this decision — but it is evidence against the folklore that Alpine adopters uniformly regret it. Single-source, launch-flavoured, publisher is the adopting company (advocacy discount applies), and I did not open the post.
  source: https://stories.fylehq.com/p/how-we-replaced-vue-2-with-alpinejs | publisher: Fyle (company engineering blog) | published: unknown | accessed: 2026-08-01 | EVIDENCE GRADE: search-snippet only

- [D3-15] class=tooling confidence=low — UNVERIFIED BELIEF, flagged as such: Vue's full/CDN build compiles templates with `new Function()`, which a strict `script-src` CSP without `'unsafe-eval'` blocks, and Vue ships a separate CSP-safe build for that case. ## Leads

- alpinejs.dev official docs — the actual "Alpine is for sprinkles / reach for something else" statement, if it exists as a documented maintainer line rather than a 2020 contributor comment in a discussion thread. Check `alpinejs.dev/start-here`, the homepage tagline, and Caleb Porzio's conference talk "Say No To Complexity With AlpineJS" (gitnation.com/contents/say-no-to-complexity-with-alpinejs) for a datable, attributable quote. The brief's premise that "Alpine's own documentation is explicit about a complexity ceiling" is NOT yet evidenced.
- Alpine v3 reactivity: whether the `x-html`/broad-re-evaluation problem (D3-6) survives in v3, which is built on Vue's `@vue/reactivity`. Search the alpine repo for issue #286's current state and for v3 release notes. This is the single highest-value follow-up because it decides whether the main documented Alpine complaint is a live one or a fixed one.
- `Alpine.store()` / `$store` as the answer to cross-pane shared state (D3-7), and `x-model` binding into nested objects inside `x-for` (`x-model="step.config.operator"`) — does two-way binding through an `x-for` iteration variable write back to the source array? This is the exact make-or-break API question for Alpine on this UI and I have no evidence either way.
- Vue's `<component :is>` with the global build: how a component "template" is authored without SFCs — template strings in JS, `<template id="...">` + `template: '#step-filter'`, or in-DOM templates — and what the DX cost is (no syntax highlighting, no type checking, HTML-in-string escaping). Also whether `defineComponent` objects registered globally survive the `vue.global.js` path cleanly.
- The unexplored wildcards: Svelte 5 (requires a compiler → almost certainly disqualified by "no build step" unless a REPL-compiled bundle is inlined), Lit (works from CDN, but check whether decorators/TS are required or whether plain-JS static-properties authoring is documented), Preact+htm (the canonical no-build combo — `htm` exists specifically to remove JSX's build requirement; strongest untested candidate for this brief), VanJS. Preact+htm deserves its own pass.
- MDN/BCD browser-compatibility table for `moveBefore()` — pin actual versions and dates, and check `caniuse`/webstatus.dev for the Baseline date. Also check whether any framework (Vue) has adopted `moveBefore()` internally for keyed-list moves.
- Retrospective search surfaces not yet tried: Hacker News threads ("Show HN" follow-ups), r/vuejs and r/laravel ("we used Alpine for a year"), and Caleb Porzio's own blog. Query shapes that might work: "Alpine.js two years later", "why we moved off Alpine".
