# Round 2 digest — Alpine API viability, build-less authoring ergonomics, live-preview architecture

## Claims

- [R2-1] class=api confidence=high — `x-for` builds each iteration's scope by assigning the *item itself* (`scopeVariables[iteratorNames.item] = item`) into a fresh plain object which is then wrapped with `reactive()`, so the iteration variable is a reference to the array element, not a copy — meaning `x-model="step.config.value"` writes through to the object stored in the source array (writes to a *primitive* iteration variable, e.g. `x-model="color"` over `['Red',…]`, hit only the per-iteration scope and would NOT reach the array).
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/alpinejs/src/directives/x-for.js | publisher: alpinejs/alpine (main branch source) | published: unknown (current main, read 2026-08-01) | accessed: 2026-08-01
- [R2-2] class=api confidence=medium — Alpine has no documentation or test asserting two-way binding through an `x-for` iteration variable: the whole `x-model` docs page never mentions `x-for` except for populating `<option>` lists, and the Cypress `x-model` spec's only `x-for` tests are select/option rendering (`x-model initializes single select values rendered with x-for`, `x-model re-syncs select value after x-for re-renders options`) — the write-back conclusion in [R2-1] rests on reading the implementation, not on a maintainer statement.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/tests/cypress/integration/directives/x-model.spec.js | publisher: alpinejs/alpine | published: unknown (current main) | accessed: 2026-08-01
- [R2-3] class=api confidence=high — On re-render `x-for` does not rebuild matched elements: it looks up an existing element by key and calls `el._x_refreshXForScope(scope)`, which mutates the existing reactive scope in place (`scope[key] = value`); only unmatched keys get a fresh clone with `reactive(scope)` + `addScopeToNode`. Consequence for the step list: replacing the steps array wholesale preserves DOM nodes, focus and input state for every step whose `:key` is unchanged.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/alpinejs/src/directives/x-for.js | publisher: alpinejs/alpine | published: unknown (current main) | accessed: 2026-08-01
- [R2-4] class=api confidence=high — The `x-for` docs state keys are opt-in via `:key` and that "Without dynamic keys, Alpine may have a hard time keeping track of what re-orders and will cause odd side-effects"; `:key` may be bound to the index explicitly. The test suite corroborates: `adding key attribute moves dom nodes properly`, `can key by index`, `x-for handles moved elements correctly`, `x-for throws descriptive error when key is undefined`.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/docs/src/en/directives/for.md + .../tests/cypress/integration/directives/x-for.spec.js | publisher: alpinejs/alpine | published: unknown (current main) | accessed: 2026-08-01
- [R2-5] class=retrospective confidence=high — Discussion #570 is dated 2020-06-12 (Alpine v2 era). The substantive answer, from contributor ryangjchandler the same day, gives three causes: no virtual DOM, "Alpine re-renders an entire component when any piece of data changes", and `:key` lookup overhead in `x-for` which he defends as worth it because it preserves per-element state. Only two later comments exist: a 2024-01-10 suggestion to write a TanStack-Virtual-style plugin, and a 2024-02-16 note from calebporzio (collaborator) that a merged PR "drastically" improved large-list keyboard-navigation performance for the x-listbox/x-combobox components.
    source: https://github.com/alpinejs/alpine/discussions/570 | publisher: alpinejs/alpine (GitHub Discussions, via GraphQL API) | published: 2020-06-12 (last comment 2024-02-16) | accessed: 2026-08-01
- [R2-6] class=api confidence=high — The central claim of #570 is stale for 3.15.x: Alpine 3's own Reactivity page documents per-effect granular reactivity built on `Alpine.reactive()` + `Alpine.effect()` ("Alpine uses VueJS's reactivity engine under the hood"), where an effect re-runs only when data it touched changes — not whole-component re-rendering. Treat #570's perf numbers as v2 history, not as a 3.x measurement; there is no 3.x-era `x-for` perf statement in the thread.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/docs/src/en/advanced/reactivity.md | publisher: alpinejs/alpine docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-7] class=pattern confidence=high — `Alpine.data()` supplies *data only*, never markup: it registers a named factory reusable as `x-data="dropdown"` or parameterised as `x-data="dropdown(true)"`, with `init()`/`destroy()` lifecycle, and the only markup-sharing mechanism offered is `x-bind` objects that bundle *directives* onto an existing element (`x-bind="trigger"` → `{ ['@click']() {...} }`). There is no `<component :is>` equivalent and no template-per-component concept anywhere in the globals docs.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/docs/src/en/globals/alpine-data.md | publisher: alpinejs/alpine docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-8] class=pattern confidence=medium — Therefore a list of heterogeneous step editors must dispatch markup by one of exactly two documented means: a chain of `<template x-if>` blocks inside the `x-for` (the docs show `x-if` nested in `x-for` and the test suite has `renders children in the right order when combined with x-if` and `correctly renders x-if children when reordered`), or `x-html` with a template string — for which the docs carry a standing warning: "Only use on trusted content and never on user-provided content." Per-step behaviour can still be factored into `Alpine.data('stepEditor', …)` bound as `x-data` inside the loop; only the markup cannot. This is an absence-based conclusion (no doc offers a third mechanism), hence medium.
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/docs/src/en/directives/html.md + .../directives/for.md | publisher: alpinejs/alpine docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-9] class=api confidence=high — `Alpine.store()` provides exactly: named global state registered inside an `alpine:init` listener (script-tag case), reactive access from any expression via `$store.name`, mutation from expressions, external access via `Alpine.store('name')` with no second argument, an optional `init()` run right after registration, and single-value (non-object) stores. It is a flat namespace of named values — the docs show no scoping, no modules, no subscription/watch API on the store itself, and no serialization or persistence (persistence is a separate plugin, not part of this page).
    source: https://raw.githubusercontent.com/alpinejs/alpine/main/packages/docs/src/en/globals/alpine-store.md | publisher: alpinejs/alpine docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-10] class=tooling confidence=high — Vue's own quick-start states plainly that with the CDN/global build "there is no build step involved… However, you won't be able to use the Single-File Component (SFC) syntax", and that Composition API without a build step must use the `setup()` option rather than `<script setup>`. The global build exposes all top-level APIs on the `Vue` object (`const { createApp, ref } = Vue`).
    source: https://raw.githubusercontent.com/vuejs/docs/main/src/guide/quick-start.md | publisher: vuejs/docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-11] class=tooling confidence=high — Vue's docs name three build-less template sources that are *exempt* from in-DOM parsing caveats — SFCs, inlined template strings (`template: '...'`), and `<script type="text/x-template">` — and enumerate the caveats that apply if you instead write templates in the DOM: PascalCase component names and camelCase props/events must be written kebab-case, self-closing component tags are illegal (`<my-component></my-component>` required), and `<ul>`/`<table>`/`<select>` impose element-placement restrictions. So the recommended build-less authoring shape is per-component `template:` strings or `<script type="text/x-template">` blocks, not in-DOM templates.
    source: https://raw.githubusercontent.com/vuejs/docs/main/src/guide/essentials/component-basics.md | publisher: vuejs/docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-12] class=api confidence=high — `<component :is="…">` accepts "the name string of a registered component, OR the actual imported component object", and the Composition-API variant of the docs' own tabbed-interface example is `<component :is="tabs[currentTab]"></component>` — i.e. a plain object map from key to component. In the global build this needs no registration step: a `{ filterStep: {...}, renameStep: {...} }` map indexed by `step.type` is exactly the documented pattern for a heterogeneous step list.
    source: https://raw.githubusercontent.com/vuejs/docs/main/src/guide/essentials/component-basics.md | publisher: vuejs/docs | published: unknown (current main) | accessed: 2026-08-01
- [R2-13] class=tooling confidence=medium — htm's README documents component interpolation as `<${Foo}>` "instead of `<Foo>` (where `Foo` is a component reference)", with explicit end-tags `<//>`, and its standalone Preact example is served from a single `<script type="module">` importing `htm/preact/standalone.module.js`. The only list example in the README is homogeneous (`todos.map(todo => html\`…\`)`); no official example dispatches a list to *different* components, so the `<${map[step.type]}>` shape is an inference from the documented interpolation slot, not a documented pattern.
    source: https://raw.githubusercontent.com/developit/htm/master/README.md | publisher: developit/htm | published: unknown (master branch, read 2026-08-01) | accessed: 2026-08-01
- [R2-14] class=maintenance confidence=high — htm is dormant, not archived: latest npm release 3.1.1 published 2022-04-26 (registry `modified` 2022-10-11), latest GitHub release also 3.1.1 (2022-04-26), last push to the repository 2024-02-01, 49 open issues, ~9.0k stars, `archived: false`. Four years without a release and ~2.5 years without a commit — legitimate for a 1.3 KB finished library, but it means no upstream fix path if a defect surfaces.
    source: https://registry.npmjs.org/htm + https://api.github.com/repos/developit/htm (releases + repo metadata) | publisher: npm registry / GitHub API | published: 3.1.1 = 2022-04-26; repo pushed_at = 2024-02-01 | accessed: 2026-08-01
- [R2-15] class=retrospective confidence=medium — No practitioner evidence was found for the client-side live-preview recompute question. A web search for pipeline-UI incremental recomputation returns exclusively server-side/big-data material (Databricks materialized-view refresh, Spark Declarative Pipelines, Dataform, Azure Data Factory, Palantir Foundry) whose economics — cluster cost, partition pruning, change tracking — do not transfer to a single-page in-memory tool. The one conceptually adjacent hit, Jane Street's Incremental library, is a general incremental-computation library described as applicable to UIs, and it surfaced only via an aggregator blog, not a primary source read this run.
    source: https://www.databricks.com/blog/optimizing-materialized-views-recomputes ; https://www.palantir.com/docs/foundry/building-pipelines/incremental-overview ; https://nexbit.art/blog/incremental-jane-street-library | publisher: Databricks / Palantir / nexbit.art (aggregator) | published: unknown | accessed: 2026-08-01

## Leads

- Jane Street `Incremental` (and its JS-adjacent descendants) as a *conceptual* frame for per-step memoization; primary source would be janestreet/incremental docs or the Jane Street Tech Blog, not the aggregator post above. Unread this run.
- Alpine's `x-for` `_x_refreshXForScope` mechanism ([R2-3]) is worth a 20-line spike: build a 3-step list with `:key="step.id"`, focus an input, replace `steps` wholesale, confirm focus and caret survive. That single experiment also empirically settles [R2-1]/[R2-2] write-back, which no document asserts.
- Alpine plugin `x-listbox`/`x-combobox` perf PR referenced by calebporzio 2024-02-16 in #570 — if large source lists ever matter, that PR is where the current large-list technique lives.
- Vue `<script type="text/x-template">` ([R2-11]) is the one build-less authoring shape that keeps templates as HTML in the document (so editor syntax highlighting works) while staying exempt from in-DOM parsing caveats — worth checking whether it survives being inlined in a single self-contained file with no external fetch.
- htm's `babel-plugin-transform-jsx-to-htm` exists (tag seen 2021-07-09) — relevant only if the project ever adds a build step; irrelevant to the file:// constraint.

## Looked for and could not find

- Any Alpine documentation page, maintainer comment, or test asserting that `x-model` on a property of an `x-for` iteration variable writes back to the source array. The `x-model` docs page does not discuss `x-for` at all beyond option lists; the `x-model` Cypress spec has no such test. [R2-1] is therefore implementation-derived and should be spike-verified before it is load-bearing.
- Any Alpine equivalent of `<component :is>` / dynamic template selection. The docs' globals, directives and advanced sections offer no third mechanism beyond `x-if` chains and `x-html`.
- Any statement in discussion #570 — or any newer maintainer statement located this run — about `x-for` performance in Alpine 3.x specifically. The thread's technical content is entirely v2-era.
- An official htm example of a heterogeneous list dispatching to different components.
- Any practitioner retrospective (blog, conference talk, issue thread) from a comparable *client-side* step-list/live-preview tool comparing whole-pipeline recompute against per-step memoization, or describing where either goes wrong. Absence is the finding; the search surface is dominated by server-side ETL vendors.
