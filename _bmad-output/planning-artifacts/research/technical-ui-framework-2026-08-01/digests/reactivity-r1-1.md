# D2 — Reactivity model under large data (r1-1)

Scope: what a UI layer's reactivity system does to a 100k-row array of plain objects held in memory, for Vue 3 / Alpine.js / vanilla. Research run 2026-08-01. Budget: 10 tool calls, 5 sources actually read (2 of them primary source code / package metadata).

## Claims

- [D2-1] class=performance confidence=high — Vue 3's reactivity is deep by default and every property access goes through a proxy trap that performs dependency tracking; Vue's own docs state this "becomes noticeable when dealing with large arrays of deeply nested objects, where a single render needs to access 100,000+ properties."
  source: https://vuejs.org/guide/best-practices/performance.html | publisher: Vue.js official documentation | published: unknown (no date on page) | accessed: 2026-08-01

- [D2-2] class=api confidence=high — Vue's officially documented escape hatch for exactly this case is `shallowRef()` / `shallowReactive()`: "Shallow APIs create state that is reactive only at the root level, and expose all nested objects untouched. This keeps nested property access fast, with the trade-off being that we must now treat all nested objects as immutable, and updates can only be triggered by replacing the root state." The doc's own example is literally `shallowRef([/* big list of deep objects */])`. This is the idiomatic hatch for "hold a big frozen dataset, render a window of it".
  source: https://vuejs.org/guide/best-practices/performance.html | publisher: Vue.js official documentation | published: unknown | accessed: 2026-08-01

- [D2-3] class=api confidence=high — The documented footgun of `shallowRef` is mutation semantics, not memory: `shallowArray.value.push(newObject)` does NOT trigger updates; `shallowArray.value = [...shallowArray.value, newObject]` does. Likewise `shallowArray.value[0].foo = 1` does not trigger; replacing the root with a spread-copied element does. For a pipeline tool where each step recomputes a fresh Arquero result array, this is a natural fit — every step edit produces a new root array anyway.
  source: https://vuejs.org/guide/best-practices/performance.html | publisher: Vue.js official documentation | published: unknown | accessed: 2026-08-01

- [D2-4] class=api confidence=medium — Vue's performance page names `v-once` (sub-tree skipped for all future updates) and `v-memo` (conditionally skip update of large sub-trees or `v-for` lists) as the render-skipping hatches, and separately recommends list virtualization (vue-virtual-scroller, vue-virtual-scroll-grid, vueuc/VVirtualList) as the fix for "one of the most common performance issues... rendering large lists". Note the docs frame virtualization as the primary answer to big lists, and shallow reactivity as the answer to big *state* — they are complementary, not alternatives. Confidence medium only because the page carries no date and I could not confirm which Vue minor it documents.
  source: https://vuejs.org/guide/best-practices/performance.html | publisher: Vue.js official documentation | published: unknown | accessed: 2026-08-01

- [D2-5] class=api confidence=medium — `shallowReactive` has had at least one real regression where shallowness leaked: vuejs/core#11869 (opened 2024-09-09, Vue 3.5.3) reported that array items from a `shallowReactive` array were converted to *fully reactive* objects during `v-for` rendering. Maintainers labelled it `p4-important` ("violates documented behavior / significant perf impact") and a regression; it was closed by PR #11870, so it is fixed in a release after 3.5.3. Cited as evidence that the shallow guarantee is a real, tested contract that has been broken and repaired — not as a live defect.
  source: https://github.com/vuejs/core/issues/11869 | publisher: vuejs/core issue tracker | published: 2024-09-09 (opened) | accessed: 2026-08-01

- [D2-6] class=version confidence=high — Alpine.js current release is **3.15.12, published 2026-04-30** (npm dist-tags latest). Author Caleb Porzio, repo alpinejs/alpine.
  source: https://registry.npmjs.org/alpinejs/latest | publisher: npm registry (primary package metadata) | published: 2026-04-30 | accessed: 2026-08-01

- [D2-7] class=version confidence=high — **Alpine does build on `@vue/reactivity`, and pins it at `~3.1.1`.** The `dependencies` field of alpinejs@3.15.12 is exactly `{"@vue/reactivity": "~3.1.1"}`. Vue 3.1.1 is a mid-2021 release, so Alpine 3.15.12 (2026) ships reactivity internals roughly five years behind Vue 3's current core. Any reactivity-performance improvement landed in Vue 3.2/3.4/3.5 is therefore NOT in Alpine.
  source: https://registry.npmjs.org/alpinejs/latest | publisher: npm registry (primary package metadata) | published: 2026-04-30 | accessed: 2026-08-01

- [D2-8] class=api confidence=high — Verified against the shipped bundle (`unpkg.com/alpinejs@3.15.12/dist/module.esm.js`, 106,351 bytes, `version: "3.15.12"`): the @vue/reactivity code is inlined, and Alpine wires it up at line 3516 with
  `alpine_default.setReactivityEngine({ reactive: reactive2, effect: effect2, release: stop, raw: toRaw });`
  So Alpine's reactive primitive is Vue's `reactive()` (deep, `createReactiveObject(..., mutableHandlers, ...)`) and its `raw` is Vue's `toRaw`. There is **no `shallowReactive` and no `markRaw` in the bundle's exported surface** — a `sed` extraction of a `shallowReactive` function definition came back empty, and the Alpine public API object contains `reactive`, `raw`, `effect`, `store`, `data`, `bind`, `watch`, `mergeProxies`, `setReactivityEngine`, `nextTick` etc., but no shallow/markRaw entry.
  source: https://unpkg.com/alpinejs@3.15.12/dist/module.esm.js | publisher: Alpine.js dist bundle (primary source) | published: 2026-04-30 | accessed: 2026-08-01

- [D2-9] class=api confidence=high — **Alpine DOES have a usable escape hatch, inherited from the bundled @vue/reactivity, even though it is undocumented at the Alpine level.** In the bundle, lines 2461–2465:
  `function getTargetType(value) { return value["__v_skip"] || !Object.isExtensible(value) ? 0 /* INVALID */ : targetTypeMap(toRawType(value)); }`
  and `createReactiveObject` bails out returning the raw target when targetType is INVALID (line 2499). Consequences, both testable in five lines:
  (a) setting `obj.__v_skip = true` (i.e. hand-rolled `markRaw`) keeps the object un-proxied;
  (b) **`Object.freeze()` or `Object.preventExtensions()` on an object makes it non-extensible, so Alpine/Vue reactive() returns it untouched — no proxy is ever created for it.** Since Vue-style `reactive()` converts nested objects *lazily on property get*, freezing the row objects (or the array) keeps 100k rows entirely outside the proxy system while still living inside `x-data`. Alpine's own code also honours `__v_skip` independently at line 374.
  source: https://unpkg.com/alpinejs@3.15.12/dist/module.esm.js | publisher: Alpine.js dist bundle (primary source) | published: 2026-04-30 | accessed: 2026-08-01

- [D2-10] class=api confidence=high — Alpine additionally exposes `Alpine.setReactivityEngine({reactive, effect, release, raw})` as public API (present in the exported Alpine object and used by Alpine itself at line 3516). This means the whole reactivity engine is swappable: a single-file app could inject a modern `@vue/reactivity` (gaining `shallowReactive`/`markRaw`), or a deliberately dumb engine, without patching Alpine. This is an under-appreciated hatch and materially changes the "Alpine has no escape hatch, so it fails the hard requirement" hypothesis.
  source: https://unpkg.com/alpinejs@3.15.12/dist/module.esm.js | publisher: Alpine.js dist bundle (primary source) | published: 2026-04-30 | accessed: 2026-08-01

- [D2-11] class=memory confidence=medium — Independent measurement of Vue-style proxy memory, run against Alpine's data stack: **1,000,000 proxies cost 449.75 MB, i.e. 471.6 bytes per proxy**, reduced to 110.75 MB (116.1 bytes/proxy) after the author's optimisation PR — "~75% reduction". Speed deltas from the same run: depth-10 / 1M iterations 1.20x faster on Node and Deno, 1.49x on Bun; depth-26 / 100k iterations 1.32x (Node/Deno), 1.42x (Bun). Methodology: proxies created from object stacks of depth 10 and 26, then all keys accessed 1M / 100k times, across Node (V8), Deno (V8), Bun (JSC). **Weak-evidence flags: no publication date on the page, no engine version numbers, no machine spec, and the author states no raw timing data was retained.** Treat the 471.6 bytes/proxy figure as an order-of-magnitude anchor, not a precise constant.
  source: https://awesomealpine.com/posts/alpine-performance-part-1/ | publisher: AwesomeAlpine (community, independent of Alpine core) | published: unknown (article references a PR from "September of previous year") | accessed: 2026-08-01

- [D2-12] class=memory confidence=medium — **Direct consequence for this project, arithmetic mine from D2-11.** The brief measures ~471 bytes per data row and 235 MB for five 100k-row sources. The independently measured proxy overhead is ~471.6 bytes *per proxy*. Deep-proxying 500k row objects would therefore add roughly the same order of magnitude again (~236 MB) purely in proxy bookkeeping — before counting one proxy per nested value — plausibly doubling heap to ~470 MB. The coincidence that both numbers are ~471 bytes is exactly that, a coincidence, but it makes the ratio easy to state: **naive deep reactivity roughly doubles the heap for this dataset.** Confidence medium: the per-proxy figure carries the weak-methodology flags of D2-11, and I did not measure this workload.
  source: https://awesomealpine.com/posts/alpine-performance-part-1/ | publisher: AwesomeAlpine | published: unknown | accessed: 2026-08-01

- [D2-13] class=performance confidence=low — Secondary, UNREAD (search-snippet only, no methodology, no version, no machine): a DEV Community post claims that assigning a large array to `ref()` makes Vue "recursively walk through every single object and nested property, wrapping them in ES6 Proxies", such that a 50,000-item array of 10-property objects yields "500,000 Proxies", and "a 5MB JSON payload can easily balloon into 50MB of reactive overhead in RAM". The 10x-blowup figure is unsourced and I did not read the article — recorded only because it is directionally consistent with D2-11/D2-12, NOT as an independent confirmation.
  source: https://dev.to/ameer-pk/the-vue-3-reactivity-trap-why-large-datasets-crash-your-browser-1ikb | publisher: DEV Community (self-published) | published: unknown | accessed: 2026-08-01 (via search snippet only)

- [D2-14] class=pattern confidence=medium — Vue's docs treat "keep the full result out of the DOM and render only a window" as the standard answer to large lists (virtualization: only items in or close to the viewport are rendered), and treat shallow reactivity as a separate axis. Mapped onto the three-pane design: the preview table should be a windowed render over a shallow/frozen result array, and the pipeline-step list (tens of items, deeply mutable) can stay fully reactive without cost. Confidence medium — this is the docs' recommendation applied to this architecture by me, not an account of someone shipping this exact tool.
  source: https://vuejs.org/guide/best-practices/performance.html | publisher: Vue.js official documentation | published: unknown | accessed: 2026-08-01

- [D2-15] class=pattern confidence=low — On the vanilla baseline, the retrieved evidence is thin. Search surfaced hand-rolled virtual scrolling as a routinely-solved vanilla problem (a from-scratch implementation "in less than 150 lines of code"; a dependency-free library claiming to scale past 1,000,000 items using phantom height + DOM recycling), and a js-framework-benchmark data point placing hand-written vanilla at a weighted geometric mean of ~1.03 with a minimal framework at ~1.06. I did NOT read these pages — titles and snippets only — so this is a lead, not a finding. The one defensible reading: windowed table rendering is ~150 lines of vanilla, and the framework-vs-vanilla gap on the standard benchmark is small for the fastest frameworks.
  source: https://stackfull.dev/implementing-virtual-scroll-for-web-from-scratch-in-less-than-150-lines-of-code (and https://www.html-code-generator.com/javascript/virtual-scrolling, https://dev.to/yanivsuzana/how-i-built-a-js-framework-that-beats-vanilla-js-in-row-selection-performance-5e6e) | publisher: mixed community | published: unknown | accessed: 2026-08-01 (search snippets only, unread)

- [D2-16] class=pattern confidence=low — Alpine-specific large-list pain is acknowledged in Alpine's own discussion tracker: "Possible to improve x-for performance with large lists?" (alpinejs/alpine discussion #570) and "[Question] Using Objects in x-data and dealing with Proxies" (issue #206) both exist; a community tips page notes `x-show` vs `x-if` can swing performance either way and advises trying both. Titles/snippets only — I did not read these threads and cannot report their resolutions or whether they are current against 3.15.x.
  source: https://github.com/alpinejs/alpine/discussions/570 (also https://github.com/alpinejs/alpine/issues/206, https://codewithhugo.com/alpine-tips/) | publisher: alpinejs/alpine issue tracker + community | published: unknown | accessed: 2026-08-01 (search snippets only, unread)

## Leads

- **Highest-value unread thread**: alpinejs/alpine discussion #570 ("Possible to improve x-for performance with large lists?") — read it for whether maintainers offer an official large-list stance, and whether it predates 3.15.
- **Verify D2-9 by experiment, it is cheap and decisive**: in a scratch HTML file, put `Object.freeze`-d row objects into `x-data`, then check `Alpine.raw(obj) === obj` and whether `x-for` over the frozen array still renders. Ten minutes of work settles the Alpine question harder than any further searching. Same test for `__v_skip`.
- **Test D2-10**: swap Alpine's engine via `Alpine.setReactivityEngine` with a current `@vue/reactivity` build and confirm `shallowReactive` becomes available — this would give Alpine full parity with Vue's documented hatch.
- **Quantify the real risk directly**: the honest measurement for this decision is not a blog benchmark but `performance.memory` / a heap snapshot before and after wrapping one 100k Arquero output in `reactive()` vs `shallowRef(Object.freeze(...))`, in the actual target browser.
- Check whether Vue 3.5's reactivity rewrite (widely reported to cut reactivity memory substantially) changes D2-1's cost model — and note it does NOT help Alpine, which is pinned to 3.1.1 (D2-7).
- The AwesomeAlpine optimisation PR referenced in D2-11: find whether it merged and in which Alpine version, i.e. whether the 471.6 → 116.1 bytes/proxy improvement is in 3.15.12 today. If merged, D2-12's "doubles the heap" estimate should be revised down ~4x.
- js-framework-benchmark (krausest) official results table — the one dated, methodologically-stated framework-vs-vanilla comparison for table-ish UIs. Not fetched this run.
- No evidence gathered at all on petite-vue, Preact+htm, Svelte 5 signals, Lit, or VanJS under large data. Svelte 5 runes and VanJS both make explicit claims about avoiding proxy overhead that a second round should test.

## Looked for and could not find

- **A dated, methodology-stated benchmark of Vue 3 `reactive()` vs `shallowRef()` on a 100k-row array in a browser.** Searched "Vue 3 reactive large array 100000 performance shallowRef"; results were DEV Community explainers and a php.cn FAQ mirror — no measured browser numbers with version/machine. The best measured artefact I found (D2-11) is Node/Deno/Bun, not a browser, and undated.
- **Any Vue documentation page giving concrete numbers** (ms, MB, row counts) for reactivity overhead. The official performance page is qualitative throughout — its only quantity is the rhetorical "100,000+ properties" per render. Vendor docs therefore cannot ground a memory budget; independent measurement must.
- **Any Alpine.js documentation of an escape hatch.** Alpine's docs surface has `Alpine.raw` (magics/data was in results) but I found no Alpine-authored page on large-data reactivity, no documented `markRaw`/`shallowReactive` equivalent, and no guidance on keeping an array out of `x-data`'s reactive scope. The hatch in D2-9 is real but is an implementation detail of the bundled @vue/reactivity, undocumented by Alpine — meaning it is unsupported and could in principle break on an Alpine dependency bump.
- **Publication dates.** Neither the Vue performance docs page nor the AwesomeAlpine benchmark carries a visible date. Both are outside the freshness bars as a result and are cited with that flag.
- **Practitioner retrospectives on the step-list-with-live-preview architecture** (recompute-whole-pipeline vs memoize-per-step, where it goes wrong in production). Not searched — budget exhausted at 10 tool calls before reaching Q5. This is the single largest untouched question in my dimension.
- **Whether Alpine's `x-for` diffs by identity or index on a replaced array**, which determines whether replacing a frozen 100k array re-creates 50 DOM rows or churns more. Unresolved.
