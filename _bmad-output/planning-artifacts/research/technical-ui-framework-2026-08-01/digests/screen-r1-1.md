# Wildcard screen — round 1, researcher 1

Scope: screen Preact+htm, Lit, Svelte 5, VanJS against G1–G5 for a single-file, `file://`-opened, 100k-row data-transformation tool. petite-vue already CUT elsewhere (not re-researched).

## Screen verdict

| candidate | verdict | deciding gate/capability | evidence ref |
|---|---|---|---|
| **Preact + htm** | **ADVANCE** | G2 passes on a real, shipped UMD: `htm/preact/standalone.umd.js` is a classic script exposing global `htmPreact` and bundling preact core + hooks + htm in one 13,296 B file. No proxy layer anywhere in Preact, so 100k rows held in `useRef`/module scope are structurally outside reactivity (G5). | [D5-1] [D5-2] [D5-3] [D5-8] |
| **Lit** | **CUT** | G2. `lit@3.3.3` is `"type": "module"` and neither `lit`, `lit-html@3.3.1` nor `@lit/reactive-element@2.1.1` contains a single UMD/IIFE/global/bundle file; the docs require bare-specifier resolution, i.e. a bundler. It cannot be inlined as a classic script from any published artifact. | [D5-4] [D5-5] |
| **Svelte 5** | **CUT** | G1/G2 build path unverified. Svelte 5's public `CompileOptions` no longer exposes a `format`/`iife` option — the compiler emits ES modules only, so a classic script requires a bundler-level `output.format: 'iife'` plus an inliner, a chain I could not evidence end-to-end this run. Reversible on a working prototype. | [D5-6] [D5-7] [D5-9] |
| **VanJS** | **ADVANCE (weak)** | G2 passes on a first-party, version-matched non-module build (`van-1.6.1.nomodule.min.js`, documented for exactly the "no ES6 modules" case). Reactivity is explicit `van.state` containers, never a proxy over data, so G5 is free. Weak because the heterogeneous-list pattern likely needs the separate VanX extension and the bus factor is one person. | [D5-10] [D5-11] [D5-12] [D5-13] |

## Claims

- [D5-1] class=build confidence=high — `htm@3.1.1` ships `/preact/standalone.umd.js` (13,296 B) plus `/dist/htm.umd.js` (1,364 B) and `/mini/index.umd.js`, and the fetched file body is a genuine UMD wrapper that falls back to assigning the global `e.htmPreact = {}`, i.e. it is inlinable as a classic `<script>` with no module loader.
  source: https://data.jsdelivr.com/v1/packages/npm/htm@3.1.1?structure=flat and https://cdn.jsdelivr.net/npm/htm@3.1.1/preact/standalone.umd.js | publisher: jsDelivr / npm (package author: Jason Miller / Preact team) | published: package version 3.1.1, file listing served live | accessed: 2026-08-01
- [D5-2] class=size confidence=high — Measured this run, not quoted: `htm/preact/standalone.umd.js` = 13,296 B raw / 5,340 B gzip -9; that single file contains preact core, the hooks implementation (the tail of the file defines `useDebugValue`/`useErrorBoundary`) and htm's tagged-template parser. Separately, `preact@10.29.8/dist/preact.min.umd.js` = 11,390 B raw / 4,852 B gzip and `preact/hooks/dist/hooks.umd.js` = 3,800 B raw / 1,580 B gzip.
  source: https://cdn.jsdelivr.net/npm/htm@3.1.1/preact/standalone.umd.js (byte count via curl | wc -c, gzip -9 | wc -c) | publisher: jsDelivr CDN | published: n/a (live artifact) | accessed: 2026-08-01
- [D5-3] class=license confidence=high — `preact@10.29.8` is MIT; `htm@3.1.1` is Apache-2.0. Both permissive, both G4-clean.
  source: https://registry.npmjs.org/preact/latest , https://registry.npmjs.org/htm/latest | publisher: npm registry | published: metadata for current `latest` tags | accessed: 2026-08-01
- [D5-4] class=build confidence=high — `lit@3.3.3` declares `"type": "module"`, its `exports` map lists only `.js` ES modules, and a flat file listing of `lit@3.3.3`, `lit-html@3.3.1` and `@lit/reactive-element@2.1.1` returns **zero** files matching umd/iife/global/nomodule/bundle. The `lit` package's own files are ~60–600 byte re-export shims. There is no published classic-script build to inline.
  source: https://data.jsdelivr.com/v1/packages/npm/lit@3.3.3?structure=flat , .../lit-html@3.3.1 , .../@lit/reactive-element@2.1.1 , https://registry.npmjs.org/lit/3.3.3 | publisher: jsDelivr / npm | published: current published versions | accessed: 2026-08-01
- [D5-5] class=build confidence=high — Lit's own tooling docs state the requirement plainly: "The only transformation required to use Lit on modern browsers is to convert bare module specifiers to browser-compatible URLs", and that "the build system needs to handle them" (for Rollup, via `@rollup/plugin-node-resolve`). A build step is therefore mandatory even for the "CDN" story, and its output is still ESM.
  source: https://lit.dev/docs/tools/requirements/ | publisher: Google / Lit team (official docs) | published: unknown (undated page) | accessed: 2026-08-01
- [D5-6] class=build confidence=medium — Svelte 5's published type definitions (`svelte@5.56.8/types/index.d.ts`) contain no `format?:` key in `CompileOptions` (grep for `format\??:` and `'iife'` returned nothing; `customElement?:` matched, proving the grep reached the option interfaces). Read as: the Svelte 5 compiler emits ES modules only and offers no IIFE output mode of its own. Medium confidence because this is inference from absence in the type surface, not an explicit doc statement.
  source: https://unpkg.com/svelte@5.56.8/types/index.d.ts | publisher: npm/unpkg (Svelte maintainers) | published: version 5.56.8 | accessed: 2026-08-01
- [D5-7] class=build confidence=medium — `vite-plugin-singlefile@2.3.3` (MIT, published 2026-04-17) does "inline all JavaScript and CSS resources directly into the final `dist/index.html` file" and explicitly contemplates local-file use (local HTML files as secure contexts, hash-based routing; History-API routing does not work over `file://`). But its README does **not** state whether the inlined script is emitted as `type="module"` or as a classic script, and documents no `rollupOptions.output.format: 'iife'` recipe. The critical link in Svelte's G2 chain is therefore undocumented.
  source: https://github.com/richardtallent/vite-plugin-singlefile , https://registry.npmjs.org/vite-plugin-singlefile/latest | publisher: Richard Tallent (author) / npm | published: 2026-04-17 (npm publish time) | accessed: 2026-08-01
- [D5-8] class=reactivity confidence=medium — Preact has no proxy/deep-reactivity layer in core: the UMD bundle's API surface is `h/render` plus hooks (`useState`, `useRef`, `useErrorBoundary`, …), i.e. re-render is triggered only by an explicit setter call, never by property access or mutation. Consequence for G5: 100k-row arrays parked in a `useRef`/module-scope variable are never wrapped, walked or observed — the "keep data out of the reactivity system" requirement is satisfied by default rather than by opt-out. Medium because this is read off the shipped API surface, not a doc page dedicated to large data.
  source: https://cdn.jsdelivr.net/npm/htm@3.1.1/preact/standalone.umd.js (API surface), https://preactjs.com/guide/v10/getting-started/ | publisher: Preact team | published: unknown (undated docs page) | accessed: 2026-08-01
- [D5-9] class=reactivity confidence=high — Svelte 5's `$state.raw` is documented verbatim as the large-data escape hatch: "In cases where you don't want objects and arrays to be deeply reactive you can use `$state.raw`… State declared with `$state.raw` cannot be mutated; it can only be _reassigned_… This can improve performance with large arrays and objects that you weren't planning to mutate anyway, since it avoids the cost of making them reactive." So Svelte's G5 story is real and first-party — G5 is not what cuts it.
  source: https://raw.githubusercontent.com/sveltejs/svelte/main/documentation/docs/02-runes/02-%24state.md | publisher: Svelte maintainers (repo docs, `main` branch) | published: unknown commit date on `main` | accessed: 2026-08-01
- [D5-10] class=build confidence=high — VanJS's official Get Started page documents the classic-script path explicitly: "To code without ES6 modules, add the following line to your HTML file instead: `<script type="text/javascript" src="https://cdn.jsdelivr.net/gh/vanjs-org/van/public/van-1.6.1.nomodule.min.js"></script>`", and offers `van-1.6.1.nomodule.min.js` for local download. The nomodule build is version-matched to the current npm release (1.6.1), so it is maintained in lockstep, not a legacy artifact.
  source: https://vanjs.org/start | publisher: VanJS (official site) | published: unknown (page undated; references current 1.6.1) | accessed: 2026-08-01
- [D5-11] class=build confidence=high — Note the trap: the **npm package** `vanjs-core@1.6.1` contains only `src/van.js` (4,988 B, ESM) and `src/van.debug.js`, with `exports: {".": "./src/van.js"}` — no UMD. The classic-script build lives only in the GitHub `public/` folder served via jsDelivr's `gh` endpoint. A screen based on npm alone would wrongly cut VanJS on G2.
  source: https://data.jsdelivr.com/v1/packages/npm/vanjs-core@1.6.1?structure=flat , https://registry.npmjs.org/vanjs-core/latest | publisher: npm / jsDelivr | published: version 1.6.1 | accessed: 2026-08-01
- [D5-12] class=reactivity confidence=medium — VanJS's whole API is five functions (`van.tags`, `van.add`, `van.state`, `van.derive`, `van.hydrate`); state is an explicit container object, not a proxy over user data, so a 100k-row array simply is not reactive unless you put it in a state. Its own README concedes that list rendering is out of core: "Want reactive list, global app state, server-driven UI, serialization and more? Check out VanX — The 1.2kB official VanJS extension." The heterogeneous-step-list pattern therefore likely pulls in a second dependency.

For a project one solo dev must carry for years, this is the material risk, not the technology. (Vendor self-description; not an independent contributor-graph measurement.)

The winning configuration for this project is the *same* standalone entry point in its `.umd.js` form, inlined — supported by the shipped artifact [D5-1] but not by the docs' happy path.

## Leads

- **Prototype-cheap Svelte reversal**: the single unknown is whether `vite build` with `rollupOptions.output.format: 'iife'` + `inlineDynamicImports` + `vite-plugin-singlefile` yields a `<script>` without `type="module"`. One 30-minute spike settles it. If it does, Svelte 5 re-enters on the strength of [D5-9] and should be re-screened rather than assumed cut.
- **Challenge the G2 premise itself**: G2 assumes `<script type="module">` is blocked over `file://`. The blocking mechanism is CORS on module *fetches*; a fully inlined module script performs no fetch. Worth an empirical check in Chrome 143 / Firefox 145, because if inline module scripts do run from `file://`, the gate loosens for Lit and Svelte both and the whole screen changes shape. Do not act on this without a browser test.
- **htm maintenance is the Preact combo's soft spot**: htm sits at 3.1.1 and I did not verify its last publish date this run. Check `time` in the npm registry doc and recent commit activity on `developit/htm` before finalizing — the runtime is 1.4 kB and forkable, so even an unmaintained htm is a survivable risk, but it should be named.
- **Lit's reactivity model was never the problem** — non-reactive class fields hold large data trivially, and plain-JS `static properties` authoring exists. If a bundler step ever becomes acceptable, re-screen Lit on ergonomics rather than re-litigating G2.
- **VanX** (`vanjs-ext`) needs its own G2 check — verify a `nomodule` build exists for the extension too, or VanJS's list ergonomics story collapses back to manual DOM.

## Looked for and could not find

- Any UMD/IIFE/global build in the Lit family — searched `lit`, `lit-html`, `@lit/reactive-element` file listings for umd/iife/global/nomodule/bundle; zero hits. Absence is well-evidenced, not merely unfound.
- An explicit Svelte doc statement that the compiler cannot emit IIFE — inferred from the absence of `format` in the 5.56.8 type definitions [D5-6]. Not the same as a positive statement; treat as medium.
- Whether `vite-plugin-singlefile` emits module vs. classic scripts — not stated in its README [D5-7]. This is the pivotal undocumented fact for Svelte.
- Publication dates for the Preact, Lit and VanJS doc pages consulted — all undated. Version numbers cited in them (VanJS 1.6.1) match current npm releases, which is the freshness proxy I used.
- htm's last publish date and recent commit activity — not checked (budget). Flagged as a lead.
- Measured byte size of `van-1.6.1.nomodule.min.js` — not fetched; the "1.0 kB gzipped" figure is a vendor README claim, not a measurement, whereas the ESM `src/van.js` measured 4,988 B raw / 1,770 B gzip unminified.
